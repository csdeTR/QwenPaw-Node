# UI 约定与性能测量口径

本文记录界面层的跨页面约束、已验证的错误做法，以及性能数据的测量方法。
这些条目全部来自实际调试，修改界面之前应通读。

分层与状态流转见 [architecture.md](architecture.md)；服务端接口与失败模式见 [protocol.md](protocol.md)。

---

## 1、边到边（edge-to-edge）适配

### 1.1 背景

`targetSdk = 35`。从 Android 15 起，系统对声明该 targetSdk 的应用**强制**边到边：
状态栏与导航栏变为透明，浮在应用内容之上。应用不再能通过系统自动避让获得留白。

实测环境为红米 K80（HyperOS，Android 15）。修复前，除设置页外的所有页面都被通知栏与手势条压住。

### 1.2 根因：Scaffold 的一条隐式约定

M3 `Scaffold` 的 `ScaffoldDefaults.contentWindowInsets` 取值是 **systemBars**，
但它注入的内容留白遵循一条容易忽略的条件：

> **只有当对应的 bar 槽位为空时，Scaffold 才把该方向的系统栏留白算进内容区。**

由此产生两种截然不同的结果：

- 设置页使用**不带** `topBar` / `bottomBar` 的 `Scaffold`，槽位为空，Scaffold 自动注入留白，因此显示正常；
- 其他页面把自定义栏传给 `topBar` / `bottomBar`，Scaffold 认为「这一方向由你自行处理」，不再注入留白，
  而自定义栏本身又没有处理，于是内容被系统栏压住。

用户反馈中「设置页除外」这一条线索，正是这个机制的直接体现。

### 1.3 规则

**底色仍然铺满系统栏区域（保持真边到边），只把内容让开。**

- **顺序不能颠倒：先 `.background(...)`，再 `.statusBarsPadding()`。**
  如果反过来写，留白区域位于背景之外，会显示父容器的底色，
  屏幕顶部因此出现一条与其他区域颜色不同的色带。这是最容易出现的视觉瑕疵。
- 自定义顶栏一律补 `.statusBarsPadding()`。
- 自定义底栏补 `.navigationBarsPadding()`。
- 需要同时避让键盘与手势条时，用 `NavigationBars ∪ Ime` **取并集**
  （`WindowInsets.navigationBars.union(WindowInsets.ime)`），**不要相加**。
  键盘高度本身已经包含手势条占用的部分，两者相加会把内容顶高出一截，
  表现为键盘弹出后输入条与键盘之间出现一段空隙。
- 留白要加在**有背景色的那个容器内部**。例如 `ChatInputBar` 的 inset 加在 `Surface` 里面；
  若加在 `Surface` 外面，Surface 之外会露出一条页面底色。
- **裸页面**（没有被 Scaffold 包裹的页面，如 `ConnectScreen`）自行补
  `statusBarsPadding()` + `navigationBarsPadding()`。
  留白要加在**页面这一层**，不要加进被复用的子表单（`InstanceForm`）内部。
  原因是设置页也复用该表单，而那边已经由 Scaffold 注入留白，加在表单内部会造成双重留白，
  表现为顶部出现一块明显多余的空间。
- 对话框走 Compose `Dialog`，其默认 `decorFitsSystemWindows = true`，不受边到边影响，无需处理。

### 1.4 已适配的位置与对应现象

| 文件或位置 | 处理方式 | 未处理时的界面现象 |
| --- | --- | --- |
| `ChatTopBar` | `statusBarsPadding()` | 会话标题与返回按钮压进通知栏，被状态栏图标遮挡 |
| `ChatListScreen.ListHeader` | `statusBarsPadding()` | 列表页标题与搜索框贴近屏幕顶边 |
| `ChatListScreen` 新建按钮 / 批量操作条 | `navigationBarsPadding()` | 按钮压住手势条，滑动返回手势与点击冲突 |
| `ChatInputBar` | `Surface` 内部使用 `navigationBars ∪ ime` | 发送按钮被手势条覆盖；键盘弹出时输入条与键盘之间出现空隙 |
| `ArchivedScreen` / `UsageScreen` / `ModelsScreen` | `statusBarsPadding()` | 标题压进通知栏 |
| `ConnectScreen` | 外层 `statusBarsPadding()` + `navigationBarsPadding()` | 连接表单顶部贴边、底部按钮压住手势条 |

### 1.5 验收基准

测量环境已从模拟器换成 redroid 15 容器：**720×1600、280dpi、手势导航**。

| 位置 | 期望值（原环境） |
| --- | --- |

| 聊天页输入条按钮 | 底边 y = 2293，位于手势条上沿（2337）之上 |

## 2、重组作用域

### 2.1 不要把 `derivedStateOf` 用 `by` 委托在页面作用域读取

`derivedStateOf` 会在其依赖的状态变化时重新计算，并把连续变化折叠为少量翻转。
它的价值正来自「折叠」：滑动过程中滚动位置每帧都在变，但「是否在底部」这个布尔值只在越界时才翻转。

问题在于**读取位置**。若在页面的组合作用域中用 `by` 委托读取，
这个布尔值一旦翻转，就会重组该作用域下的全部内容。

`ChatScreen` 曾因此产生实际开销：每次滑动开始与结束时，`atBottom` 都会翻转一次，
导致整屏可见条目连同 Markdown 正文被重组两遍。
用户感知为「一开始滑动就顿一下，停下来又顿一下」。

正确做法有两条，任选其一：

- 保留 `State` 对象（`remember { derivedStateOf { ... } }`），在**真正需要的位置**
  显式读取 `.value`，例如在协程内部判断；
- 把读取点封装进更小的组件内部，让重组范围收敛到该组件。

### 2.2 滚动相关的高频状态优先用 `derivedStateOf`

与之相对，滚动位置、能否继续滚动这类每帧都在变化的值，必须先用 `derivedStateOf` 折叠，
再交给 UI 使用。直接用原始滚动状态驱动 UI，会让每个滚动帧都触发一次重组。

## 3、列表与缓存

### 3.1 昂贵解析必须 `remember`

列表条目滚出视口后会被销毁，滚回来时重新执行组合。
因此 `MarkdownParser.parse`、行内样式 `AnnotatedString`、表格单元格内的行内样式，
都必须按内容 `remember` 缓存。

不做缓存的后果不是「稍微慢一点」，而是**每次滚回同一段内容都要重新完整解析一遍**，
在长列表中表现为持续的主线程开销，越往回滚越明显。

### 3.2 解析期的 `Regex` 必须提到文件级常量

`java.util.regex.Pattern` 的编译不便宜。把 `Regex("...")` 写在循环体内，
会让每一行文本、每一个表格单元格都重新编译一次正则。

本项目的 `MarkdownParser` 曾有两个正则写在循环里：

- `^\d+[.)]\s+.*`（有序列表判定）
- `^:?-{2,}:?$`（表格分隔行判定）

后者在一张十几行的表格上会被执行几十次。现已提升为文件级常量。

### 3.3 不要在重组中新建格式化对象

`SimpleDateFormat`、`Calendar`、`Scanner` 这类对象不应在每次重组时新建。
日期展示改用 `java.time.LocalDate`，并按时间戳 `remember` 缓存结果。

会话列表的时间标签曾因此产生明显开销：每次滑动、每一行都执行一次日期解析。

## 4、性能测量口径

### 4.1 模拟器上的掉帧百分比不可信

在 `-gpu host` 模式下（宿主 GPU 为 GTX 950），RenderThread 单帧 `Drawing` 可达 45ms，
`dequeueBuffer` 出现阻塞。此时掉帧百分比完全由 GPU 主导，无法反映客户端代码的差异。
用软件渲染（swiftshader）时情况更极端，GPU 项直接出现 4950ms 的量级。

**识别特征**：`dumpsys gfxinfo` 的直方图里 GPU 项远大于 CPU 项，
或 RenderThread 的 `Drawing` 单帧耗时超过 30ms。出现这种情况时，该次测量作废。

### 4.2 使用与 GPU 无关的主线程帧指标

正解是取 `dumpsys gfxinfo <pkg> framestats` 中
`HandleInputStart → PerformTraversalsStart` 的间隔。

Compose 的 doFrame 回调在 `performTraversals` 之前完成，
因此这一段就是「一帧里主线程真正花掉的时间」，与 GPU 无关，可以在模拟器上做 A/B 对比。

### 4.3 atrace 的两个坑

**必须带包名。** `atrace --async_start -c gfx,input,view` 采不到应用级 trace section，
`AndroidOwner:measureAndLayout`、`Compose:recompose`、`Recomposer:animation`、
`compose:lazy:prefetch:*`、`TextLayout:initLayout` 这些都不会出现。
必须写成 `atrace --async_start -a <包名> -c gfx,input,view`。release 包名是
`io.qwenpaw.node`，debug 包名是 `io.qwenpaw.node.debug`（见 [release.md](release.md) 4.1）。

**解析时 `B|<pid>|` 里的 pid 是进程 id，不是线程 id。**
`tracing_mark_write: B|<pid>|` 中的这个数字标识的是进程，
而嵌套栈的配对必须用行首 `comm-tid (pid)` 里的 **tid** 作为 key。

**识别特征**：解析脚本算出的总时长为 0.0ms，或某个 section 的累计时长出现数量级异常
（例如远超采集窗口长度）。两者都说明栈 key 用错了。

## 5、debug 与 release 的差距

### 5.1 数据

**debug 包明显更慢，评估流畅度必须使用 release 包。**

debug 变体 `isMinifyEnabled = false`：没有 R8 的内联与优化、没有 AOT、
没有 baseline profile，Compose 内部还会走 debug 断言路径。

同一份源码、同一会话（171 条消息）、同一手势，取主线程帧耗时：

| build | p50 | p99 | max |
| --- | --- | --- | --- |
| debug（三轮） | 1.41 / 1.75 / 1.72 ms | 26.8 / 4.7 / 3.7 ms | **43.3 ms** |
| release（三轮） | 0.77 / 0.65 / 0.68 ms | 2.7 / 2.0 / 11.4 ms | **11.9 ms** |

release 的主线程帧耗时约为 debug 的 **43%**，长帧从 43ms 降到 12ms。

debug 构建下的 atrace 分片可以印证这一点：`AndroidOwner:measureAndLayout` 累计 440–500ms
（单次最大 145.6ms）、`Compose:recompose` 208–244ms、`TextLayout:initLayout` 出现上百次。

在宿主机这种较快的 CPU 上，debug 的 p50 只有 1.4–1.75ms，看起来无碍。
但换算到中低端手机的 CPU 上，这个基数会被成倍放大，一旦跨过 16.67ms 的帧预算，
用户就会感知到卡顿。

> `scripts/e2e_acceptance.sh` 安装的是 **debug** 包。
> 因此「脚本通过」不等于「用户手上流畅」。

### 5.2 已被实测排除的方向

以下四个假设都曾被认为可能是滚动卡顿的原因，均已用实测否定。
再次遇到卡顿时，不要先往这些方向投入。

| 假设 | 当时为什么会产生 | 实测结论 |
| --- | --- | --- |
| 历史一次铺开太多条 | 长会话有 500 条以上消息，直觉上认为条目数量是负担 | LazyColumn 只组合可见项。对比窗口化 8 条与铺开 500 条，滚动时可见项数量一致，无差异 |
| `SelectionContainer` 嵌套导致指针节点翻倍 | 每个气泡都包了选区容器，怀疑指针事件开销 | 仅约 8%，属于噪声级 |
| Markdown 解析与正则新建是主因 | 聊天页每条消息都要解析 Markdown，看似重活 | 微基准 0.113ms/条、正则 1μs/次，量级不足 |
| `atBottom` 在父组合作用域被 `by` 读取 | 确实存在作用域过大的问题，且修改后有可测收益 | 重组从 221ms 降到 208ms（约 10%），`measureAndLayout` 无变化，因此不是根因 |

这四条中有三条本身是真实存在的问题，只是**量级不足以解释用户感知到的卡顿**。
把它们与真正的根因（构建类型）区分开，是这一轮排查的主要工作量。

## 6、字号缩放

UI 缩放与聊天正文缩放是**两条独立的链**：

- **UI 缩放**（`uiScale`）作用于整套 `Typography`，由 `QwenPawTheme` 提供。
  影响标题、按钮、列表等界面元素。
- **聊天缩放**（`chatScale`）只叠加在消息正文上，由 `ChatFontScale` 作用域包裹列表。
  顶栏与输入框仍使用 UI 字号。

两者都是连续值，不是档位枚举。

`Typography` 的构造开销不低，必须按缩放系数 `remember` 缓存；否则每帧重建整套字体定义。

**自定义固定字号必须跟随 `LocalChatFontScale` 一起缩放**，包括标题与代码块。
若使用硬编码的 `sp` 值，用户把聊天字号调大之后，这些元素会相对显得偏小，
整体排版失去一致性。

### 6.1 字号预览页

「设置 → 外观」的聊天字号一行提供「预览」，打开独立页面 `ChatPreview`。
预览页的约定：

1. **示例消息与聊天页同源。** 气泡、头部与正文缩放的实现与聊天页复用同一段代码，
   不另写一套缩略实现，否则预览与实际效果会不一致。
2. **底部输入框的位置换成字号滑块。** 预览页不展示可输入的输入框，
   把这一整块换成滑块与百分比读数，用户在同一屏内既能看效果又能改值。
3. **示例内容覆盖三类排版。** 用户气泡、助手气泡、公式与代码，
   这三类在字号放大后的表现不同，只放纯文本会漏掉溢出问题。
4. **说明行明确作用范围。** 文案固定为「只影响对话正文。顶栏与输入框不随字号变化。」

预览页滑块的取值范围与设置页那个滑块完全一致，共用同一个持久化键，
从任何一处调整都会同步到另一处。

## 7、时间显示与列表分组

### 7.1 服务端时间是 UTC，必须折算到本地时区

服务端给的是 UTC ISO 8601（`2026-10-29T02:13:41.029Z`，个别版本不带 `Z`）。
早期实现直接截字符串前 10 位当日期，等于按 **UTC 日界**划分「今天／昨天」：
东八区早上 7 点发的消息会被算成前一天。这是实际存在的偏差，不是理论风险。

统一入口是 `ui/TimeLabels`：

| 方法 | 用途 |
| --- | --- |
| `parse(raw)` | 解析到本地时区的 `ZonedDateTime`，失败返回 null |
| `timeOnly(raw)` | 消息气泡头部的 `HH:mm` |
| `relativeDay(raw)` | 分组用：今天 / 昨天 / `M月d日` / 完整日期 |
| `listStamp(raw)` | 会话列表右上的时或短日期 |

日期差用**本地日历日**相减，不用 24 小时差：用户说的「昨天」是日历概念，
跨夏令时或中途换时区时按小时算会偏。

### 7.2 分组三态

`GroupMode` 三档与 QwenPaw 网页版一致：按时间、按来源、不分组。单击按钮循环，
顺序 `TIME → SOURCE → NONE`，默认 `TIME`。

`ChatGrouping` 是纯函数，无 Compose 依赖，因此 `ChatGroupingTest` 能在 JVM 上覆盖
跨日边界、缺时间、未知分组这类情况。

两条贯穿两种模式的规则：

1. **置顶项单独成区并排最前。** 置顶的意义是「永远在我手边」，
   若按时间桶散落到「近 7 天」里，等于没有置顶。
2. **空桶不输出。** 只有表头没有内容的分区是噪声。

另有一条交互规则：**搜索时强制不分组**。分组会把命中的会话拆到多个表头下，
反而更难扫读。

表头用 `stickyHeader` 吸顶；不分组模式下只有一个无标题分区，表头不渲染。

## 8、消息气泡的结构

### 8.1 三段式

用户消息整体靠右、头像在最右；智能体消息整体靠左、头像在最左。上下结构一致：

```
[头像]  [昵称]          ← 第一行
        [2021.09.21 10:43:20]  ← 第二行，完整时刻
        ╭──────────╮
        │  气泡内容  │
        ╰──────────╯
        [复制] [复制为 Markdown]
        [输入 N · 输出 M · 模型 tokens]
```

- 头像 32dp 圆形。没有自定义头像时渲染「昵称首字 + 按名字取色的底色」——
  一个空圆圈比首字更难分辨谁是谁。同一名字永远得到同一颜色。
- **头像与昵称同处头部行，内容列独占整宽。** 头像若与内容同处一个 `Row`，
  内容列就必须让出 `8dp + 32dp` 的头像宽度，用户气泡的右侧、智能体气泡的左侧
  各留一条空白，气泡永远贴不到屏幕边缘。内容列用 `fillMaxWidth()`，
  头像不参与内容宽度计算。
- 昵称：用户侧取设置里的名字（默认「我」），智能体侧优先用消息自带的
  `metadata.original_name`，缺失时退回实例的智能体名。
- **昵称与时刻分两行，不合成一行。** 合成一行时昵称一长就只剩时间，或者时间被截掉；
  分开后两者各自完整，且用户侧右对齐、智能体侧左对齐，与头像位置一致。
- 时刻用 `TimeLabels.fullStamp()`，格式 `yyyy.MM.dd HH:mm:ss`。
  用户侧用创建时间，智能体侧优先用完成时间。
- **流式期间隐藏时间与复制按钮**。那时 `finished_at` 还没到，显示创建时间会让人
  以为回复已结束；复制也会复制到半句话，且按钮每帧抖动。
- 用量行只在该轮收尾消息上出现，且受设置开关控制。

**时间解析必须兼容带偏移量的字符串。** 服务端的 `metadata.timestamp` 形如
`2026-10-26T00:15:42.910613+08:00`，`Instant.parse` 在 Android 的 `java.time` 上
不接受偏移、会返回 null。`TimeLabels.parse()` 因此按 `Instant` → `OffsetDateTime`
→ 补 `Z` 的顺序依次尝试。**这类 bug 单测发现不了**，因为测试样本通常都是 `Z` 结尾。

### 8.2 为什么统计只挂一条

服务端把整轮的 `qwenpaw_turn_usage` 重复挂在**该轮每一条** assistant 消息上。
若逐条渲染，一个多步回合里每段正文下面都会重复同一组数字，
看起来像每段话都花了那么多。`HistoryMapper.markTurnEnd()` 按回合去重，
只让该轮最后一条带统计的正文保留。

### 8.3 头像规格

静态图裁剪为正方形后压到 500×500 PNG（不是 JPEG：头像多为带透明背景的截图，
JPEG 会把透明区染成黑色）。GIF 原样保存，由 `AvatarStore.imageLoader` 逐帧播放。

逐帧解码必须显式注册，否则 `AsyncImage` 只画第一帧：

| API | 解码器 | 说明 |
| --- | --- | --- |
| 28+ | `coil.decode.ImageDecoderDecoder` | 走系统 `ImageDecoder`，动画由框架驱动 |
| 26–27 | `coil.decode.GifDecoder` | Coil 自带 `Movie` 逐帧播放 |

minSdk 是 26，两条分支都必须留。静态 PNG 与 GIF 走同一个 `AsyncImage`，没有第二条渲染路径。

首字回落只在图片就绪前显示。图片就绪后不再叠在底下：带头像的 GIF 常有透明区域，
首字会从透明处透出来。加载失败（文件损坏、格式不支持）退回首字，不留空洞。

头像存在 `filesDir/avatars/`，不上传服务端。`AvatarStore.version` 是 StateFlow，
任何一次写入或删除都会 +1，界面据此重新读文件——设置里换完头像返回聊天页靠它生效。

**服务端头像（网页端设置的那一张）。** 服务端的 `avatar_owner()` 固定返回 `"console"`，
只有用户一份头像，没有按智能体区分的端点，因此这项只作用于用户侧，智能体头像仍走本地。

取值顺序由 `resolveUserAvatar(hasLocal, serverEnabled, hasServerImage)` 决定，纯函数、可单测：

| 本地有图 | 开关开 | 服务端有图 | 结果 |
| --- | --- | --- | --- |
| 是 | 任意 | 任意 | 本地 |
| 否 | 是 | 是 | 服务端 |
| 否 | 任意 | 否 | 首字 |
| 否 | 否 | 是 | 首字 |

两条规则容易在后续改动里被颠倒：**本地优先于服务端**（本机选的图是用户在这台设备上的
主动选择），以及**开关只作用于服务端**（关掉它的含义是「不显示」，不是「清空我的头像」）。

服务端图片缓存在 `filesDir/server-avatar/{selectedId}.img`，另有 `index.txt` 记当前 id。
用 id 而不是固定文件名：同一路径被覆写时，Coil 的内存缓存仍按路径命中，会继续显示旧图。
`selected` 为 null 时清空缓存并删除旧文件；id 未变时只发一次清单请求，不重复下载。
冷启动先读 `cached()` 上屏，再 `refresh()` 联网核对，因此断网也能显示上一次的头像。

### 8.4 选区配色与长按手势

**选区底色不得与它能覆盖的任何气泡底色同系。** 用户气泡底色是品牌橙
（实测 `rgb(255,127,22)`），若选区取 `colorScheme.primary`（同为橙），
叠上去完全看不见，用户会以为「选中失败了」。`Theme.kt` 因此单独给
`LocalTextSelectionColors` 一套蓝系配色：浅色 `#1F6FEB`、深色 `#7AA7FF`，
底色取把手色 32% 透明度。

长按与文本选择是两套互斥手势，不能同时挂在同一处：

- 普通态：气泡挂 `combinedClickable(onLongClick = 弹菜单)`，长按出
  「复制 / 复制为 Markdown / 选择文本」，**不直接复制**。
  直接复制会让想选一段话的人先被塞满剪贴板。
- 选择态：`SelectionContainer` 才包裹正文，同时**撤掉 `combinedClickable`**。
  两者共存时长按会被外层 `combinedClickable` 先吃掉，`SelectionContainer` 拿不到手势。
- 选择态必须有一个显式出口。底部操作行换成「完成选择」，否则用户选完没有回到普通态的路。
- **进入选择态的入口有两个：长按菜单与消息底部的「选择文本」按钮**，
  两者都要弹同一条轻提示，说明「完成选择」在这条消息下方。
  用户按的是「选择文本」这个字样，不一定知道退出入口在哪。

「复制」与「复制为 Markdown」必须是两种行为：「复制」走 `MarkdownPlainText.strip()`
剥掉标记，「复制为 Markdown」保留原文。两个按钮行为相同等于一个功能两个名字。

`strip()` 的边界：围栏代码块内的内容原样保留（代码里的 `*`、`_` 是语法本身），
删掉分隔线与表格分隔行时要顺手收掉相邻空行，否则会留下三连空行。

### 8.5 自行计算绘制区域时必须裁剪

凡是用 `drawImage` 或 `drawPath` 自己算 `dstOffset` / `dstSize` 的场景，
必须给容器加 `Modifier.clipToBounds()`。

原因：Compose 的绘制**默认不按布局边界裁剪**。绘制区域超出容器尺寸时，
多出来的部分会直接画到同一父容器里的其它兄弟节点之上。头像裁剪页就踩过这一点——
`drawImage` 的 `dstSize` 是「图片尺寸 × 有效缩放」，放大或图片长宽比极端时大于取景框，
溢出部分把顶部「取消 / 调整头像 / 保存」压住了。

`CropGeometry.clampOffset` 只保证图片**铺满**取景框，不保证**不溢出**，
两者是不同约束，不能靠位移计算替代裁剪。

这类问题用 `uiautomator dump` 查不出来（节点树正确，只是画错了），
只能靠截图取像素判断：沿中心列扫颜色突变点找容器边界，
再在容器外按网格采样确认没有前景像素。

### 8.6 工具交付的文件卡片

智能体调用 `send_file_to_user` 交付的文件渲染在回合末尾，独立成一个
`ChatItem.Files`，不塞进工具卡。原因：工具卡在「折叠结果」模式下整组收成一行摘要，
文件随之被折起来，而交付物恰恰是这一轮最需要看到的结果。

- 每个文件一行：44dp 缩略图、文件名、完整路径、右侧「已发送」。
- 缩略图只在图片类型存在。其它类型统一用 `Icons.Default.Description`，
  不按扩展名换图标——图标差异在 44dp 下分辨不出来，反而增加判断分支。
- 缩略图走 `ChatImageLoader` 的 data URI 分支。交付的文件字节来自工具输出里的
  base64，与历史消息里的图片共用同一套解码与 LRU 缓存，不另建加载器。
- 解码失败或格式不支持时退回到占位图标，不留空行。文件卡片本身仍然可读：
  文件名与路径才是这一行的主体。
- 图片行可点开 `ImageViewerDialog`，非图片行不可点。点不开的行不应有按压反馈。

同一回合里重复交付同一路径只显示一次，按路径去重；这一轮的卡片锚在
第一个携带交付的工具消息上，保证卡片与「处理完成 · N 步」的顺序稳定。

### 8.7 公式渲染

聊天页支持 `$…$`（行内）与 `$$…$$`、`\[…\]`（块级）两种写法。
渲染分两条路径，原因是二维结构在段落里没有位置放：

| 位置 | 方式 | 理由 |
| --- | --- | --- |
| 行内 `$…$` | 压成单行文本 | `InlineTextContent` 要预先给出固定尺寸，而公式高度随分式嵌套变化，估出来的框不是压字就是留空 |
| 块级 `$$…$$` | Row/Column 组合排版 | 独占一行，能用竖向叠放表达分式与上下标 |

行内降级的具体写法：分式写成 `a⁄b`（分子分母含运算符时加括号），根式写成 `√(x)`，
可映射的数字与正负号换成 Unicode 上标/下标（`x^2` → `x²`）。
有一个字符映射不到时整段退回 `^`，避免出现半上标半普通字的混排。

块级排版用组合而不是自绘 `Layout`：分式、根式、上下标都是「上下叠放 + 居中」，
组合式写法不必推算基线偏移，也不会在字号缩放变化时算出与实际测量不一致的尺寸。
字号逐层缩小，分式取 0.72、上下标取 0.58，与数学字体的 script 比例接近。

**容错优先，不做整条降级。** 未知命令降级成 `Sym("\\name")` 照原样画出来，
其余部分继续排版；只有花括号不配平、`\left` 缺 `\right`、嵌套超过 8 层这类
结构错误才让整条公式退回源码。此前的「一处未知命令即整条失败」让带 `cases`、
`\mathbb`、`\vec` 的公式全部退回原文，真机上一眼看上去就是「公式全都渲染不了」。

**多行环境与块级公式共用无上界宽度。** 块级公式放在 `horizontalScroll` 容器里，
父约束的 `maxWidth` 是 `Constraints.Infinity`。Compose 只接受 `Infinity` 本身，
传入 `Infinity - n`（哪怕是 n = 1）会抛
`IllegalArgumentException: Can't represent a width of … in Constraints`。
需要按定界符占位收窄内容宽度时，必须先判断是否无上界，判断集中在
`envContentMaxWidth`，由 `LatexLayoutTest` 守住。

**横线不能用 `fillMaxWidth` 画。** 无上界约束下它会拿到 `Infinity`，实际宽度为零，
分式的分数线与根号上的尾巴都会消失。改用 `SubcomposeLayout` 先量出分子与分母，
再按较宽一侧用 `Constraints.fixed(width, 1.dp)` 铺线。同理不能用
`Modifier.width(IntrinsicSize.Max)`：子项是多行环境（`SubcomposeLayout`）时，
固有测量会直接抛异常。

**段落里的裸上下标只认数字与花括号。** `H_2O`、`CO_2`、`x^2`、`x^{n+1}` 由 `MarkdownText`
转成 `BaselineShift.Superscript/Subscript` 的 span；`P_A`、`msg_id`、`user_name`
一律保持原文。判据见 `isBareScriptAt`，两条各挡一类误判：标记前必须是 ASCII 字母或数字，
因此 `[^1]`（前一个是 `[`）与「第_1_章」（汉字不是 ASCII）不排版；标记后必须是数字或 `{`，
因此标识符不再被拆走一个字符。花括号算作者的显式意图，`P_{A}` 仍排下标。
判据落在被标注的一侧而不是主体一侧，代价是 `C^2` 仍会排成上标——改判主体会让
`x^2`、`2^10` 一起失效。`readBareScript` 把连续数字整段收进一个下标，
否则 `x_12` 会排成「₁2」这种半截。反引号内与 `**…**` 内不转换。
上下标在基线上偏移之外**还要缩字号**：`inline()` 接收该块的基准 sp，
上下标 span 取 `baseSize * 0.58f`，与块级公式的 `LatexView` 同比例。
只做基线偏移时 `H_2O` 读起来是「一个大写字符掉下去」，比原症状更像排版错误。

三个基准各不相同：段落、列表、引用用 `MaterialTheme.typography.bodyLarge`，
标题按层级取 `headingSizeSp(level, scale)`，表格单元格用 `bodySmall`。
段落基准**可以直接从 `MaterialTheme.typography` 取**：M3 的 `MaterialTheme`
自身提供 `ProvideTextStyle(typography.bodyLarge)`，`ChatFontScale` 作用域内
`LocalTextStyle` 就是已乘过 chatScale 的 `bodyLarge`，与渲染字号严格一致。
（`LocalTextStyle` 的字号为 `Unspecified` 的说法不成立，见
[devlog](devlog.md) 43.2。与之配套，段落、列表、引用三处 `Text` 显式写出
`style = bodyLarge`，把「基准 = 渲染字号」这条等式固定下来。）

`remember` 的缓存键必须同时包含基准字号与缩放系数。只按 `blocks` 缓存时，
条目滚出视口再回来会复用旧字号的解析结果，上下标停在上一档大小上。
实测 `H_2O` 中 `H` 的墨迹高 30px、下标 `2` 为 17px（约 0.57），且未撑高行距。

**`_` 斜体按 CommonMark 的词边界配对。** 判定集中在 `closingUnderscoreEmphasis`：
开侧前不接词字符、开侧后不接空白、闭侧前不接空白、闭侧后不接词字符，
词字符按 Unicode 字母/数字算（汉字同样算）。因此 `snake_case`、「第_1_章」
「这是_重点_内容」保持原文，`_斜体_`、`见 _重点_ 内容` 仍然成对；
中文里要强调应写 `*重点*`。上一版把 `*` 与 `_` 共用「行内下一个 `_`」当闭合位置，
一个孤立下划线会把中间整段变成斜体（`附录_ 与 表_` 即为此例）。
`MarkdownPlainText` 的复制路径用同一条边界规则（`[\p{L}\p{N}_]` 而非 `\w`），
两处不能各写一份，否则界面上没有斜体、复制出来的文本却少一对下划线。
已知差异：复制路径不处理裸上下标，`H_2O` 在气泡里是下标、复制出来仍是 `H_2O`。

**流式输出时只有闭合的公式才渲染。** `$$` 与结尾的定界符之间没有内容时，
`MarkdownParser` 不让它成为 `MdBlock.Math`，而是留在普通段落里。
否则每帧都会拿半条公式去解析、失败、再退回源码，界面在两态之间反复跳。

**行内 `$` 与货币符号的区分**：起始 `$` 后必须紧跟非空白，闭合 `$` 前必须紧邻非空白，
且两者之间不含 `$$`。因此 `$5 and $10` 保持原样，不会变成公式。

自行实现而不是引入现成库的理由是许可：`jlatexmath-android` 为 GPL-2.0，
会传染整个 APK 的分发条款；WebView + KaTeX 则要额外打包几百 KB 的 JS，
且流式刷新时每帧都要重建 WebView。实现见 `Latex.kt`（解析）与 `LatexView.kt`（渲染）。

### 8.8 选择文本与原文页

点「选择文本」先弹一次三选：「显示」「不显示」「取消」。

理由是触摸选中的只是屏幕上渲染出来的文字：公式是二维排版的、表格被重画、
图片只剩占位，拖动选到的字符与原文并非一一对应。三个答案的后续：
显示 → 打开原文页；不显示 → 进原有的选择态并提示「完成选择」在消息下方；
取消 → 什么都不做。

对话框用 `ChoiceDialog`，三个按钮同排。不用 `DestructiveActionDialog`：
那个要把影响范围逐条列出，这里是并列的无破坏性分叉；
「不显示」与「取消」若分列两端，读起来会像两种不同程度的确认。

原文页 `MessageSourceScreen` 只做一件事：把源字符串等宽铺开、可拖动选中、可整条复制。
**不做 Markdown 渲染是刻意的**——这里要给的就是标记本身，再渲染一遍又回到与原文有差异的状态。
页面从聊天页进入，`parentOf(MESSAGE_SOURCE) = CHAT`，因此返回会回到聊天页并向右滑出。

## 9、顶栏状态、浮层与选项对话框

### 9.1 顶栏状态必须反映真实连接

顶栏状态行同时承载两件事：**服务端是否在生成回复**，以及**现在能不能连上**。
这两件事必须分开渲染，不能用一个「已连接」糊过去。

| 状态 | 文案 | 色点 |
| --- | --- | --- |
| 正在生成 | 「正在生成」 | 主色偏黄 |
| `LinkState.OFFLINE` | 「连接中断，点击重连」 | 错误色 |
| `LinkState.UNKNOWN` | 「正在连接…」 | `onSurfaceVariant` |
| 已连接 | `connectedLabel(boundUrl, boundLabel)` | secondary |

`UNKNOWN` **不能当已连接**。它是「还没被证明」的状态，冷启动与网络刚恢复时都会出现。
此前它落进 `else` 分支显示「已连接」，断网后因为没有任何请求立刻失败，
状态会一直停在上一轮的 ONLINE，与眼前事实相反。

`connectedLabel()` 的措辞规则：有别名且与地址不同 → 「已通过「别名」连接至「服务器名称」」；
别名与地址相同或别名为空 → 直接用地址，避免「「192.168.1.10:8088」」双重引号；
没有服务器名称时末尾写产品名 `QwenPaw`。

**地址的写法要按场景分开，不能合并成一个工具函数。**
顶栏那一行右边还有上下文胶囊，宽度很紧，而协议与默认端口对「连的是哪台机器」
没有任何信息量：`UrlDisplay.address` 一律去掉协议，`http` 的 80 与 `https` 的 443
一并省略，其余端口照写，IPv6 保留方括号。设置页的地址清单相反，
用户在那里要核对「这条到底是不是 https」，`compactUrl` 因此保留 `https://`。

比较 `label == url` 仍用原串：别名与地址是否相同是配置里的事实，
不能因为展示形式变了就误判成「有别名」。

**末尾的归属名不能直接用 `InstanceConfig.name`。** 名称是表单留空时由
`InstanceDraft.resolvedName()` 回落出来的首条地址，直接拿来会显示成
「已通过「EasyTier」连接至「10.0.2.9:8088」」——地址出现两次，且那不是正在用的那条。
正确做法是用 `InstanceConfig.serverDisplayName`：它拿实例的**全部**地址比对
（忽略协议前缀与结尾斜杠），命中任一条就返回空串表示「没起名字」。

排版细节：「连接至」后面接中文引号不留空格，接拉丁产品名留一个空格。
两者都写成空格会得到「连接至 「家里的机器」」，多出一个洞。

断网信号必须真的能传到聊天页。`AppViewModel` 的网络订阅里，
`if (!online) return@collect` 这类「先返回再处理」的写法会让断网分支永远空转。

### 9.2 「跳到最新」的可见条件

浮层按钮的语义是「跳到最新」，所以可见条件必须是**不在底部**。

- `visible = { !atBottom.value }`，写成 `atBottom.value` 正好相反：
  停在底部时常驻、上翻历史时反而消失。
- 判定容差用 `8.dp.toPx()`，不要写裸像素。24 像素在 xxhdpi 上只有 8dp，
  手指一碰就误判为离开底部，按钮会闪。
- 浮层自己读 `atBottom`，读发生在浮层内部，翻转时只重组这一小块，
  不会把整张消息列表连同 Markdown 正文一起拖下水。

### 9.3 「贴底」必须传偏移量，且跟随判定不能用实时位置

**首屏窗口必须把本轮的用户消息包进来。** 列表只铺末尾一页（`PAGE_SIZE = 8`），
而一个回合里的「思考 + 工具 + 多段正文」很容易超过 8 个条目。若起点只取末尾一页，
流式期间重新进入会话时界面立刻贴底，用户自己发的那条就在窗口之外，
上滑到顶也补不到页（见下一条），结果是永远看不到「我说了什么」。

`timelineStartFor(items, pageSize)` 取「最后一条用户消息的下标」与「末尾一页起点」
的较小值作为窗口起点。`rawStart` 的 `remember` 键必须带「列表是否已加载」这一维：
进入会话时列表先是空的，此时算出的起点是 0，只按 chatId 记忆会让历史落地后仍是 0，
等于整段历史一次铺开。

**补页守卫不能带 `running`。** 写成 `if (followTail.value || state.running) return`
时，生成期间停在顶部既不补页、提示行还一直写着「向上滑动可查看更早的消息」。
`followTail` 才是「用户想跟随底部」的真实意图，`running` 与补页无关。

三个约束叠在一起才能让长回复也稳定停在底部。

**一，`scrollToItem(index)` 的默认偏移 0 是「顶部对齐」。** 它把第 index 条的
**顶部**对齐到视口顶部。最后一条经常是几屏长的回复，那样只停在它的开头，
`atBottom` 仍为 false。贴底要写 `requestScrollToItem(index, Int.MAX_VALUE)`：
偏移超出内容范围会被钳到真实底部，等价于「滚到最后」。

`requestScrollToItem` 与 `scrollToItem` 的区别：前者只登记目标下标、由下一帧按新结构应用；
后者是挂起函数、按调用那一刻的结构计算，列表正在被整体替换时落点会偏。

**二，跟随与否不能用实时 `atBottom`。** 流式内容变长会重新分组，`ChatItem` 的 key
跟着变，LazyColumn 找不到原锚点、位置跳一下；跳完 `atBottom` 变 false，
若据此刻判断就永久停止跟随。改为由 `FollowTail` 状态机记录跟随意图，
`isScrollInProgress` 不能用来识别用户——它对程序化滚动同样为 true，
而贴底几乎每帧都在做。用 `interactionSource.interactions` 里的 `DragInteraction`，
并等惯性也停下（`isScrollInProgress` 转 false）再读最终位置。

`FollowTail` 是普通对象而非 `mutableStateOf`：它的取值只在副作用里读写、不参与组合，
因此不需要触发重组；抽出来是为了四条转移规则能在 JVM 里完整断言。

| 事件 | 结果 |
| --- | --- |
| `DragInteraction.Start` | 立即停止跟随 |
| `DragInteraction.Stop` / `Cancel` 且惯性停下 | 跟随与否 = 是否停在底部 |
| 发送消息 | 强制跟随 |
| 点「跳到最新」 | 强制跟随 |

第一条是本轮修的问题：此前只在松手后采样，按住上滑的几秒里流式内容仍把列表拉回底部，
表现为「拖不动、拖到一半被拽回去」。`Cancel` 也要采样，否则来电或布局突变打断手势时，
`pendingSample` 永远不会置位，跟随状态会停在上一次的值。

**收集 `interactions` 不能再套 `snapshotFlow`。** 它本身就是 `Flow<Interaction>`，
写成 `snapshotFlow { listState.interactionSource.interactions }.collect { ... }`
时 collect 拿到的是那个 Flow 对象，三个 `is DragInteraction.*` 分支恒不成立。
编译期会报 `Check for instance is always 'false'`，但只是警告、不影响构建成功——
本轮正是先构建出包、看到这三条警告才发现拖拽响应整体失效。
正确写法是 `listState.interactionSource.interactions.collect { ... }`。

同一个 `when` 里的 `userScrolled = true` 也会因此从不执行，而补页逻辑用它判断
「用户是否真的滚动过」。症状是长历史永远补不出下一页，与拖拽问题不是同一处表现，
排查时容易当成两个 bug。

**三，触发贴底的变化不止一种。** 回复结束时 `reconcileWithServer` 用服务端历史整体替换：
本地 id（`local-user-N` / 流式 `msg_id`）全换成服务端 id 而条数可能不变；
同时流式标记被清掉，一串「正文 + 思考 + 工具」被折成一个 `Steps`，条目数反而减少。
因此要挂三个键：最后一条的 id、最后一条的文本长度、分组后的条目数。

**补页也要让路。** 列表被整体替换的瞬间旧锚点消失，`firstVisibleItemIndex` 可能短暂塌到 0，
被误判成「翻到顶了」而把几个月前的历史铺回来。补页副作用开头加
`if (followTail || running) return`。

### 9.4 「正在生成」等待行

首帧到达前界面上只有用户气泡。这一段时间可能持续数秒（尤其是在没有当前会话、
还要先 `createChat` 的情况下），缺少反馈会让用户以为发送失败。

判据是 `running && messages.lastOrNull()?.role == USER`，抽成纯函数
`needsAwaitingPlaceholder(messages, running)`。

不要写成「没有任何 `streaming` 的智能体消息」：`ResponseStatus=completed` 会先清掉流式标记，
而 `running` 要到流处理结束才复位，中间这段空档会让等待行重新冒出来又立刻消失。
按「最后一条是不是用户消息」判断，任何智能体消息（正文、思考、工具、错误）落下来就永久退场。

文案取「正在生成」，不用「已发送」：此刻请求未必已经到达服务端，写成状态确认是错的。

### 9.5 二级选项一律居中对话框

聊天页需要选一项的操作（切换模型、审批模式、移动到分组）统一走 `OptionDialog`：
`Dialog` + 圆角 16dp 卡片 + `LazyColumn(heightIn(max = 420.dp))`，
选中项右侧对勾，`leading` 放固定首项（如「跟随智能体默认」「未分组」）。

不用 `DropdownMenu` 的理由：这些列表项较长（模型名形如
`CodeArts/deepseek-v4.1-flash-1017`），下拉菜单宽度会跟着内容涨，
在窄屏上挤成一列；居中对话框有稳定的最大宽度与限高。

思考强度在 0.2.2 改为居中对话框，与上面三类一致。原因是它的取值不再固定为几个短标签：
数值预算型模型要显示 token 数，档位型模型要展示服务端给出的全部档位，
`DropdownMenu` 放不下读数与滑块，也无法表达「跟随默认」与「关闭思考」之间的连续关系。
对话框里只放一条滑块与一句说明，见下一小节。

### 9.5.1 思考强度对话框

`ThinkingDialog` 的结构固定为：标题「思考强度」、当前取值一行、一条 `Slider`、
一行说明、右下角「恢复默认设置」。

1. **两种模型共用一条滑块。** 离散档位型（`control.kind = "effort"`）按 `efforts` 停靠，
   支持关闭时最左再加一格；数值预算型（`kind = "budget"`）连续，读数是 token 数。
2. **初值取当前实际生效的值。** 跟随默认时用服务端 `effective` 里的 token 数，
   不能取 `budget_min`。实测 Qwen3.8-Flash 的 `budget_min = 1`，
   按它起始会让对话框显示「1 tokens」，与「跟随默认」的实际含义相反。
3. **松手才提交。** `onValueChange` 只更新本地显示，`onValueChangeFinished` 才发
   `PUT /api/chats/{id}/thinking`，否则拖动过程每一帧都会打一次接口。
4. **关闭带宽度是区间的 12%。** 关闭带左端为 `budget_min - 12% × (max - min)`，
   判为关闭的中点是关闭带与 `budget_min` 的中点，与官方 Web 端同一判据。
5. **预算型模型的档位描述按比例分段**：低于 25% 为「轻量思考」，25%–60% 为「均衡思考」，
   60%–85% 为「深入思考」，85% 以上为「充分思考」。
6. **菜单项显示当前值。** 聊天页「更多」菜单里写作「思考强度：跟随默认」这类形式，
   只在当前模型支持调节时出现；切换到不支持调节的模型后该行消失。

输入框上方的模型胶囊必须是可点的（`.clickable(role = Role.Button)`），
点它打开与「...」菜单里同一个对话框——胶囊显示当前模型，点它换模型是最直觉的路径。

### 9.6 菜单图标与操作行样式

所有下拉菜单项的图标走 `MenuIcons.of(MenuAction)` 单一映射，图标全部取自
`material-icons-extended`，不新增 drawable：矢量图标跟随主题着色，深色模式下不会出现
一列黑色小图。`MenuAction` 是枚举而不是散落的字符串，`MenuIconsTest` 遍历全枚举断言
`of()` 不为 null——新增动作时漏配图标的表现只是「这一项没图标」，肉眼扫菜单未必看得出来。

`Icons.Default.Label` 已废弃，镜像布局的图标要用 `Icons.AutoMirrored.Filled.Label`。

消息下方的操作行有文字与图标两档，默认文字。理由是三项里「复制」与「复制为 Markdown」
的图形几乎无法区分，图标档需要文字兜底。图标档下 `contentDescription` 仍取同一段文字，
读屏与自动化测试都靠它，不能因为换成图形就把文字丢掉。

### 9.7 设置页的两级结构

设置页是一级列表 + 二级子页，不再把七组内容平铺在同一页上。

一级页每行由图标、标题、当前取值与右侧箭头组成，按「服务器」「个人资料与外观」
「此手机」「关于」四段分组。副标题必须写出当前取值（「跟随系统 · 字号 100%」
「折叠结果 · 用量关」「记录中 · 5 类事件」），而不是只给一句说明：
用户不点进去也能确认状态，是这个结构相对平铺页面的主要收益。

**新增类入口放在卡片内部最后一项之后**，写法是 `Divider()` + `ActionRow(text = "…")`，
与「添加实例」一致。空列表时同样要保留该入口：一个项目都没有的页面，
这是唯一的创建路径，把入口藏在「非空才有」的分支里会让用户无从下手。

子页复用同一个 `Scaffold`，只切换内容区，因此标题栏与返回行为只实现一次。
进入子页时滚动位置回到顶部（`LaunchedEffect(page) { scrollState.scrollTo(0) }`），
沿用上一页的位置会让用户落在半截内容里。这里的 `page` 取自 `current.page`，理由见下。

`AnimatedContent` 的 targetState 必须是「页 + 该页依赖的数据」整体（`SettingsNav`），
不能只传页面枚举。**内容槽内部同样不能读外部的 `section`**：它和 targetState 同步变化，
点击瞬间已是新值，正在退出的旧槽位会被画成新页面。
两处都要读 `current.page`——先取一次 `val page = current.page`，再让顶栏副标题、
滚动重置与内层 `when` 全部读它。写操作（`onClick` 里的 `section = …`）保持不变。

系统返回键按层级后退：表单 → 方式选择 → 关闭添加；子页 → 一级列表 → 关闭设置。
实现见 `BackHandler(enabled = nav.page != SettingsPage.MAIN)`。

服务器行的副标题在实例名与地址相同时只说一次。连接流程在名称留空时用地址当名称，
不去重会显示成「10.10.0.211:8088 · 10.10.0.211:8088」。

### 9.8 按来源分组时的排序

`ChatGrouping.rankOf(kind)` 给出五级权重，`order` 只在同一权重内生效：

| 权重 | kind | 位置 |
| --- | --- | --- |
| 0 | `custom` | 自建分组最前 |
| 1 | `default` | 默认分组 |
| 2 | 其他内置、null | 排在未分组之前 |
| 3 | `cron` | 定时任务 |
| 4 | `subagents` | 子智能体最末 |

定时任务与子智能体置底，依据是它们由后台自动产生，不是用户当下要处理的会话。
**不能只按服务端 `order` 排**：实测该字段在不同服务器上并不一致，一台把 `cron` 给 1、
另一台给 3，只按 order 排会让定时任务偶尔顶到默认分组之前。

未分组会话（`groupId` 为空或指向不存在的分组）单独成区，位置紧随「其他内置分组」、
在定时任务之前——它属于用户自己产生的会话，不该被自动任务的表头压在下面。
置顶分区仍最优先，不受上述权重影响。

同权重内 `order` 相同时保持服务端返回的列表顺序（`withIndex()` 参与排序），
否则同一份数据两次渲染的顺序可能不同，用户会觉得列表在跳。

### 9.9 会话图标

每个会话可以在长按菜单里「设置图标」：8 个预设（Material 矢量）或从相册选一张图。
图片优先于预设，保存一类时清掉另一类，因此两者实际不会共存；
`resolveChatIcon` 仍按「图片 > 预设 > 默认」判一次，因为从备份恢复时两份可能同时存在。

图片存 `filesDir/chat-icons/{sha256(chatId) 前 16 位}.png`。用哈希而不是原 id：
渠道会话 id 带冒号与斜杠，直接拼进路径轻则建不出目录，重则写到目录之外。

只在非紧凑排版下显示：紧凑排版把整个左侧图标区都去掉了。删除会话时调
`ChatIconStore.clear(chatId)`，包括批量删除——图标是本机数据，服务端不知道它的存在。
留着的话，新建一个同 id 的会话会显示上一次的图标。

### 9.10 主页面栈的过渡方向

方向按「入口按钮在哪条边缘」决定，返回是进入的反向，不按页面枚举序推导。

| 转场 | 位移 |
| --- | --- |
| 聊天页 → 对话列表（入口在左上角） | 抽屉：列表从左侧滑入、退出时向左滑走，被盖住的聊天页只淡入淡出 |
| 列表 → 设置 / 归档 / 用量 | 深入：从右滑入，返回向右退出 |
| 设置 → 运行日志 | 深入：从右滑入，返回向右退出 |

沿枚举序推导不可行：`LIST` 在 `Screen` 里的序号比 `CHAT` 大，按序号会把进入判成「深入」，
点左上角时列表会从右边弹出，与按钮位置相反。`parentOf(screen)` 显式给出父页，
`BackHandler` 据此逐层后退；设置页的父页是列表而不是聊天页，
否则「设置盖住列表」这层关系在返回时被跳过，方向也就无从推导。

位移幅度：抽屉半屏、子页三分之一屏。再小在 220ms 的动画里会被看成单纯的淡入。

### 9.11 界面文案与内置分组名

界面统一使用「对话」，不出现「会话」。`strings.xml` 之外的中文字面量同样适用。

三个内置分组的服务端名称是英文，读取时按 `kind` 映射成中文：
`default` → 未分组，`cron` → 定时任务对话，`subagents` → 子智能体对话。
自建分组保留用户起的名字，只有名称为空时才退回 id。

映射集中在 `groupTitle(group)`，列表表头、顶栏的当前分组标签、长按菜单的
「移动到分组」对话框都走这一处，避免列表显示中文而菜单显示英文。

### 9.12 图标集统一为 lucide

界面图标全部取自 `io.qwenpaw.node.ui.theme.QwenIcons`，几何图形源自 lucide 0.400.0
（ISC 许可）。选它的依据是官方 Console 用 `lucide-react`：`ui-vendor` 打包产物里
该库出现 232 次，同一套图形才能让两端的线宽与圆角看起来一致。
工具页的 19 个图标取自同一套库的 0.562.0，理由见 9.16。

构建方式是统一参数：24×24 视口、2px 描边、圆头端与圆角接、`fill = null`。
描边色恒为 `Color.Black`，由 `Icon(tint = …)` 的 ColorFilter 整体替换，
因此深色模式下不会出现一列固定黑色的小图。

新增图标的做法是从 `lucide-static` 取 SVG 转成 path 数据，不手抄。转换有四类静默错误：

| 现象 | 原因 |
| --- | --- |
| 图标位置空白 | 只含 `circle / rect / line` 的 SVG 漏了分支，path 为空 |
| 圆形跑到画布外 | `circle` 的起点写成 `cx`，应为 `cx - r` |
| 圆角矩形画塌 | 四段弧的顺序错位；正确顺序是上边 → 右上弧 → 右边 → 右下弧 → 下边 → 左下弧 → 左边 → 左上弧 → 闭合 |
| 取不到图 | `more-vertical` / `alert-triangle` 在 0.400.0 改名 `ellipsis-vertical` / `triangle-alert` |
| 编译不过 | 图标名撞 Kotlin 关键字，`package` 只能写成 `packageIcon` |

**转换必须做渲染对比，不能只看编译与单测。** `ImageVector` 只要 path 非空就是合法的，
形状错了任何断言都发现不了，而这些错误曾整批进入真机包。验证方法是：
把原始 SVG 与转换后的 path 用绝对定位排成两列、各 64×64，
用 `chrome --headless=new --screenshot` 截一张图，把两块区域二值化后算墨迹 IoU，
要求每个图标 ≥ 0.98。实测修正后 59 个图标全部 ≥ 0.986。

`QwenIconsTest` 只能守住可观测的三项：视口一律 24×24、内部名字与属性名一致、
任意两个图标不是同一个对象。形状本身必须靠上面那步比对。

### 9.13 空态首页

空对话时展示智能体头像（56dp）、标题「你好，我今天能帮你做什么？」、
副标题「我是一个智能助手，可以帮助你解答问题。」，以及两张预设卡片。

头像走 `ChatAvatar`，因此在设置页换的智能体头像会直接反映到这里。
智能体侧没有本机图片时回落到内置的 `agent_default.png`；用户侧仍用首字 + 底色，
因为自己的头像缺省时，通用标志不如首字好辨认「哪个是我」。

预设点击后先弹「发送这条消息？」。依据是触屏误触成本高，且这两条会真的建立一个对话。
### 9.14 底部输入条的候选列表与列表页筛选

**斜杠命令候选内嵌在输入条内部，不用 `Popup`。** 输入条的 `Column` 已经挂了
`navigationBars ∪ ime` 的内边距，内嵌的候选自然被键盘顶上去，不必自己算浮层位置；
`Popup` 开新窗口后要么抢焦点导致键盘收起（恰好发生在用户正要继续打字时），
要么点到窗口外无法穿透。`ChatScreen` 的 `bottomBar` 本来就在随状态改变高度
（审批条、错误条、语音面板三处先例），内嵌不引入新的布局问题。

候选限高 200dp 后内部滚动；分类标题用 `labelSmall`。点击候选项只写草稿、
不接管焦点，写回内容是 `"/name "`（带尾随空格），既能直接接参数，也让候选立刻收起。

**候选只在「整条草稿以 `/` 开头且其后无空白」时出现。** 这与服务端
`SlashCommandRegistry.resolve` 的判据一致；正文中间的 `/` 不是命令，
名字后一旦出现空格就进入参数阶段。

**请求失败静默。** 补全缺失不影响手打命令，失败时不弹错误、不清空已有候选。

**会话列表的频道筛选用一行 chip，只在候选多于一个时渲染。** 位置在搜索行之下，
横向滚动不换行；首项固定「全部」，候选按名称排序（服务端每次刷新都会重排，
首次出现顺序会让 chip 位置漂移）。候选必须从**未过滤**的完整列表算：
从切片结果算会让候选在选中后退化成单个、控件消失，用户被锁死在该频道里。
筛选状态不持久化——换服务器或换智能体后旧频道可能根本不存在。

筛选管线是「先按频道切片，再在切片里搜索」，`onSelectAll` 的基数因此自动跟随可见项。

### 9.15 工具行与命令文案的形态

**工具行是「两行文字 + 一组控件」，整行不挂 `clickable`。** 左侧第一行是
`图标 + 中文名`，第二行是中文描述；右侧在启用时依次放「同步 / 异步」两段圆片与启用开关。
行内已有两个可点区域，整行再加点击后事件会同时落到两处，点圆片时启用开关会被顺手改掉。
关闭态的点击区域靠开关本身，与设置页其它开关行一致。

**分段圆片用 `selectable` 而非 `clickable`。** 圆片是一组单选，
`clickable` 生成的语义节点不带选中态——`uiautomator dump` 里 `checked` 与 `selected`
都是 `false`，读屏也念不出当前选的是哪一个。写法是
`selectable(selected = …, role = Role.RadioButton, onClick = …)`。
圆片只在工具启用时出现：关掉的工具不会被执行，留着异步选项会让人以为设置没生效。

**工具行不加英文工具名。** 中文名与描述已占两行，再加一行英文会把每行堆到 4 行，
比原先的两行开关还高，与「更清爽」的目标相反。需要与服务端字段对账时看接口，
不在界面上并置。

**斜杠候选只列面向对话的命令。** 内部命令用黑名单剔除
（`CommandCopy.isUserFacing`），不用白名单：服务端还会注册插件与技能提供的命令，
白名单会把它们一并挡掉。过滤排在前缀匹配之前，否则全量与收窄结果来自两个不同的集合，
用户会看到「先出现、后消失」的条目。

**中文文案查表，服务端仍是英文。** 命令与工具的译名集中在
`ui/LocalCopy.kt` 的 `CommandCopy` 与 `ToolCopy`，未收录的条目回退到服务端原文
（插件工具、技能命令走这条）。服务端没有 i18n 接口，译文只能从 Console 打包产物摘取，
因此这是一份静态数据，不随服务端版本自动更新。

### 9.16 工具分组与图标、环境变量页的三段结构

**工具分组按官方静态表，不按服务端 `category`。** `GET /api/tools` 的内置工具
`category` 实测为 `null`，照它分组会把 33 个工具全部塞进「未分类」。
官方 Console 的规则是：`source_plugin_id` 非空的插件工具用 `category`，
内置工具查 `toolPresentation-*.js` 的 `TOOL_PRESENTATION`。
客户端把这份表照搬到 `ui/settings/ToolGrouping.kt` 的 `TOOL_GROUP_OF`，
组顺序固定为 `files / web / media / agents / runtime / migration / other`，空组不输出。
服务端新增内置工具且未收录时落入「未分类」，不影响其它组的渲染。

**工具行的图标是 lucide，不再用服务端下发的 emoji。** 官方 `TOOL_PRESENTATION`
每项带一个 lucide 组件（0.562.0），客户端逐个还原成 `QwenIcons` 里的等价 path
（转换规则见 9.12），由 `ToolGrouping.kt` 的 `TOOL_ICONS` 映射到工具名。
未收录的工具用 `QwenIcons.wrench` 兜底。`view_audio` 在官方表里没有条目，
按语义取 `volume-2`。DTO 的 `icon` 字段仍照常解析，只是不再展示。

**环境变量页常驻三段：已配置、实时配置、只读配置。** 分段依据是 catalog 的
`mutability`：`hot_runtime` 的两项进「实时配置」，`startup_only` 的 15 项进「只读配置」。
「已配置」仍是 `GET /api/envs` 落盘的完整清单，因此被改过的实时项会在两段同时出现；
已配置段给这类行挂「实时配置」小标签，实时配置段给 `configured=true` 的行挂「已修改」，
让两处的关系可见，而不是当成重复项删掉其中一处。

**只读项整行可点，弹窗直接显示明文。** 只读项不含用户密钥，用户点进来是为了核对值。
弹窗首句固定为「仅供查看，QwenPaw 运行期间不能修改。」（与官方 `startup_only` 文案一致），
下面列当前值、默认值、来源、只读原因、说明与修改方式。
说明文案见 `ui/settings/EnvCatalogCopy.kt`：官方只提供了两条流式超时项，
其余按 `qwenpaw/constant.py` 与 `config/config.py` 的读取位置补写，属于客户端自撰。

**删除与恢复默认都走二次确认。** 复用 `ui/common/DestructiveAction.kt` 的
`DestructiveActionDialog`，列出变量名与遮罩后的当前值。恢复默认不是销毁数据的操作，
通过 `confirmDanger = false` 让确认按钮用强调色而不是错误色。

### 9.17 工具卡片操作区、排期表单与双时区对照

**工具卡片的操作区只在运行中且服务端已登记时出现。** 条件是
`!tool.done && ChatUiState.toolCalls[callId] != null`。服务端对已完成的条目只保留
约 60 秒缓存，结束后一律 404，因此不在结束的卡片上保留按钮。
操作项为「取消执行」（先弹 `DestructiveActionDialog`）、「转入后台」（仅 running）、
「推迟转后台」（仅 offload 时限存在）、「延长执行超时」。
状态徽标统一四种写法：`running` → 运行中、`offloaded` → 已转后台、`completed` →
已完成、`end_state == "interrupted"` 或 `force_cancelled` → 已取消。
倒计时一行只在有可显示的时限时出现。执行超时字段非空即显示；**后台时限只有在服务端
策略为「自动转入后台」时才显示，策略为「保持前台」时整段不出现**，
两个时限都有时较短的在前、另一个放同一行括号里；
减到 0 写「即将转入后台 / 即将中止」，不再报秒数。

**两个时限的动作要分开写明，不能都叫「转入后台」。** 转入后台与执行超时是两个独立的时限：
前者到期后工具在后台继续跑，后者到期后工具被中止。主句按字段取值措辞，
自动转后台的剩余时间写「N 秒后自动转入后台」，执行超时的剩余时间写「M 秒后中止」。
两个都在时显示「N 秒后自动转入后台（M 秒后中止）」；只读到超时一个字段时显示「N 秒后中止」，
**后台时限读到了但策略不是「自动转入后台」时也按这一种显示**——到期后工具仍在前台，
报「N 秒后到达后台时限」只会让人以为它马上要转走。

实测（2.2.2.post1，`execute_shell_command` 执行 `sleep 90`）：
服务端 `default_action` 为 `offload` 时显示「9 秒后自动转入后台（79 秒后中止）」；
为 `keep_foreground` 时只剩超时一项，显示「94 秒后中止」。

**工具卡片运行超过 7.5 秒会自动展开。** 与官方网页一致：命令迟迟不结束，
继续只显示一行「运行中」会让用户以为卡住，因此到时主动展开，露出参数、输出与操作项。
常量 `AUTO_EXPAND_MS = 7500L` 与判定 `autoExpandDue()` 在 `ui/chat/ToolDeadline.kt`，
由 `ToolDeadlineLabelTest` 覆盖。**用户手动切换过就不再自动动**：
`userToggled` 为真表示用户已经表达过意图，此后不再被自动展开打断——
否则用户刚收起又被弹开，比不自动展开更烦。

**排期表单提供「快捷」与「自定义」两种模式，并按需回落到直接编辑。**
快捷是固定预设（每 5 / 10 / 15 / 30 分钟、每小时整点、每天 09:00、每周一 09:00、
每月 1 日 09:00）；自定义按频率类型逐项填出 5 字段表达式，表达式本身只读展示。
打开「直接编辑表达式」后变成输入框。`parseCronExpression` 只做客户端能生成的形状的逆运算，
认不出就保留原文并停在直接编辑模式，不猜测性重写——服务端接受 3 段与 4 段写法，
客户端若强行归一化会把用户写的东西改坏。第 5 段必须同时认数字
（`1`…`7`）与三字母缩写（`mon`…`sun`），后者是服务端归一化后的实际输出。

**双时区对照用页面内嵌块，排序固定为客户端在前、服务端在后。**
两边同偏移（实测 UTC+8）时整块不显示。时区名用 IANA 原名，偏移量按该时刻现算，
夏令时地区不同月份会不同。已保存任务取服务端 `next_run_at`，不本地重算；
表单草稿才用 `nextRuns()` 在本地推算，且只支持客户端能生成的表达式形状，
自定义表达式认不出时只保留说明行、不显示推算时间。
入口放在「设置 → 服务端配置 → 定时任务」。

**目标会话选择器显示会话名称，并支持搜索；`console` 频道不出现。**
`GET /api/cron/dispatch-targets` 的元素只有 `channel` / `user_id` / `session_id`，
**没有名称**，名称要从 `GET /api/chats` 按 `session_id` 配对补齐（`CronUiState.chatNames`）。
补不到时退回显示 `session_id`，不显示空白行，也不拦保存。
`console` 是网页与手机端自己的通道，移动端定时任务唯一可用的投递通道就是它，
因此频道选项里过滤掉它：列出名字反而让人以为要选什么。若服务端还派生了其它频道，
仍然显示出来供切换。

### 9.18 公网地址的安全提示

**判定只用两个前提：地址会被公网访问到，且缺一项防护。** 主机判据复用
`InstanceRepository.isLocalHost`（与「没写协议时按 http 还是 https」同一套规则），
缺的防护指「服务端不要求登录」与「用明文 http」两条。内网地址、解析失败的地址一律不提示：
误报一次，之后的真告警都会被忽略。

**「要登录」取 `enabled && has_users`，不是 `QWENPAW_AUTH_ENABLED`。** 开关打开但没有注册用户时
服务端仍不要求登录，按开关判断会把这条提示写反，实测会漏掉最严重的那一段。
`assessSecurity` 的参数因此叫 `loginRequired`，不叫 `authEnabled`。

**三条触发路径都要有。** 引导式添加验证成功后、填表添加验证成功后、每次进程启动一次。
以前只有引导式那条路会弹，走默认填表页的用户永远收不到提醒。

**两条风险分别是两个对话框，按严重程度依次出现。** 先弹「未启用登录」，
关掉之后若地址仍是明文 http，再弹「通信内容未加密」；两条都没有风险时不弹。
合成一个长对话框时，用户往往只看前半段就点掉，而后半段关于证书与反向代理的处置
恰恰是他需要照着做的那一条。弹窗顺序的状态收在 `SecurityNoticeDialog` 内部，
调用方仍只传一个 `SecurityNotice`。

**「文档」只在登录这条上出现**，打开
`https://qwenpaw.agentscope.io/docs/security#Web-%E7%99%BB%E5%BD%95%E8%AE%A4%E8%AF%81`。
点「文档」与点「知道了」都按关闭当前这一条处理，并继续到下一条；
用浏览器打开后停留在同一个弹窗上，用户回来还得再点一次，属于多余的一次操作。

**对话框打开期间「下一步」不可点**（`canNext` 带 `securityNotice == null`），
否则提示会被用户直接点掉。填表页没有「下一步」，靠模态对话框本身挡住后续操作。

**关闭开关要二次确认，并在关闭的当下收起已弹出的提示**，否则提示会悬在屏幕上，
与「已关闭提示」这个选择互相矛盾。

### 9.19 添加实例表单的输入法适配

**两个入口共用同一套处理：首次启动页与「设置 → 服务器 → 添加实例」的表单。**

首次启动页在根布局上给 `navigationBars ∪ ime` 的并集留白；
设置页的各子页则在最外层 `Column` 上调用 `imePadding()`，并让表单自己滚动。
两种写法的效果一致：键盘弹出时表单整体让开，输入框不会被遮住，
滚到底部也能看到「取消 / 添加」按钮。

实测（redroid 15、720×1600）：点击「服务器地址」后键盘弹出，
地址框完整可见；键盘保持弹出时向上滑动，底部按钮完整显示在键盘上方。

**不要只给输入框加键盘避让。** 表单有多个字段与按钮，只避让当前输入框时，
下面的字段依旧被挡住；behaviour 需要作用在整块可滚动内容上。

### 9.20 收件箱筛选条

**来源与智能体都做单选，不做多选。** 服务端的 `source_types` 支持多值，
但移动端宽度下多选的选中态难以辨认，且 web 控制台的推送消息页也是单选。
客户端因此只传 `source_type`，不传 `source_types`。

**筛选条改为两个带维度前缀的按钮，不再用横向滚动的 Chip 行。** 原来的 Chip 行有两个问题：
来源与智能体入口同排，看上去像同一组选项；六个来源加一个智能体在 411dp 宽度下一行放不下，
必须横向滚动才能看到后面的来源。现在左侧是「来源 · 当前值」与「智能体 · 当前值」两个按钮，
维度写进文案，右侧只在筛选生效时出现「清除」，点击同时复位两个维度。
两个维度共用同一个 `InboxFilterDialog`：竖向列表、项高 48dp、选中项右侧打勾，
列表过高时内部滚动，不做横向滚动。

**两个维度都用同一个竖向对话框，首项负责清除筛选。** 与 9.5 的二级选项约定一致；
一个实例通常只绑定一个智能体，列表往往只有一项，因此首项写「全部」而不是「全部智能体」，
避免在只有一项时出现同义重复。读取失败时只显示首项并注明「未能读取智能体列表」，
不弹错误。

**筛选必须交给服务端，不在本地过滤已加载的条目。** 本地过滤只能筛出已取到的 30 条，
`total` 与未读数都会失真。切换筛选时清空列表、显示加载态，再按新参数取第一页。

**筛选生效时隐藏「全部已读」。** 服务端的 `all: true` 清除整库未读，
筛选到某个来源时点它会把范围外的未读一并清掉，与用户看到的范围不一致。

**筛选生效且没有结果时，空态文案换成「没有符合条件的记录」**，
不再显示「收件箱是空的」，也不显示「定时任务与记忆写入的结果会出现在这里」这行说明。

**未读数跟随筛选范围。** 筛选状态下服务端返回的 `unread_count` 只统计符合条件的条目，
顶栏直接显示这个数字；插件推来的全局未读数在筛选期间不参与更新。

### 9.21 聊天输入条的单框结构

**所有控件装进同一个圆角框，框外只留斜杠命令候选。** 结构自上而下是附件条、
输入框（最小 44dp、最多 6 行）、高 40dp 的工具栏。参考 openclaw 的 Android composer：
附件与语音分处框内外时，底部会占掉接近三行的高度，而工具栏各控件彼此独立，
收进框内后视觉上只有一块区域。

**工具栏不使用描边按钮。** 图标按钮 34dp、无底色，按下与录音高亮用 12% 的 `primary` 底色；
顺序固定为「+ / 模型名 / 思考 / 麦克风 / 发送」，发送靠右。

**模型名是纯文字按钮，不是胶囊。** 胶囊与容器的 1dp 描边会争视觉重心；
透明按钮加 12dp 下拉箭头即可表达可点，限宽 132dp、超出尾部省略。

**发送键是 34dp 圆角矩形（圆角 10dp），与 console Web 一致。** 不可用时用 `outlineVariant`；
运行中在同尺寸内显示 10dp 停止方块，点击中断。

**「+」菜单承载「这一轮怎么跑」的设置。** 菜单宽 176dp、项高 44dp，
顺序固定为「添加附件 / 魔法命令 / 审批模式 / 全屏输入 / 智能体工作区」。

- 「审批模式」与「智能体工作区」的当前值都放在**第二行整行**，不用右侧限宽的写法。
  右侧只剩八十来 dp 时，`default` 这类短名字会被截成「defa…」，稍长的审批档位同理。
  换行后标题保持不变，第二行整行省略，可读性明显更好。
- `approvalLevel` 为空时不渲染「审批模式」这一项，不留空行。
- 五项都作用于「接下来这一轮怎么跑」，因此从右上角菜单整体搬到这里。
  右上角只留对话本身的动作；分组项也去掉 `:分组名` 后缀，固定写「移动到分组」。

**「魔法命令」是一次列全的斜杠命令清单。** 它与输入框里键入 `/` 后的补全共用
`presentableCommands` 与 `groupByCategory`，因此两处永远同源，不会出现一份能发、
另一份找不到的情况。菜单项用 `sparkles` 图标；弹窗内按分类分组，组名用 `primary` 色，
每条命令一行命令名、一行灰字说明；没有描述的命令（例如服务端新增的 `/new`）只显示命令名，
不留空行。

- 单击把 `commandInsertion()` 的结果写入草稿并关闭，与补全点选的行为一致。
- 长按在列表之上再叠一层详情，给出「作用」与「示例」两段；示例用等宽字体、浅底，
  可以直接照抄。详情关闭后回到清单，不退出整个弹窗。
- 长按不可见，标题下必须有「点按填入输入框，长按查看用法」这一行提示。
- 命令说明与示例分别来自 `CommandCopy.descriptions` 与 `examples`，
  详情比列表那句更具体（`details`）。插件与技能注册的命令没有固定形态，
  详情回退为 `/命令名`，不编造参数。`CommandCopyTest` 逐条核对两张表没有遗漏。

**思考按钮是 lucide `brain` 轮廓加按强度填充。** 填充比例取 `ThinkingScale.fillRatio`：
`effort` 按档位序号均分，`budget` 按 token 区间线性映射，关闭与 `inherit` 为 0。
液体层用 `clipRect(top = 18 - 17 × ratio)` 裁出下半部分，配 `#FFD1A3 → #FFA348 → #F57808`
纵向渐变，比例变化用 300ms 的 `tween` 过渡。不做 console 的液面波浪动画：
触屏上收益低，且会持续占用帧。

**轮廓路径必须从 lucide 原样复制，不要手写近似。** 曾按印象重画这八条路径，
把相对弧 `a4 4 0 1 1 …` 与绝对弧 `A4 4 0 1 1 12 18 …` 混用，
画出来是两个小圆圈叠在一起，看上去像「b₀」。现用 console 网页那份
lucide 0.562.0 的八条 `d` 原样，描边宽度 2f（lucide 默认值，18dp 下约 1.5dp）。
改描边宽度或缩放时保持这两者一起变，否则轮廓会变糊。

**滑块松手只提交，不关闭对话框。** 拖动过程中每帧都会回调，若顺带关窗，
连续调几档就要重开几次。现在 `onSet` 只写入取值，退出只由关闭按钮与返回键触发。

**圆角 20dp、描边 1dp。** 聚焦且未录音时描边取 `primary`，其余取 `outlineVariant`；
容器底色 `surfaceVariant`，外层 `Surface` 仍是 `surface`，系统栏区域不会出现色差。

**全屏输入铺在聊天页内部，不包成 `Dialog`。** 对话框是独立窗口，实测
`WindowInsets.ime` 在其中恒为 0，`SOFT_INPUT_ADJUST_RESIZE` 也不生效
（`DialogProperties` 的 `usePlatformDefaultWidth`、`decorFitsSystemWindows`
与 `DialogWindowProvider.window` 三种改法都试过，发送按钮照样被键盘整块盖住）。
现在改成从 `ChatScreen` 顶部提前 `return`、整页渲染 `FullscreenInput`，
键盘让位跟随宿主 Activity，`windowInsetsPadding(WindowInsets.ime)`
加在最外层 `Column` 上即生效。代价是全屏输入期间聊天页不参与组合，
这与「整页接管」的语义一致，关闭后草稿与滚动位置仍在。

**全屏输入打开后要等第一帧再要焦点。** 在首次组合里直接 `requestFocus()`
会被窗口的初始焦点覆盖，表现为打开后键盘不弹、用户还得再点一下输入区。
正确写法是在 `LaunchedEffect` 里先 `withFrameNanos { }`，再 `requestFocus()`
并调用 `LocalSoftwareKeyboardController.show()`。

**工作区弹窗从 `browse-dirs` 逐层浏览，不再只收绝对路径。** 弹窗上半部分仍是输入框，
下半部分是按当前路径读到的子目录列表，行内为文件夹图标加目录名，点击进入。
「上级」回到上一层，「刷新」重新读取，「使用此目录」把浏览到的路径写回输入框；
读取失败与空目录各有独立文案（「无法读取这个目录，可能不存在或没有权限」
与「这个目录下没有子目录」），不弹错误。列表固定高 188dp，
外层整列可滚动，键盘弹出时按钮仍可见。请求固定带 `show_hidden=true`：
不带这一项时服务端可能返回空的 `dirs`，看上去像目录里什么都没有。

### 9.22 受信任的连接

**按主机匹配，不含端口。** 同一台机器换端口不改变风险属性；按端口记会让用户为
`10.0.0.5:8088` 与 `10.0.0.5:9000` 各加一次。归一化集中在 `normalizeTrustedHost`：
去协议前缀、截断 `/` `?` `#` 之后、取方括号内 IPv6、单冒号去端口、去尾部点、转小写，
无法识别返回 null；`isTrustedHost` 两侧都归一化后比较。

**白名单只过滤提示，不改判定。** `assessSecurity` 的两条规则与三条触发路径都不动，
弹窗照常计算，命中白名单时不写入 state、不弹。

**安全弹窗里说明这个功能。** 两个阶段都在按钮上方加一行：「如果这台服务器是你自己的，
可以在「设置 → 服务器 → 受信任的连接」里添加该地址，之后不再弹出本条提示。」
不做可点击跳转：提示可能在首次连接时出现，此时设置页不可达。

**存储用 `StringSet`，键名 `trusted_hosts`。** 初始化时逐项归一化并丢弃非法值；
移除某个 host 后重新连接同一地址，提示恢复。

### 9.23 设置页「服务端配置」的行的顺序

「服务端配置」卡片里的行按**是否写入服务端**排序，只读展示放最后：

1. 配套插件（开关，其余功能的前提，排在最前）
2. 工具 / 环境变量 / 定时任务 / 模型与提供商（都会写服务端状态）
3. 工作区文件 / 备份 / 检查点 / 后台策略
4. 用量统计（纯只读，排在卡片末尾）

依据：一个卡片里混放「会改服务端」与「只看一眼」的入口时，用户点开后者的预期是
「看完就退」，把它插在中间会让相邻的配置入口看起来也像只读。
新增行时按这条排，不要按实现先后顺序追加。

**两个页面都是独立的 `Screen`，不新增 `SettingsPage` 枚举项。** 与工作区、备份、
检查点一致：它们有自己的返回落点，塞进设置页的二级页会让返回逻辑分叉。

### 9.24 图表：空数据与刻度

用量统计的趋势图用 Vico 画，三条约定在实现时被设备验收逼出来：

- **空数据不给空坐标系。** 没有趋势数据时直接显示一行「所选时间范围内没有调用」，
  不组合图表。空的折线图会画出一块带网格的空白，看起来像加载失败。
- **轴格式化器不能返回空串。** Vico 对这一点有硬校验，返回 `""` 会抛
  `IllegalStateException` 并整页崩溃（实测在切换时间范围时触发）。
  刻度由 `ItemPlacer` 控制；格式化器只负责把值转成文字，越界时夹到有效范围。
- **纵轴不要截断成整数。** 区间上限低于 1 时 Vico 会给 `0.2` / `0.4` 这类刻度，
  统一 `toLong()` 会得到一排「0」。写法是「大数走 k/M、整数原样、其余保留一位小数」。

**多条序列写在一个 `lineSeries {}` 块里。** 分两次调用会得到两个 Partial，
图层只消费第一个，第二条线静默消失——不报错，只是图上少一条。

**第二条线不能用主题的 `tertiary`。** 本项目 `tertiary` 是警告色 `#FAAD14`，
与主色 `#FF7F16` 只差一点色相，2dp 细线几乎分不开。第二条用 `onSurfaceVariant` 的灰，
并让图例的色点与线一致。

### 9.25 返回时保留滚动位置

**从列表进入某一项、再返回，列表应停在离开时的位置**，而不是回到顶部。
设置页是最容易踩到的一处：分区切换与页面切换各有一层 `AnimatedContent`，
两层都会销毁离开页面的组合，页内的 `rememberScrollState` 跟着一起没了。

两条写法：

- 页内的滚动位置存在页面外层（`rememberSaveable` 的整型列表，按分区索引），
  用 `rememberScrollState(initial = 保存值)` 恢复。不要写成「先建在顶部，再
  `LaunchedEffect` 里 `scrollTo`」——那会在切换动画结束后补一次可见的跳动。
- 整页级的返回（设置 → 工作区 → 返回）需要 `rememberSaveableStateHolder()` +
  `SaveableStateProvider(key)` 把 `rememberSaveable` 存下来，否则整页重建，
  连当前分区都会丢。

**未访问过的页面仍从顶部开始。** 恢复位置只对「来过又回去」成立；
第一次进入任何页面都应该看到它的标题，而不是上次别处的偏移。
