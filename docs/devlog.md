## 1、立项与可行性（2026-10-25）

起点是一个可行性问题：QwenPaw 是否已有 Android 客户端，若没有，做到「该有的都有」的难度如何。

此前的调研已经确认两件事：官方与社区都没有 Android 客户端；QwenPaw 使用纯 REST + SSE，
不像 OpenClaw 那样需要 WS 网关与节点能力协商，因此工程量低一个量级。

本轮进一步确认 L2 的可行性，结论如下：

- L2 所需能力服务端基本都已具备，**不需要改动 QwenPaw 源码**，这是项目能够成立的前提。
- 有两项需要重新定义而不是直接实现：**离线自动补发**（QwenPaw 没有 outbox 概念）与
  **实时推送**（没有推送通道，Console 自身也是轮询）。
- 有一个前置问题必须先定：**直连还是代理**。QwenPaw 的鉴权是可选的，
  直连局域网地址是最省事的路径。

**项目范围在本轮即已固定**，此后未再变更：

| 项 | 决定 |
| --- | --- |
| 目标 | 只做 L1 + L2，不做 L3 管理面 |
| 连接 | 直连，不做代理层 |
| 自动补发 | 不做，仅保留草稿箱与手动重试 |
| 实时推送 | 不做，审批走 2.5s 轮询 |
| Mermaid | 不做，降级为可复制源码 |
| 构建方案 | 采用当时最新（Kotlin 2.1 / AGP 8.7.3 / compileSdk 35） |
| 测试深度 | C 级（功能可用且关键路径通过验收） |

在项目开始阶段就把「不做什么」固定下来，后续节省了大量反复讨论。
[protocol.md](protocol.md) 第 13 节的「已知取舍」正是这一轮的产物。

**环境**：用户要求安装 javac 与 Android 开发环境，并指定使用 **redroid（Android 12）**。

## 2、环境搭建与 L1+L2 首版（2026-10-25）

用户离开前留言：环境弄好后先做一份开发计划，然后直接开始。

### 2.1 redroid 未能启动

依次尝试了 `docker.1ms.run`、`daocloud`、`1panel`、`rat.dev` 等镜像源，
`redroid/redroid:12.0.0_64only-latest` 全部拉取失败，表现为无进度或鉴权返回 401。

最终改用本机 KVM 与 Android 15 模拟器（AVD `qp35`）完成 C 级测试。
binder 模块已通过 `modprobe` 加载，用户后续自行拉取 redroid 时环境是通的。

### 2.2 首版交付

约 4600 行 Kotlin，分层为 `data/`（API、SSE、Room）、`ui/chat/`、`ui/settings/`。
核心文件：

- `QwenPawApi.kt`：auth、version、agents、chats、console、approval 全套端点
- `ChatStreamClient.kt`：SSE 长连接，支持 `reconnect: true`
- `ChatEventParser.kt` / `StreamAccumulator.kt`：把增量帧折叠为消息
- `ChatViewModel.kt`：发送、停止、重连、审批轮询、草稿
- `MarkdownText.kt`：轻量 Markdown 渲染器，覆盖表格、代码块、行内样式
- `InstanceStore.kt`：多实例管理，token 使用 `EncryptedSharedPreferences`
- `AppDatabase.kt`：草稿与历史缓存

### 2.3 一处测试基础设施的妥协

Compose 语义树在无头模拟器上不稳定：由 `createAndroidComposeRule` 托管的 UI 测试
反复出现「Compose 层级未附着」，而应用本身运行完全正常。

因此设备端测试收敛为验证「Activity 能启动、内容视图真实渲染」，
界面细节验收改由 adb 截图脚本承担。这是测试基础设施的限制，不是功能缺陷。

这一妥协直接影响了后续策略：**能覆盖的逻辑一律写成 JVM 单测**，设备端只做冒烟。

**结果**：50 个 JVM 单测全部通过，仪器化冒烟测试 1 个通过。

## 3、资源事故（2026-10-25）

### 3.1 现象

用户报障：整个 GNOME 桌面失去响应，内存与 swap 接近耗尽。

### 3.2 原因

当时连续执行了 `./gradlew` 全量构建与 `connectedDebugAndroidTest`，
并与设备测试、模拟器、Gradle daemon、Kotlin daemon 叠加：

| 进程 | 内存占用 |
| --- | --- |
| `qemu-system-x86_64`（模拟器 qp35，已运行 3 小时） | 3.6 GB |
| Gradle daemon（`-Xmx3072m`） | 2.8 GB |
| Kotlin 编译 daemon（`-Xmx3072m`） | 1.1 GB |

三者合计超过 7.5G，加上桌面环境自身（gnome-shell 372M、壁纸渲染 213M），
8G 的 swap 被完全占满。**gnome-shell 卡住的原因是 swap thrash，而非 shell 自身的问题。**

更无谓的是，那次设备端测试本身也失败了（`INSTRUMENTATION_FAILED`，测试 APK 未安装成功），
内存被消耗却没有产生任何结果。

### 3.3 教训固化

用户要求把这些约束写入 agent 约定文件，重点关注编译与构建环节的资源占用。
由此形成 [AGENTS.md](../AGENTS.md) 第 1 节的硬约束，核心几条：

- 构建与设备测试**不连跑**，逐个执行
- 动手前先 `free -h`，可用内存低于 3 GB 时先关闭进程
- 用完即关：`gradlew --stop` / `pkill -f KotlinCompileDaemon` / `adb emu kill`
- 模拟器内存固定 2048 MB，不加
- 优先增量构建（`installDebug` / `testDebugUnitTest`），不使用 `gradlew build`
- 单测优先于设备测试

此后每一轮重活之前都会执行 `free -h`，也确实多次拦住了「模拟器与构建同时运行」的做法。

## 4、真机验收（2026-10-25）

模拟器操作繁琐，用户提供了真机 `192.168.1.20:5555`（LM-G820N，Android 12，arm64），
可通过 `ssh lg` 免密登录 Termux，adb 走 TCP 5555，锁屏密码已关闭。

### 4.1 真机的坑（均已写入 AGENTS.md）

- **Termux 保活 Magisk 模块**会定期把 Termux 拉到前台。看到界面切到 Termux 不是应用崩溃，
  重新执行 `am start` 即可。用户提前说明了这一点，避免误判。
- **中文输入法把 `.` 与 `:` 打成全角**（`。`、`：`），`adb shell input text` 输入地址会变形。
  应用侧后来在 `normalizeBaseUrl` 中做了全角到半角的折叠。
- 输入框获得焦点后键盘会挡住按钮，点击前需先 `input keyevent 4` 收起键盘。
- 屏幕会自动息屏，且偶发**唤醒无效**（`mWakefulness=Asleep` 持续，`input keyevent 26/82` 均无效）。
  此时应通过 `pidof` 与 `logcat -b crash` 确认进程存活且无崩溃，而不是当作应用问题排查。

### 4.2 A6 断网场景

用户询问 A6 断网场景应当如何操作，并贴出了 `uname` 输出。

由此发现**手机具备 root（Magisk）**：直接 `adb shell` 得到的是 uid=2000，
但 `su -c` 可以取得 uid=0。此前判断「真机没有 root」是错的。

脚本随后改为自动探测三种提权方式（已 adb root、`adb root` 成功、su 免密），
并依据 `HOST` 中的端口封闭网络，不再写死 8088。

需要留意的边界：封闭的是服务端端口 8088，不是 adb 使用的 5555。
误封 5555 会直接断开 adb 连接。

### 4.3 验收结果

A1–A6 全部通过：审批卡片弹出与回传、图片上传、断线重连接回运行中的输出、
停止后服务端回到 idle、多实例隔离、断网中文提示与草稿保留及重试成功。

### 7.1 MiSans 字体：从子集到完整

第一版打包的是**子集**（约 200KB，仅含项目自身文案用到的字）。
结果是智能体回复中出现生僻字时回退到系统字体，**视觉效果不一致**。

两次判断都成立——前期以一致性优先，后期以包体优先，取舍随项目阶段变化。

### 7.2 语音输入：从系统识别到 sherpa-onnx

第一版计划使用系统 `SpeechRecognizer`，几乎不增加包体。
用户要求支持实时字幕，因此改用 **sherpa-onnx**（k2-fsa，Apache-2.0），全部在本地运行。

决策过程经过两次调整：

1. 用户最初确定「默认使用系统识别，本地模型作为可下载的附加能力」；
2. 随后改为「语音功能必须额外下载模型，同时在设置中提供是否显示该按钮的开关」。

最终形态：模型为 126MB 压缩包（解压后约 168MB），在设置页手动下载，
并提供「显示语音按钮」开关。

### 7.3 语音实现的三个问题

**问题一：识别不出文字。** sherpa 日志显示 `in_sample_rate: 1600`。
原因是 `OnlineStream.acceptWaveform` 的第二个参数是**采样率**，而非采样数，
而实现中一直把 buffer 长度当作采样率传入（那个 4000 实际是 `minBufferSize`）。
修正后识别正常。

**问题二：按钮点击无响应。** 初期怀疑是 `AnimatedVisibility` 拦截了点击事件，
或面板每帧移动导致点击落空。**实际原因是点击坐标错误**——面板位置会随消息数量变化。
改用 `uiautomator dump` 动态获取坐标后恢复正常。

由此确立约定：操作界面时坐标一律从 dump 动态获取，不凭截图目测，
因为截图是缩放的，按截图坐标点击会落空。

**问题三：按住说话时中途松手。** 最初手指滑出按钮范围即停止录音。
用户要求手指在不离开屏幕的前提下持续录音。
实现改为只跟踪按下那一根手指的抬起（`awaitFirstDown` 配合跟踪相同 id 的 `pressed` 状态）。

### 7.4 其它补齐项

- **智能体选择**：用户指出手动输入 id 的体验很差，因为不会有人特意记住这个 id。
  改为填完网关后拉取 `/api/agents` 列表点选，手填 id 淡化为备用方案。
- **页面切换动画**：使用 `AnimatedContent` 做淡入与轻微水平位移，返回时反向。
- **时间不对齐**：标题使用 `weight(1f, fill = false)` 并跟随一个弹性 `Spacer` 抢占空间，
  导致时间缩进随每行标题长度浮动。改为标题 `weight(1f)` 占满剩余宽度（超长自动省略）、
  时间固定贴右。
- **左侧圆角方块**：原本显示会话名首字（出现「U」「新」这类看不出含义的单字），
  改为对话气泡图标，当前会话以橙色点亮。

## 8、性能第一次攻坚（2026-10-26）

用户反馈每个页面上下滑动都有卡顿。

### 8.1 走过的弯路

**弯路一：怀疑 MiSans 字体。** 假设是 `Compose` 的 `Text` 每次遇到不同字重都会触发完整字体解析。
实测关闭 MiSans 后反而更卡（jank 32% 升至 54%），说明字体不是主因。
但当时样本量太少，该测法本身也不严谨。

**弯路二：在设置页做测量。** 设置页内容少，无法体现真实差异。

**弯路三：只依赖 jank% 判断。** 真机 LM-G820N 上测出列表页 65%、聊天页 80% 的 jank，
但 `dumpsys gfxinfo` 的 jank% 在设备性能偏低时噪声很大，且会被 GPU 项主导。
这一指标需要谨慎使用，当时尚未意识到（详见第 13 节）。

### 8.2 实际找到的问题

| 问题 | 修法 |
| --- | --- |
| 2.5s 轮询每次 `copy` 出新 state，导致整页重组 | 改为有变化才更新（approvals 未变化时 `return@onSuccess`） |
| `QwenPawTheme` 每帧重建 `Typography` 与字体族查表 | 按 `(scale, family)` 做 `remember` 缓存 |
| `SideEffect` 每帧重设状态栏外观 | 改在 `LaunchedEffect(dark)` 中只执行一次 |
| `timeLabel()` 每次重组都新建 `SimpleDateFormat` 与 `Calendar` | 改用 `java.time.LocalDate`，并按时间戳 `remember` |

**效果**：列表页 jank 从 65% 降到 8.78%，聊天页从 80% 降到 5.16%，设置页基线约 3%。

这一轮是有效的，但并不彻底。第 37 轮用户再次反馈滑动卡顿。
当时的修法都集中在「减少重组次数」，而真正的量级问题在别处，直到第 13 节才查清。

## 9、全方位开发计划（2026-10-26）

### 9.1 先核实服务端能力，再写计划

- `PUT /api/chats/{id}`，请求体 `{"pinned": bool}`：置顶，与重命名共用端点
- `POST /api/chats/{id}/archive` 与 `/unarchive`：归档（**运行中的会话会被拒绝**）
- `GET /api/chats?archived=true|false`：按归档状态过滤
- 服务端**没有** summary 字段，因此会话摘要只能由客户端生成
- 服务端**没有**图片下载端点，但发现 `GET /api/files/preview/{绝对路径}` 可用

过程中误操作将一个真实会话归档，随后通过 unarchive 还原。
由此确立：在用户的真实数据上执行写操作需要格外谨慎。

### 9.2 图片消息的字段问题（影响最大的一次）

服务端在 `runtime/message_convert.py` 的 `_request_input_to_msgs` 中读取的是**扁平字段**
`image_url` / `video_url` / `file_url`，**不是**早期协议中的嵌套结构
`{"type":"image","source":{"url":...}}`。

早期版本按嵌套结构发送，服务端会**静默丢弃**该内容块：不返回任何错误，
图片无法进入模型上下文，历史中也只留下文字。排查完全依赖阅读服务端源码。

正确形状：

```json
{"type":"image","image_url":"/home/u/.qwenpaw/workspaces/default/media/xxx.png"}
```

历史侧返回的则是 `data:image/png;base64,...`，由服务端将本地文件内联为 data URI。

**渲染方案**：不引入 Coil，`ChatImageLoader` 直接使用 OkHttp 与 `BitmapFactory`，
支持 `data:`、`http(s)://` 与服务端本地路径三种形态。
大图先读取尺寸再用 `inSampleSize` 采样，避免 OOM。

### 9.3 补完的功能

会话摘要（取前 20 个会话各拉一次详情，截取最后一条有内容消息的前 60 字）、置顶、
归档与已归档页、上下文用量明细、导出与复制 Markdown、思考模式与模型切换入口。

## 10、包体瘦身与 GitHub 仓库（2026-10-26）

用户反馈包体过大，同时提供 GitHub token，要求创建仓库并将 MiSans 改为从 GitHub 拉取。

### 10.1 诊断：主要成因不是字体

133MB 的 debug APK 构成如下：

| 组成 | 体积 |
| --- | --- |
| sherpa-onnx `.so` × 4 ABI | **约 98 MB** |
| dex（debug 未优化） | 44 MB |
| MiSans 字体 × 2 | 15.8 MB |
| 其它 | 约 10 MB |

MiSans 仅占 12%，**4 个 ABI 的 native 库才是主因**。

### 10.2 两项措施

1. **只保留 `arm64-v8a`**（`ndk.abiFilters`）：`.so` 从 98MB 降到 21.4MB
2. **MiSans 改为运行时下载**：默认使用系统字体，设置中的开关默认关闭

结果：debug APK 从 133MB 降至 **40.6MB**（降幅约 70%）。

### 10.3 MiSans 的许可约束

`adivenxnataly/MiSans` 中的 `MiSans.ttf` 为 Medium（500）、`MiSans-Static.ttf` 为 Regular（400），
与本地两个字重一一对应。Compose 提供 `Font(File, …)` 可在运行时构造 FontFamily。

但 MiSans 许可**明确禁止再分发字体本体**，因此仓库不提交字体文件
（`.gitignore` 排除 `res/font/*.ttf`），应用也不随包分发，
仅在用户主动点击时从其 GitHub 原址下载，并在设置页与关于页标注出处。

下载策略：两个字重先下载到 `.tmp`，**全部成功后再原子改名**，
避免半成品被判定为「已安装」；任一失败则清空全部并回到未安装状态。

### 10.4 顺带清理的死代码

发现一批「已定义但未接线」的代码：`OutboxEntity` 与 4 个 outbox DAO 方法、
`ChatWatchService` 前台服务壳（从未被调用）、`archiveChat`、`channel_watch_*` 字符串。

清理后 release APK 从 1.6M 降到 1.5M，56 个单测通过。

这次清理在文档中留下了一处隐患：旧文档仍写着「`ChatWatchService` 只是前台服务壳」，
而该类在本轮已被删除。第 15 节重构文档时才发现并修正。

## 12、折叠与分页（2026-10-26）

### 12.1 对齐官方 Console 的折叠语义

阅读官方前端 bundle 后找到关键枚举：
**Expanded / Collapse process / Collapse results**，默认为 **Collapse results**。
此外 `autoCollapseThinking` 会在流式输出结束后折叠思考内容。

据此实现三档（`AssistantCollapse`）：

| 档位 | 行为 |
| --- | --- |
| `EXPANDED` | 全部展开 |
| `PROCESS_COLLAPSED` | 每条正文单独显示，思考与工具调用合并为一组（对应官方 text-only） |
| `RESULT_COLLAPSED` | 一个回合只保留最后一条正文，其余全部并入一组（对应官方 result-only） |

用户猜测可以一次只加载 8 条，向上滚动时按需加载。

## 13、卡顿根因：debug 与 release 的差异（2026-10-27）

用户反馈卡顿问题依然存在。

这一轮的价值在于**此前所有假设都被推翻**。

### 13.1 测量方法本身的三个陷阱

**陷阱一：模拟器的掉帧百分比不可信。** 在 `-gpu host` 模式（宿主 GPU 为 GTX 950）下，
RenderThread 单帧 `Drawing` 可达 45ms、`dequeueBuffer` 出现阻塞，
jank% 完全被 GPU 主导，无法反映客户端差异。
软件渲染（swiftshader）下更为极端，GPU 项出现 4950ms 量级。

**陷阱二：atrace 必须指定包名。** 使用 `atrace --async_start -c gfx,input,view`
不包含应用进程，采不到 `AndroidOwner:measureAndLayout`、`Compose:recompose`
这类应用级 section。必须使用 `-a io.qwenpaw.node`。

**陷阱三：atrace 文本解析中的 pid 语义。**
`tracing_mark_write: B|<pid>|` 中的 `<pid>` 是**进程 id**，不是线程 id。
嵌套栈配对必须使用行首 `comm-tid (pid)` 中的 **tid** 作为 key。
最初以 pid 作 key，算出 `total=0.0ms` 或出现大量错配，白费了一轮工作。

**正解**：采用与 GPU 无关的主线程帧指标，即
`dumpsys gfxinfo <pkg> framestats` 中 `HandleInputStart → PerformTraversalsStart` 的间隔。
Compose 的 doFrame 回调在 `performTraversals` 之前完成，
因此这一段代表「一帧内主线程实际消耗的时间」，与 GPU 无关。

### 13.2 决定性数据

同一份源码、同一会话（171 条消息）、同一手势：

| build | p50 | p99 | max |
| --- | --- | --- | --- |
| debug（3 轮） | 1.41 / 1.75 / 1.72 ms | 26.8 / 4.7 / 3.7 ms | **43.3 ms** |
| release（3 轮） | 0.77 / 0.65 / 0.68 ms | 2.7 / 2.0 / 11.4 ms | **11.9 ms** |

release 的主线程帧耗时约为 debug 的 **43%**（快约 2.3 倍），长帧从 43ms 降至 12ms。

debug 变体 `isMinifyEnabled = false`：没有 R8 内联与优化、没有 AOT、
没有 baseline profile，Compose 内部还会走 debug 断言路径。

debug 构建下的 atrace 分片也印证了这一点：`AndroidOwner:measureAndLayout` 累计 440–500ms
（单次最大 145.6ms）、`Compose:recompose` 208–244ms、`TextLayout:initLayout` 出现上百次。

### 13.3 四个被排除的假设

| 假设 | 实测结论 |
| --- | --- |
| 历史一次铺开太多条 | LazyColumn 只组合可见项；窗口化 8 条与铺开 500 条在滚动时的可见项数量一致，无差异 |
| `SelectionContainer` 嵌套 | 仅约 8%，属噪声级 |
| Markdown 解析与正则新建 | 微基准 0.113ms/条、正则 1μs/次，量级不足 |
| `atBottom` 在父作用域被 `by` 读取 | 确实会导致滑动起止重组整屏，但 A/B 只带来重组时间从 221ms 降到 208ms（约 10%），`measureAndLayout` 无变化 |

这四个方向此后不再投入。记录于 [ui-guidelines.md](ui-guidelines.md) 5.2 节。

### 13.4 保留下来的实际收益

虽然不是根因，但值得保留：

- `MarkdownText`：行内样式按块缓存、表格单元格按内容缓存；
  解析期 `Regex` **提升为文件级常量**（原先写在循环内，每行、每个单元格都重新编译 `Pattern`）
- `ChatScreen`：`atBottom` 改为 `remember { derivedStateOf { … } }` 且**不使用 `by`**，
  读取点仅存在于协程内部与 `JumpToLatestButton` 组件内部

### 13.5 一个被忽略的交付环节

`scripts/e2e_acceptance.sh` 安装的是 **debug** 包（`APK=.../apk/debug/app-debug.apk`）。

因此「脚本通过」与「用户手上流畅」是两件事。这正是用户反复反馈卡顿的直接原因：
验收一直通过，但验收使用的构建本身就是慢的那一种。

用户安装 release 包后确认卡顿消失。

## 14、边到边适配（2026-10-27）

当时真机 LM-G820N 已关机，因此改用模拟器。
用户反馈：除设置页外的页面都出现顶部挤占通知栏、底部挤占小白条的问题，
设备为红米 K80。

### 14.1 根因：一条容易被忽略的 Scaffold 约定

`targetSdk = 35`，Android 15 起系统**强制**边到边（系统栏透明浮在内容之上）。

但直接原因是 M3 `Scaffold` 的语义：
`ScaffoldDefaults.contentWindowInsets` 取值为 **systemBars**，
而 Scaffold **只在顶栏或底栏槽位为空时**，才把对应方向的系统栏留白算进内容区。

因此：

- 设置页使用**不带** `topBar` / `bottomBar` 的 `Scaffold`，自动避让，显示正常
- 其他页面把自定义栏传入 `topBar` / `bottomBar`，Scaffold 认为由页面自行处理，于是被压住

用户提供的「设置页除外」这一条线索直接指向了答案。

### 14.2 修复原则

**底色仍铺满系统栏区域（保持真边到边），只把内容让开。**

- 顺序：先 `.background(...)`，再 `.statusBarsPadding()`
- 顶栏补 `statusBarsPadding()`：`ChatTopBar`、`ListHeader`、`ArchivedScreen`、`TokenUsageScreen`
- 底栏补 `navigationBarsPadding()`：新建按钮、批量操作条
- 输入条：留白加在 **`Surface` 内部**（否则外部会露出一条页面底色），
  且使用 `navigationBars ∪ ime` **取并集**而非相加——键盘高度本身已包含手势条
- `ConnectScreen` 是裸页面，自行补齐。**不能加进 `InstanceForm` 内部**，
  因为设置页也复用该表单，那边已由 Scaffold 注入留白，加在内部会造成双重留白
- 对话框走 Compose `Dialog`（默认 `decorFitsSystemWindows = true`），无需处理

### 14.3 验收

环境为模拟器 1080×2400、420dpi，状态栏 128px、手势条 63px。
通过 `uiautomator dump` 获取节点坐标，并解码 PNG 做像素采样
（环境中没有 PIL，PNG 解码为手写实现）：

| 位置 | 修复后 |
| --- | --- |
| 聊天页标题 | y ≈ 154（状态栏 128 之下） |
| 输入条按钮 | 底边 2293（手势条上沿 2337 之上） |
| 列表页顶栏 | y ≈ 158 |
| 设置页（原本正常） | y ≈ 154，**无双重留白** |
| 键盘弹出 | 输入条上移至 1424–1469，无多余空隙 |

状态栏区域的像素采样结果为应用自身底色 `#F9F8F4`，确认保持了真边到边。

## 18、九项体验修复（2026-10-28）

用户提出九个问题，其中三项是功能缺失，五项是体验与配色偏差，一项是文案错误。
本轮同时确定了测试设备的变更：**停用真机，只用模拟器**。

### 18.1 语音按钮的 bug 有两个成因

表面现象是「开关关了麦克风还在」，实际是两处独立的错误叠加：

1. `ChatInputBar` 无条件渲染麦克风，只靠 `enabled` 置灰。开关关闭时按钮仍在，只是变灰。
2. `MainActivity` 传的值是 `voiceEnabled && modelState is Ready`。模型未下载时
   条件恒为 false，按钮**也不显示**——用户因此无从发现这个功能缺什么。

第二个成因是第一个的`解药`被误当成`补丁`：为了让「模型没下载时不显示」成立，
可见性被绑到了模型的就绪状态上。正确做法是把「可见」与「可用」拆成两个参数：
`voiceVisible` 只由开关决定，`voiceReady` 只影响视觉与点击后的提示。

修复后实测确认：关闭开关，`uiautomator dump` 里找不到任何麦克风描述，
附件按钮与发送按钮紧邻排列，没有留白。

### 18.2 灰色小字过淡的根因是用了描边色

`colorScheme.outline` 在 Material3 里的用途是**描边**，浅色 `#D8D4CF`、
深色 `0x2EFFFFFF`（18% 白）。把它当正文小字用，深色下对比度只有 **1.78:1**，
远低于 4.5:1 的可读下限。

新增语义色 `LocalCaptionColor`：浅色 54% 黑、深色 60% 白，
再把 21 处「文字用途」的 `outline` 换掉。替换时按行号逐条人工甄别，
`border`、`HorizontalDivider`、状态圆点等描边与图形用途全部保留原色。

实测深色设置页「字体版权归小米…」一行，文字亮度 165、背景 31，
对比度 **6.69:1**。

### 18.3 深色黑字是 LocalContentColor 的默认值

`Text` 不给 `color` 时读 `LocalContentColor.current`，其默认值是 `Color.Black`。
正常情况下 `Surface` 会提供正确的内容色，但连接页是裸 `Column`、
`AlertDialog` 内的部分层级也没有 `Surface`，于是深色模式下退到黑色。

修法是给这三处显式指定 `onSurface`。实测深色模式下「智能体 default」
采样为纯 `(255,255,255)`。

### 18.4 多地址回退：只对连接失败换地址

数据结构从 `baseUrl: String` 改为 `baseUrls: List<String>`。
旧字段以 `@EncodeDefault(NEVER)` + `@SerialName("baseUrl")` 保留，
读出后由 `migrated()` 迁进列表，写盘时不再输出。

第一版迁移测试失败，原因是存储用了 `encodeDefaults = true`，
不加 `@EncodeDefault(NEVER)` 会把 `"baseUrl": null` 一起写进 JSON。
这条约束写在 [InstanceStore.kt](../app/src/main/java/io/qwenpaw/node/data/local/InstanceStore.kt) 的注释里。

回退逻辑抽成纯函数 `AddressFallback`，因为 `InstanceRepository` 依赖 Android 的
`InstanceStore`，不便在 JVM 单测里构造。两条规则：

- **只对连接类失败换地址。** HTTP 4xx/5xx 说明地址是通的，换下一个既解决不了问题，
  还会把真实原因（例如 401 需要登录）掩盖掉。
- **命中后不改写顺序。** 用户把局域网地址排在第一是有意的，隧道地址通常更慢。

OkHttp 对连接被丢弃的地址抛的是普通 `IOException`，类型上看不出来，
只能靠文案里的 `Failed to connect` 识别。漏掉这条，真实环境里回退根本不生效。

实测：主地址填 `10.99.99.99:8088`（不可达）、备用填 `10.0.2.2:8088`，
验证结果为「连接正常，服务端 2.2.2.post1，已回退到 http://10.0.2.2:8088」。

回退提示最初误报了一次：`effectiveHosts` 是用户原文（`10.0.2.2:8088`），
`result.baseUrl` 已补齐协议（`http://10.0.2.2:8088`），直接比字符串会把
「未回退」判成「已回退」。改为比较前先 `normalizeBaseUrl`。

### 18.5 模型切换：服务端不接受 null

计划里写的是「传 null 恢复智能体默认」，来自 `docs/protocol.md` 此前的记述。
实测否定：四种写法全部失败。

| 请求体 | 结果 |
| --- | --- |
| `{"provider_id": null}` | 400，`Input should be a valid string` |
| `{"provider_id": ""}` | 400，`Model provider is unavailable` |
| `{"provider_id": "", "model": ""}` | 同上 |
| `{}` | 同上 |

`DELETE /api/chats/{id}/model` 返回 `Method Not Allowed`，不存在清除端点。

正确做法是先读 `GET /api/models/active` 拿到全局默认，再显式 `PUT` 回去。
这个端点是从 Web 前端产物里找到的：`grep` 打包后的 JS 才看到 `/models/active`，
服务端不提供 `openapi.json`（返回 404）。

另一个被否定的假设是模型列表的来源。计划原先打算用
`GET /api/models/{provider_id}/pool`，实测本机部署下返回空数组；
实际可选模型在 `GET /api/models` 每个供应商的 `models` / `extra_models` /
`discovered_models` 三个数组里，共 36 个供应商、合并后上百个模型。

模型菜单因此要限高（320dp）并允许滚动，否则会顶出屏幕。

### 18.6 导出的「无论如何都失败」

用户报的是导出必定失败。排查发现两个独立问题：

1. `pendingExportText` 用的是普通 `remember`。选文件时系统会把 Activity 推后台，
   低内存下可能被杀掉重建，文本变成 null，回调里静默早退——
   表现出来的就是「点了导出什么都没发生」。
2. 失败路径没有任何原因输出，`writeTextToUri` 只返回 `Boolean`。

修法：文本与文件名改放 `rememberSaveable`；`writeTextToUri` 改为返回
可读原因（`String?`），toast 里带上具体信息。`uri == null`（用户取消）
与 `text == null`（内容丢失）也分别给出不同提示，不再静默返回。

实测导出成功，`/sdcard/Download/新会话.md` 3934 字节，内容为完整 Markdown。

### 18.7 其余三项

- **归档提示**：单条与批量两处都加「今日不再提示」，按 `yyyy-MM-dd` 存日期而非布尔值，
  跨天自动恢复，不需要额外的零点重置任务。规则抽成 `ArchiveTip` 纯函数以便单测。
- **地址验证**：步骤 1 的勾从「地址非空」改为「验证成功」。地址非空不算完成，
  否则用户会以为这一步已经过了。新增「验证连接」按钮，只查版本与鉴权状态，
  比拉智能体列表轻。
- **文案**：把「离线识别模型」「下载后不联网也能语音输入」改为
  「语音识别模型（使用前必须下载）」与「语音输入依赖此模型，未下载时无法使用」。
  原表述容易读成「下载后还能离线用」，实际是不下载就完全不能用。

### 19.1 分类依据：按「能否在 JVM 上判定」切分，而不是按功能模块

一开始想把用例按功能模块排（会话、聊天、附件、语音、设置）。排下来发现同一个模块里的

按模块排会让执行者反复在同一节里切换验证手段。

最终改成按验证层切分，每条带一个层标记：U（JVM 单测）、P（MockWebServer 桩）、
E（设备脚本）、M（手工）、N（非功能）。这样读的人可以直接筛出「本轮只能跑 U 的部分」。

「现状」列是有意加的：`已有` 与 `待补` 的区分让人一眼看出 119 个单测到底覆盖了什么，
而不是笼统地说「有测试」。

### 19.3 覆盖缺口的实际分布

盘点下来最大的一块不在解析层，而在 `ChatViewModel`：**零覆盖**。
它承担发送拦截、停止收尾、重连合并、审批轮询、草稿防抖、
后台通知判定这六件事，每一件的失败都会直接被用户看到。

解析层反而覆盖得不错：`ChatEventParser` 16 条、`StreamAccumulator` 11 条、
`HistoryMapper` 9 条、`SseReader` 9 条，真实抓包做输入，邪门形态基本都有用例。

chats、approval、token-usage、upload 全无桩测试。这是第二块缺口。

### 19.4 七条待验证疑点：读代码读出来的，不是猜的

写用例过程中顺带核对了状态更新与副作用的位置，发现七处逻辑不一致。
**没有一条在设备上复现过**，因此全部标成「待验证」而不是「缺陷」，
每条都附了验证方法。列出四条最有代表性的：

1. `finishRun` 收到新列表后直接赋值，绕过了 `orderChats`。GET `/api/chats`
   的排序无保证（[protocol.md](protocol.md) 第 2 节已写明），所以「回复结束后置顶项掉位」
   是可预期的结果。但只有实际观察才能确认，因为服务端可能恰好按时间返回。
2. `archiveChat` 在 `chats` 过滤之后才去取会话名，取不到，提示文案固定回退成「会话」。
   这是纯逻辑错误，单测可直接判定，不需要设备。
3. `MainActivity` 里图片加载与导出用的 `Connection` 取 `primaryBaseUrl`，
   而仓库与 ViewModel 都用 `resolvedBaseUrl`。多地址回退生效时，这两条路径指向不同地址。
   影响范围比前两条大：图片可能加载不出来，导出也可能写到错误实例。

4. 离线缓存表的主键只有 `id`，查询却按 `chatId` 过滤；而 `StreamAccumulator` 的
   `local-user-N` 每次从 1 起算，`HistoryMapper.uniqueIds` 的 `#N` 后缀同样按会话重新计数。
   跨会话撞号时 `REPLACE` 覆盖，断网可能读到别的会话的消息。

第 4 条在写进文档前做了一次实测纠偏。原本怀疑的是「缓存命中率差 100 倍」，
先打了一次真实接口，返回 `cache_hit_rate=94.1325…`，证实服务端给的是百分数，
`%.1f%%` 的格式化是对的。**这条假设当场否掉**，换成上面这条缓存主键问题。
这是本轮唯一一次靠实测救回来的判断：若不先验证，就会把一个不存在的缺陷写进清单。

### 19.5 与既有约定的关系

  单测最轻先跑，构建与模拟器不并行，每步之间查 `free -h`。
- 「发版前回归最小集」只列六项，理由是这些项对应的失败模式都真实发生过：
  断线丢内容、停止后内容消失、按钮卡在「停止」、Android 15 遮挡、R8 暴露问题。
- 用例里引用的协议行为一律标注了 [protocol.md](protocol.md) 的节号，
  避免以后协议变了而用例还在按旧假设跑。

### 20.4 确认了五个缺陷，否掉一个假设

**D-1（最严重）：重连后状态不回收。**
发 35 秒任务，生成中 `am force-stop`，重开 App，界面正确接回「处理中」。
但任务在服务端 10 秒后结束（`running` 归 0），界面等了 15 秒仍是「处理中 / 运行中 / …」。
服务端内容完好，纯客户端问题：`attachRunningStream` 把历史拉回来之后没有更新 `running`，
也没有把气泡的流式标记清掉。

这一条比原先列的七条疑点都严重。用户看到的是「永远转圈」，只能退出重进。

**D-2：所有提示都发不出去。**
`ChatViewModel.notifications` 是 `MutableSharedFlow`，`grep` 整个 `app/src/main` 只有
`tryEmit` 的六处调用，**没有任何 collector**。归档、删除、批量归档、批量跳过、
审批新增这五类提示全部静默。

这是本轮最有价值的发现，因为它是「操作生效但用户毫无反馈」——
功能测试全过、服务端计数全对，只有真人操作才会觉得「点了没反应」。

**D-5：图片被当文件上传。**
传一张 64×64 纯色 PNG，模型能读出 RGB(74,107,181)，说明内容确实到了服务端。
但查 `GET /api/chats/{id}`，该消息的 `content[1].type` 是 `file` 而不是 `image`。
根因在 `MainActivity.uploadAttachment`：文件名取 `uri.lastPathSegment`，
系统相册给出的是 `..._1000000158` 这类无扩展数字串，`isImageName()` 判否。

模型这次靠 `execute_shell_command` 读像素数据蒙对了结果，但走的是工具链而非视觉通道。
换成不支持工具的模型就会答「看不到图片」。

**D-3 / D-4** 分别是 V-7 与 V-6 的实机确认，见表格，不重复。

**被否掉的假设：V-1「回复结束后置顶项掉位」。**
专门置顶一条旧会话，再在另一条里发消息，结束后置顶项仍居首。
原因是本机 `GET /api/chats` 恰好按 `updated_at` 倒序返回，把 `orderChats` 的缺失掩盖了。
**这不等于代码没问题**——服务端排序无保证，[protocol.md](protocol.md) 已经写明。
结论改为「未复现，仍是隐患」，没有直接划掉。

## 21、修复七个缺陷并复验（2026-10-29）

### 21.1 修复策略：能抽成纯函数的一律抽出来

七条缺陷里有四条的核心判据可以脱离 Android 框架，这一轮把它们抽成独立文件，
单测直接覆盖，而不靠模拟器验证：

| 抽取出的文件 | 对应缺陷 | 为什么值得抽 |
| --- | --- | --- |
| `data/remote/ErrorText.kt` | D-7 | 异常到中文的映射原本在 ConnectScreen 与 ChatViewModel 各写一份，行为不一致；抽出来才能用 `IllegalStateException` / `IOException` 直接测 |
| `ui/chat/AttachmentPlaceholder.kt` | D-3 | 占位文案的判据是纯字符串逻辑，抽出来后不必启动 Compose 就能验证「空文本 + 纯图片附件」应返回空列表 |
| `data/remote/UploadNames.kt` | D-5 | 文件名归一化的入参是三个可空字符串，最容易写错也最容易测 |
| `MainActivity.uploadAttachment` 内的 `uploadFileName` | D-5 | 只剩取 `DISPLAY_NAME` 这一小段与 `ContentResolver` 打交道，其余全在纯函数里 |

反过来，D-1 / D-2 / D-4 依赖协程与 Compose 生命周期，抽不出来，只能实机验。
这是本轮取舍的判据：**能脱框架就脱框架，脱不掉的才留给模拟器**。

### 21.2 D-5 的根因比原先写的更靠前

上一轮把 D-5 记在 `MainActivity` 的取名逻辑上。这一轮改了取名方式之后发现，
问题不止「取不到扩展名」：`uri.lastPathSegment` 拿到的是 `..._1000000058` 这种数字串，
连原始文件名都没有。`OpenableColumns.DISPLAY_NAME` 才能拿到 `qa_blue.png`。

即便如此仍然不够：服务端上传接口返回的文件名也可能不带扩展名。
因此 `UploadNames.resolve()` 在拿到名字后还要再判一次扩展名，缺了就按 MIME 补。
复验时 chip 显示 `..._1000000067.png`，服务端该消息 `content[0].type` 为 `image`，
`image_url` 是 `data:image/png;base64,...`，才算真正修好。

顺带记一条实测结论：换成 `image` 块之后，`deepseek-v4.1-flash-1017` 直接回
「The request model is not multimodal」。上一轮之所以能读出 RGB 值，
是因为它用 `execute_shell_command` 去读像素，走的是工具链而非视觉通道。
**「模型能说出颜色」不能作为图片通道正常的证据。**

### 21.3 脚本修好之后反而暴露了更多问题

D-6 表面上只是「节点名对不上」，实际改下来是四个独立问题串在一起：

1. `pick_first_agent()` 取「y>400 的第一个整行宽可点区」，而地址输入框本身就是整行宽可点区。
   点进去之后地址被改坏，流程退回第 1 步，表现成「脚本卡住」。
2. 地址框首次启动带真实默认值（不是 placeholder），`input text` 会追加。
3. Android 13+ 的通知权限对话框是系统窗口，覆盖在应用之上，之后所有点击都落空。
4. `adb shell input text` 遇到引号会截断，`bash -c 'nc -e /bin/sh ...'` 只输入到 `bash` 就停。

第 4 条最有欺骗性：脚本看起来正常跑完，审批卡片却不出现，
很容易误判成「服务端不再拦截这类命令」。实际是命令根本没发全。

结论写进 [test-plan.md](test-plan.md) 22.3，同时说明一件事：
**验收脚本失败时，先怀疑脚本的输入路径，再怀疑产品。**

## 22、九项功能与体验优化（2026-10-29）

本轮范围是九条来自实际使用的反馈，涉及日志、连接状态、地址管理、消息呈现与列表分组。
分七期推进，逐期编译验证，全部编码完成后先写单测再上模拟器。

### 22.1 「已就绪」与连通性无关

用户的第一条反馈是「顶部已就绪永远存在，连不上 QwenPaw 也显示」。
查证 `ChatTopBar.kt` 的写法是 `if (running) "正在生成" else "已就绪"`，
而 `running` 的六处赋值全部来自流式事件或历史 `status`——**它描述的是服务端有没有在生成，
不是这台手机能不能连上服务端**。断网时既没有事件也没有 `status`，于是永远停在「已就绪」。

改法是引入由轮询结果推导的 `LinkState`（UNKNOWN / ONLINE / OFFLINE），顶栏三态：
正在生成（琥珀）、连接中断·点击重连（error 色，整行可点）、已连接。
`UNKNOWN` 显示为「已连接」，避免冷启动瞬间闪红。

### 22.2 断网恢复必须自动，不能只加刷新按钮

用户的原话是「1 分钟前没有网络，1 分钟后恢复，现在必须重启应用才能恢复」。
查证发现 `ACCESS_NETWORK_STATE` 在清单里声明过，但全仓零使用：
没有 `ConnectivityManager`、没有 `onResume` 刷新、列表也没有下拉刷新。

因此加了 `NetworkMonitor`，并在 `AppViewModel` 里订阅它的 `online`。
两个细节是踩过的坑：

1. **必须同时覆写 `onLost`。** VPN 断开时系统只回调 `onLost`，不再给一次能力变化；
   只听 `onCapabilitiesChanged` 的话，VPN 拔掉后客户端仍以为在 VPN 上。
2. **订阅要 `drop(1)`。** `StateFlow` 订阅瞬间会先发一次当前值，不丢会立刻重复拉一轮会话列表。

另外只对 `false → true` 的跳变动作，关闭网络时不重载——否则地铁里穿隧道会反复打请求。

### 22.3 「验证连接」慢，以及备用地址为什么形同不存在

两个问题同源，都是超时配置与缓存策略的问题。

**慢的根因**：`defaultClient` 的读超时是 10 分钟且没有 `callTimeout`，
「连上但对端不回包」（隧道或 VPN 半开连接）要等满 10 分钟。
新增 `probeClient()`：connect 4s / read 5s / `callTimeout 8s` / 不重试，
且验证只发一个 `GET /api/version`（原来每个地址发两个请求且串行）。
另外把「正在尝试 1/2 · url」显示出来，用户能分清卡住还是在回退。

**备用地址失效的根因**：`runtimeHit` 是一个**单桶永久缓存**。在家连上局域网后缓存记下
`192.168.x.x`，出门 VPN 上线时缓存仍指向那个地址，于是每条请求都先等一遍连接超时才回退。
改为按 `id@网络类型` 分桶，网络一变桶就换；同时加 `resolveOrder()` 四级优先：
网络命中 `preferOn` > 用户手动指定 `preferredBaseUrl` > 运行期命中 > 原始顺序。
前三者都只「提到最前」不排他——排他会让一次手动选择在地址故障时彻底不可用。

**实测又发现一个更隐蔽的**：冷启动（或重装）时运行期缓存为空，
`resolvedBaseUrl` 返回的只是「排序后第一个」，**并不保证可达**。
重装后第一次启动，第一个地址是失效的 `10.0.2.9`，聊天页直接报连接失败，
备用地址完全没有机会。补了 `probeReachable()`：启动后台探一次，
命中地址与当前绑定不同就重绑并重载。复验后冷启动自动切到备用地址，无需用户操作。

### 22.4 服务端 usage 的真实形状与两个假设的推翻

计划阶段用 `curl` 看过一条消息，得出「整轮用量挂在该轮最后一条 assistant 消息上」。
实机上比对整段历史后发现**假设错了**：服务端把同一个 `qwenpaw_turn_usage` 挂在
**该轮每一条** assistant 消息上（reasoning、plugin_call、plugin_call_output 全都有）。
原样渲染会让一个 37 步的回合里每段正文下面都重复一遍相同的 token 数字。

改法是 `HistoryMapper.markTurnEnd()`：按「连续的非用户消息」切成回合，
只让该轮最后一条**带统计的正文**保留 `stats` 并标 `turnEnd`，其余清空。

第二个被推翻的假设是 `cache_hit_rate` 的量纲。原以为是小数值，实测返回
`74.99633806943021`——**百分数**。解析时统一除以 100，
避免界面与日志两处各折一次、结果不一致。

顺带确认了一件事：服务端**没有**首字耗时字段（源码里搜不到 `first_token`/`ttft`/`latency`），
用户也确认不做，因此界面上只显示输入、输出、模型。

### 22.5 头像：不引入 Coil 的取舍

用户要求头像支持裁剪与 GIF。项目此前**零图片库**（自建 `ChatImageLoader`，
`OkHttp` + `BitmapFactory`，内存 LRU 24 张，无磁盘缓存），也**零裁剪/缩放/EXIF 代码**。

两个决定：

1. **GIF 存原样、只显示首帧，不引入 Coil。** 只在 32dp 的圆形头像里播动图，观感收益很低，
   却要引入第二套图片加载体系并给 R8 加 keep 规则。存原文件而不是转成 PNG 的理由是：
   将来换成支持动图的版本时不必让用户重新选图。设置页明写「GIF 动图原样保存并在头像中显示首帧」。
2. **新增 `androidx.exifinterface`。** 不处理 EXIF 的话竖拍照片存出来的头像会躺倒。

裁剪的几何换算抽成纯函数 `CropGeometry`（基础缩放 / 生效缩放 / 位移夹取 / 裁剪区域），
因为手势拖动与缩放最容易出「拖到底还能拖」「裁剪区偏出图片」这类问题，
而在 Composable 里没法断言。绘制用 `Canvas` 自己算 dst 偏移，
而不是给 `Image` 加 `graphicsLayer`：缩放与位移必须和几何计算用同一套公式，否则裁剪结果会偏。

### 22.6 分组三态与时间口径

QwenPaw 网页版的分组三态（按时间 / 按来源 / 不分组，单击循环）来自打包产物
`assets/zh-*.js` 里的 `groupByTime`/`groupBySource`/`groupByNone`，不是推测。

顺带修掉一个既有偏差：`ChatListScreen.timeLabel()` 原来直接截 UTC 字符串前 10 位当日期，
等于按**UTC 日界**划分「今天/昨天」。东八区早上 7 点发的消息会被算成前一天。
新增 `ui/TimeLabels` 统一解析到本地时区，会话列表与消息气泡共用。

分组实现上有两条规则：置顶项无论哪种模式都单独成区排最前（否则置顶等于没有），
空桶不输出（只有表头的分区是噪声）。搜索时强制不分组——分组会把命中的会话拆到多个表头下。

## 23、十一项体验问题修复（2026-10-29）

用户在一次实际使用后列了十一条问题，从「按钮显示条件写反」到「缺一整条引导流程」都有。
十一条全部落地：三处是状态判定写错，两处是手势冲突，其余是交互重构与新增流程。

### 23.1 三个根因，都在状态判定上

三条问题（跳到最新、发消息另建会话、顶栏谎报已连接）表面无关，根因都在「某个布尔/字符串
被当成了它并不表示的东西」。

1. **「跳到最新」显示条件写反。** `ChatScreen` 里 `visible = { atBottom.value }`。
   停在底部时常驻、上翻历史时消失，与语义完全相反。改为 `!atBottom.value`。
   顺带把 24 裸像素换成 `8.dp.toPx()`：xxhdpi 上 24 像素只有 8dp，
   手指一碰就误判离开底部，按钮会闪。
2. **发消息会另建会话。** `ChatViewModel.bind()` 无条件清空 `currentChatId`，
   而 `AppViewModel.refreshAll()` 也调 `bind()`，被「顶栏重连 / 网络恢复 / 改地址」三处共用。
   同实例重连一次就把会话置空，`send()` 随即走新建分支。
   改为仅当实例 id 真的变了才清空（抽成纯函数 `shouldClearOnBind`）。
3. **断网仍显示「已连接」。** `ChatTopBar` 的三分支漏了 `LinkState.UNKNOWN`，
   它落进 `else -> "已连接"`；同时 `AppViewModel` 的网络订阅在 `online == false` 时
   `return@collect` 空转，断网信号根本传不到聊天页。
   补第四分支，并让 `setNetworkState(false)` 直接置 OFFLINE、恢复时置 UNKNOWN
   交给随后的请求证明。`startRun` 失败与 `attachRunningStream` 异常两处各补一次
   `updateLink(OFFLINE)`（后者排除 `CancellationException`，否则点「停止」也会显示断线）。

**教训**：同一个状态字段被多处读取时，任何一处把它当成别的含义都会表现出来，
且症状与真正的位置相距很远。`bind()` 那次尤其典型——它的调用点是「重连」，
但后果出现在「发消息」。

### 23.2 实例名与地址别名是两件事

原表单没有实例名输入框，`connect()` 用 `addresses.first().alias ?: url` 当 `name`。
结果实例卡片的标题与副标题显示同一个字符串，读起来像「给实例起别名」，
而那个字段描述的其实是某一条连接地址。

新增 `InstanceDraft`（`addresses` / `instanceName` / `username` / `password` / `agentId`），
`resolvedName()` 在名称空白时回落到第一个地址——名称是自由文本，用户很可能只敲空格，
否则卡片第一行会是一片空白。表单在地址列表上方加「服务器名称」，与别名分开标注。

### 23.3 地址切换的两层语义

用户的原话是「仅在本次打开生效」，但编辑实例里已有持久偏好，两者不能互相顶掉。
分成两层：

- `InstanceConfig.preferredBaseUrl`：写配置，长期有效，编辑实例里改。
- `InstanceRepository.sessionPick`：内存 map，进程结束即失效，设置页点「本次使用」写入。

`resolveOrder()` 的五级优先级（sessionPick > 网络偏好 > preferredBaseUrl > 运行期命中 >
原始顺序）抽成纯函数 `resolveOrderPure()` 以便单测。前四级都只是**提到最前**，
不去重也不排他：指定地址坏了仍然能回退，否则一次手动选择会让实例在地址故障时彻底不可用。

踩坑：`sessionAddressOf` 初版直接读 `repository` 里的普通 `mutableMap`，
Compose 观察不到，用户点了「本次使用」界面纹丝不动。改为 `AppState.sessionPicks`
与仓库同步写，界面读 state。

### 23.4 分组的折叠与新建

服务端早已支持 `POST/PUT/DELETE /api/chats/groups`，客户端此前只做展示。

折叠只清 `chats`、保留表头，折叠状态存 `qwenpaw_ui` 的 `collapsed_groups`——
它是用户偏好，既不属于某台服务器，也不该跟着实例走。

空的自建分组必须显示。用户刚建完必然还没有会话，藏起来像建失败。
初版 `bySource` 写 `buckets[group.id] ?: return@forEach`，恰好把所有空组过滤掉；
改为 `.orEmpty()`，再只过滤掉空的内置分组。

### 23.5 长按从「直接复制」改为菜单

原实现 `combinedClickable(onLongClick = 复制)` 压在 `SelectionContainer` 外层，
两套长按手势互抢，结果既选不中文本又会被整段复制。

改为长按弹 `DropdownMenu`（复制 / 复制为 Markdown / 选择文本），并且
`SelectionContainer` **只在选择态下包裹正文**、选择态下不挂 `combinedClickable`。
底部操作行在选择态换成「完成选择」，那是退出该态的唯一入口。

「复制」走新增的 `MarkdownPlainText.strip()`，「复制为 Markdown」走原文——
此前两个按钮行为完全相同，等于同一个功能给了两个名字。
`strip()` 保留围栏内内容原样，因为代码里的 `*` 与 `_` 是语法本身。

踩坑：`strip()` 初版把分隔线与表格分隔行整行删掉后，上下原本的空行留下来变成三连空行。
改成删标记行时顺手收掉相邻空行（`skipBlank` + 回退删除尾部空行）。

### 23.6 选区配色不能用主色

`LocalTextSelectionColors` 此前取 `colorScheme.primary`，而用户气泡底色就是品牌橙
（实测 `rgb(255,127,22)`），同色系高亮叠上去完全不可见。
改为浅色 `#1F6FEB`、深色 `#7AA7FF`，底色取把手色 32% 透明度。

**这条约束已写进 [ui-guidelines.md](ui-guidelines.md) 8.4**：选区色不得与它能覆盖的
任何气泡底色同系。

### 23.7 气泡头部改两行

原头部是单行 `Row`（昵称 + `HH:mm`），昵称一长就只剩时间，时间也缺秒。
改为两行 `Column`：昵称在上、`yyyy.MM.dd HH:mm:ss` 在下，用户侧右对齐、
智能体侧左对齐，与头像位置一致。

`TimeLabels.fullStamp()` 新增。这里踩了一个只有真机才暴露的坑：
服务端 `metadata.timestamp` 形如 `2026-10-26T00:15:42.910613+08:00`，
**带偏移量**，而 `Instant.parse` 在 Android 的 `java.time` 上不接受偏移，
返回 null → `showHeader = stamp != null` 为假 → 整块头部不渲染。
修复是在 `parse()` 里加 `OffsetDateTime.parse(...).atZoneSameInstant(zone)` 回退分支，
并补 3 条回归单测。这个 bug 在单测里发现不了，因为测试用的都是 `Z` 结尾的样本。

用户昵称存 `qwenpaw_ui` 的 `user_name`，默认「我」。

昵称输入**逐键提交**而不是等失焦：实测在设置页按返回键只是收起键盘，
焦点仍留在输入框上，`onFocusChanged` 不触发；设置页在页面栈里也不销毁，
`DisposableEffect(onDispose)` 同样等不到。只挂失焦回调会让用户敲完直接返回时静默丢内容。

### 23.8 首次启动三步引导

新增 `InstanceWizard`：第 1 步地址 + 实例名 + 地址别名（验证通过才能下一步）→
第 2 步按 `authRequired` 决定是否需要账号（不需要则轻提示后自动跳第 3 步）→
第 3 步读智能体列表单选，手填 id 作备用。

引导页**不放多地址相关条目**：把「备用地址」「回退」这类概念摆在首次启动的路径上，
只会让人怀疑自己漏填了什么。需要多地址的人在设置里用填表方式补。

`scrollable` 参数是必须的：首次启动页外层已有滚动容器（还要接「已保存的实例」），
设置页的子页面只有这一层，两层 `verticalScroll` 会互相抢手势。

`InstanceRepository.loginRequired()` 把 `enabled && has_users` 统一到一处，
四处判定共用同一个式子。只开 `enabled` 却没有用户时，登录接口无从登录，
按「不需要登录」处理。

设置页的「添加实例」改为先选方式（填表 / 引导式），两种形态共用 `addConnecting` / `addError`。

### 23.9 二级菜单改居中对话框

顶栏三个 `DropdownMenu`（模型 / 审批 / 分组）改为 `OptionDialog`：
`Dialog` + 圆角卡片 + `LazyColumn` 限高 420dp，选中项右侧对勾，`leading` 放固定首项。

「移动到分组」补了首项「未分组」——此前下拉里没有这一项，会话进组后移不回去。

## 24、六项界面与文案修正（2026-10-30）

六项来自一轮连续使用：三处是文案与归属信息，两处是真实缺陷，一项是界面口吻清理。

### 24.1 顶栏末尾的归属名

用户要求「已通过「地址/别名」连接至 QwenPaw」里的 QwenPaw 跟随服务器名称变化，
未设置时仍写 QwenPaw。三选一确认后取了「只替换末尾的 QwenPaw」这一形态。

`connectedLabel()` 由两参改三参，`ChatState` 新增 `boundServerName`，
`ChatViewModel.bind()` 新增 `instanceName`，`AppViewModel.bind()` 传入实例名。

**第一版把「名称是不是地址」的判断放在 `connectedLabel` 里，是错的。**
它只能拿到当前绑定的那一条地址，而实例名是表单留空时由
`InstanceDraft.resolvedName()` 回落出来的**首条**地址。当实际绑定的是备用地址时，
两者不相等，判断失效，顶栏显示成「已通过「EasyTier」连接至「10.0.2.9:8088」」——
同一个网关地址在句子里出现两次，且指向的还是那条没在用的。

改在数据层：`InstanceConfig.serverDisplayName` 拿实例的全部地址比对，
忽略协议前缀与结尾斜杠（回落值存的是用户原文，`addresses` 里是规范化结果）。
命中任一条就返回空串，表示「没起名字」。

**教训**：判断需要「完整上下文」时，不能放在只拿到局部参数的纯函数里。
这一条与 第 23 节把判定抽成纯函数的做法并不矛盾——抽纯函数的前提是参数够用。

顺带修了排版：`已连接至` 后面接中文引号不留空格，接 `QwenPaw` 留一个空格。
单测先暴露了这点（`已连接至[]「家里的机器」` vs `已连接至[ ]「...」`）。

### 24.2 服务器名称改非必填

`InstanceWizard` 第 1 步此前要求名称非空（`nameOk`），而填表方式早就标了「可选」。
两处口径不一致，用户在引导页会被拦住。改成 `canNext = verified && !verifying`，
名称标签由「必填」改「可选」，说明补上回落规则。

落库仍走 `InstanceDraft.resolvedName()`，空白时回落地址，无需改动。

### 24.3 引导页第 2 步的死锁

根因在 `LaunchedEffect(step)` 的守卫写成了 `if (needsLogin != null) return`。
它把「是否已判定」与「是否要跳走」混成了一件。于是：

未开登录 → 首次进第 2 步判定 `needsLogin = false` 并跳到第 3 步 →
用户点「上一步」→ 回到第 2 步 → `LaunchedEffect` 因缓存命中提前返回，不再跳；
而该步的 `canNext` 要求 `needsLogin == true && 用户名 && 密码`，
输入框又因 `needsLogin == false` 根本不渲染。第 2 步成了不能前进也不能填的死页面。

两处一起改：

1. `LaunchedEffect` 缓存命中时也要执行跳转，只在**首次**判定时弹提示。
2. `wizardBackStep(step, needsLogin)` 在「无需登录 + 从第 3 步返回」时直接回第 1 步，
   避免「回到第 2 步被立刻弹走」的闪动。抽成纯函数以便单测。

这类缺陷的共同点是**两个条件的组合才是完整前提**，只检查其中一个会漏。
写 `if (x != null) return` 之前应当先问：这个守卫拦住的是不是全部该拦的情况。

### 24.4 消息底部的「选择文本」

消息操作行此前只有「复制」「复制为 Markdown」，进入选择态只能长按。
新增第三个按钮，复用同一个 `onToggleSelection`。

进入选择态时弹一条轻提示：「已进入选择态；「完成选择」在这条消息下方」。
理由是选择态的退出入口在与按下的地方同一条消息下方，但用户按的是「选择文本」这个字样，

### 24.5 头像裁剪器的绘制溢出

`drawImage` 的 `dstSize` 是「图片尺寸 × 有效缩放」。用户放大或图片长宽比极端时，
它会大于取景框；`CropGeometry.clampOffset` 只保证**铺满**，不保证**不溢出**。
Compose 的绘制默认不按布局边界裁剪，溢出的部分直接画到上方标题行之上，
把「取消 / 调整头像 / 保存」压住。

修法是给取景框 `Box` 加 `clipToBounds()`。实测 16:9 横图放大后，
取景框位于 y 732–1812，顶部工具行（y 140–255）采样全部是 `#101010` 纯背景，
没有任何图片像素越过边界。

**这条已写进 [ui-guidelines.md](ui-guidelines.md) 8.4**：凡是用 `drawImage`
自行计算 `dstOffset` / `dstSize` 的场景，必须给容器加 `clipToBounds()`。

## 25、发送反馈与 GIF 头像（2026-10-30）

四项来自同一轮使用：两处是同一个真实缺陷的两个观感面，一处是 GIF 只显首帧，
一处是继续清理重复的灰色说明行。

### 25.1 「发送后页面空荡荡」与「回复完毕才看到历史」是同一个 bug

用户先描述为两个问题：

1. 给智能体发消息后，聊天页没有任何反馈，要等上游开始输出 token 才出现工具调用或 think；
2. 回复完毕前看不到之前的消息，看着像新建了一个会话来发。

追问后确认第 1 点不是「完全没有用户气泡」，而是「气泡以后整屏仍然空着」。
按这个口径查代码，两问落在同一条语句上。

`ChatUiState.messages`（界面消息）与 `StreamAccumulator`（流式折叠器）是两份独立列表：

- `openChat()` 把服务端历史**直接写进** `_state.messages`，同时 `accumulator = StreamAccumulator()`
  被清空——历史**不进** accumulator；
- `startRun()` 随后写 `messages = accumulator.snapshot()`，用只含刚追加的用户气泡的快照
  **整体覆盖** state；
- `pushSnapshot()` 每收到一帧同样整体覆盖。

于是每发一条消息，此前所有消息都被整屏冲掉。首个 token / 工具调用 / think 帧到达前，
界面上只剩一条用户气泡；到帧之后才一点点长回来，观感就是「点了发送没反应」。
回复结束时 `reconcileWithServer()` 用服务端历史重新覆盖，于是「输出完毕才正常」。
两问因此是同一个根因。

**修法**：引入「历史前缀」。`private var historyPrefix: List<ChatMessage>` 只在三处更新
（`openChat` 成功、离线读缓存、`reconcileWithServer`），其余写入一律走
`mergedMessages() = mergeHistory(historyPrefix, accumulator.snapshot())`。
换实例、删会话、归档当前会话、批量删除/归档时同步清空前缀，避免旧服务器的残留被拼回来。

同一文件里 `attachRunningStream()`（重连路径）本来就是按 id 合并，写法是对的，
这次反过来把它当成范本。**教训**：同一份状态有两个写入路径时，只要其中一条是「整体覆盖」，
另一条迟早会把对方的数据吃掉。这类覆盖必须收敛到一个拼接函数里。

### 25.2 建会话往返期间界面完全不动

`send()` 在 `chatId` 为空时先 `createChat` 再 `startRun`，而用户气泡原先是在 `startRun`
内部追加的。没有当前会话时，这次网络往返期间 state 一次都没更新，界面静止。
把回显提到 `send()` 开头（`echoUser`），点下发送的同一帧就能看到自己的消息，
并立即置 `running = true`，让「停止」按钮与等待行同时出现。

建会话失败时用新增的 `StreamAccumulator.rollback(ids)` 撤回这几条回显，改由错误气泡承载
原文并挂「重试」。不撤的话用户点重试会把同一段文字再画一遍。
`rollback` 只删末尾的用户消息，不动 `indexByMsgId` / `toolIndexByCallId`——
后两者只登记智能体消息，删尾部不影响它们的下标。这一点写进了注释，否则下一个人
很容易「顺手」补一段重排逻辑。

### 25.3 等待态：判据不能是「有没有在流式」

首帧到达前的占位行由纯函数 `needsAwaitingPlaceholder(messages, running)` 决定。

第一版判据是「`running` 且没有任何 `streaming` 的智能体消息」。实机跑起来发现收尾时会闪：
`ResponseStatus=completed` 先把流式标记清掉，而 `running` 要到流处理结束才复位，
中间那段空档让等待行重新冒出来、紧跟着又消失。

改成「`running` 且最后一条还是用户自己发的」。任何一个智能体消息——正文、思考、工具、错误——
落下来它就永久退场，不存在回闪。这条抽成纯函数（`AwaitingPlaceholderTest`，6 个用例），
因为它在设备上只能靠肉眼观察，而时序最容易被后续改动碰坏。

文案取「正在生成」，不用「已发送」：此刻请求未必已经到达服务端，写成状态确认是错的。

### 25.4 列表贴底：三个连环坑

这一节是本轮耗时最多的部分，三次修改都只治了表象。

**坑一：按 `atBottom` 判断是否跟随。** 流式内容变长会重新分组，`ChatItem` 的 key
跟着变，LazyColumn 找不到原来的锚点，位置跳一下。跳完 `atBottom` 变 false，
若据此刻判断就永久停止跟随。改为只在**用户拖动结束时**采样 `followTail`。

**坑二：用 `isScrollInProgress` 识别「用户在滑」。** 它对 `scrollToItem` /
`animateScrollToItem` 同样为 true，而本文件几乎每帧都在程序化贴底，
于是跟随标记被反复误判成 false。改用 `listState.interactionSource.interactions`
里的 `DragInteraction`，并等到惯性也停下来（`isScrollInProgress` 转 false）
再读取最终位置。

**坑三（真正的根因）：`scrollToItem(i)` 默认把第 i 条的顶部对齐到视口顶部。**
最后一条往往是几屏长的回复，那样只停在它的**开头**，`atBottom` 仍为 false，
「跳到最新」按钮随即冒出来——看起来就像「跑到了别处」，其实是停在了这条消息的开头。
所有贴底调用改用 `requestScrollToItem(index, Int.MAX_VALUE)`：偏移超出内容范围会被
钳到真实底部，这才是「滚到最后」。

顺带补了两处：

- 贴底的触发键从 `messages.size` 改成三路（最后一条的 id、文本长度、分组后的条目数）。
  回复结束时 `reconcileWithServer` 用服务端历史整体替换列表，本地 id
  （`local-user-N` / 流式 msg_id）全部换成服务端 id，条数却可能不变；而此时流式标记被清掉，
  一串「正文 + 思考 + 工具」又会被折成一个 `Steps`，条目数反而减少。三个键各盯一种变化。
- 补页逻辑加 `if (followTail || state.running) return`。列表被整体替换的瞬间，
  旧锚点消失，`firstVisibleItemIndex` 可能短暂塌到 0，被误判成「翻到顶了」，
  接着把几个月前的历史铺回来。

**这一节的教训**：`scrollToItem` 的偏移参数不是「额外微调」，它决定对齐方式。
不传就是顶部对齐。项目里此前所有贴底调用都没传，只是恰好那些位置最后一条很短，
没暴露出来。看 Compose 滚动 API 时要连默认值一起看。

### 25.5 GIF 头像

用户要求 GIF 头像动起来，不是只显首帧。两条路取舍后选了引入 Coil：
`io.coil-kt:coil-compose:2.7.0` + `coil-gif:2.7.0`（约 700KB）。

`AvatarStore` 新增 `imageLoader`：API 28 及以上注册 `ImageDecoderDecoder`（系统
`ImageDecoder` 驱动动画），API 26–27 用 `GifDecoder`（Coil 自带 `Movie` 逐帧播放）。
minSdk 是 26，两条分支都必须留。`ChatAvatar` 改用 `AsyncImage`，
删掉 `AvatarStore.load()` 与它对 `BitmapFactory` 的依赖。静态 PNG 走同一条路径，没有第二条分支。

首字回落保留，但只在图片就绪前显示。图片就绪后不再叠在底下：带头像的 GIF 常有透明区域，
首字会从透明处透出来。加载失败（文件损坏、格式不支持）退回首字，不留空洞。

「关于」页补了 Coil 的第三方资源条目。

**被推翻的旧决定**：第 22 节曾明确写过「不引入 Coil，GIF 只显示首帧」，
理由是「32dp 圆形头像播动图的观感收益不足以抵依赖成本」。这次用户直接要求动起来，
前提变了——那是用户明确的需求，不再是自制与依赖之间的自主权衡。
`architecture.md` 第 5 节的两条 `ChatImageLoader` 相关行也一并改写：
会话图片仍不用 Coil（三种地址形态仍要自定义逻辑、缓存会重复），
头像用 Coil（只服务本地文件、与前者无重叠、逐帧解码已有封装）。
**这两件事不冲突，边界是「图片来自哪里」**，原来那一行没把边界写清楚，
只写了「不引入 Coil」，容易在下一次读到时被当成不可推翻的结论。

## 26、交付文件、气泡铺满与协议补全（2026-10-30）

本轮的问题都来自实际使用：智能体交付的文件在客户端完全不显示；用户气泡右侧与
智能体气泡左侧各有一条空白；只填域名时被补成 `http://`，登录接口返回 404。
另外按要求加入了两个托管平台域名的拦截。

### 26.1 `send_file_to_user` 没有文件接口

官方 Web 把交付结果渲染成带缩略图的文件卡片，客户端这边整轮回复只剩
「处理完成 · 16 步」。查历史消息后确认，服务端**没有「已交付文件」这类接口**，
文件字节直接内联在工具输出里。

实测了一次真实的 `send_file_to_user` 回合，
配对的 `plugin_call` 与 `plugin_call_output` 形如：

```json
{"call_id":"call_38d30734739842a996f508da","name":"send_file_to_user",
 "arguments":"{\"file_path\": \"/home/.../chatgpt_2022-12-05_esperanto.png\"}"}

{"call_id":"call_38d30734739842a996f508da","name":"send_file_to_user",
 "output":"[{\"type\":\"data\",\"id\":\"744e...\",\"source\":{\"type\":\"base64\",\"data\":\"iVBORw0KGgo...\"}}]"}
```

两条结论直接决定了实现：

1. **`output` 里没有文件名。** 文件名只能取 `arguments.file_path` 的 basename，
   因此解析器必须先按 `call_id` 把调用与输出配对。历史路径由
   `HistoryMapper.map()` 维护 `argsByCallId`；流式路径由 `StreamAccumulator.onToolOutput`
   传当前工具卡的 `arguments`，两条路径共用 `DeliveredFiles.parse()`。
2. **`output` 是字符串里再套一段 JSON**，不是对象。第一次解析拿到的是
   `"[{\"type\":\"data\"...}]"`，需要再解一层。

`DeliveredFile`（89 行）只对图片解 base64 并拼成 data URI；其它类型只保留
文件名与路径。`DeliveredFilesCard`（167 行）每行 44dp 缩略图、文件名、完整路径与
「已发送」，图片行可点开全屏。缩略图复用 `ChatImageLoader` 的 data URI 分支，
失败时回退 `Icons.Default.Description`，不新增图片库。

**解析后立即把 `ToolCard.output` 置 null。** base64 往往是几 MB 到几十 MB，
留在界面状态里会让每个携带工具卡的重组都复制一遍字符串，也让日志与导出
无意中带上整份文件内容。代价是工具卡片展开后不再显示这段原始输出——
它本来也不适合阅读，展示职责交给文件卡片。

### 26.2 一个转义坑：`JsonPrimitive.content`

第一版 `DeliveredFilesTest` 里「历史能配对出文件」一例失败，期望 1 实得 0。
原因是 `HistoryMapper` 取字符串用的是 `element.toString().trim('"')`，
对 `arguments` 这种本身就是 JSON 字符串的字段会保留内部转义（`{\"file_path\": ...}`），
二次解析拿不到 `file_path`。

改用 `(element as? JsonPrimitive)?.content`，它返回**已反转义**的内容。
三处取字符串的地方（`HistoryMapper`、`DeliveredFiles.pathOf`、`parse`）统一成这一种写法。
`toString()` 得到的是 JSON 表示，不是值本身，这两者不能混用。

### 26.3 气泡两侧的空白是结构造成的

`MessageBubble.MessageFrame` 原来的结构是
`Row[ChatAvatar | Column[头部, 内容, 操作行]]`。内容列因此永远让出
`8dp + 32dp` 的头像宽度：用户侧头像在右、智能体侧在左，于是两侧各留一条空白，
气泡永远贴不到屏幕边缘。

改为 `Column[头部行(头像 + 昵称/时刻) | 内容与操作]`，内容列 `fillMaxWidth()`。
头像与昵称同处第一行，视觉上仍是「头像在左/右」，但不再挤占内容的横向空间。

`ui-guidelines.md` 8.1 的示意图本来就是头像在头部行，是代码与文档不一致，
本轮以文档为准修代码。

### 26.4 默认协议按主机判断

原先把所有未写协议的地址一律补成 `http://`。公网域名多数只开 https，
`http://chat.example.com` 会被反代以 301 跳到 https；OkHttp 跟随 301 时
把 POST 改写成 GET 并丢弃请求体，`POST /api/auth/login` 于是变成
`GET /api/auth/login` 并返回 404。用户看到的却是「会话不存在或已被删除」。

现在的规则写在 `InstanceRepository.defaultSchemeFor()`：

| 主机形态 | 默认协议 |
| --- | --- |
| 显式写了 `http://` 或 `https://` | 不改写，用户的意思优先 |
| `localhost`、`127.*`、`::1` | http |
| `10/8`、`172.16/12`、`192.168/16`、`169.254/16`、`100.64/10` | http |
| `.local`、`.lan`、`.internal`、`.home` 结尾 | http |
| 其余（公网域名、公网 IP） | https |

端口回填与协议绑定：`https` 未写端口回填 443，`http` 回填 80。
此前统一回填 80，https 地址会得到 `https://example.com:80`，直接连不上。

登录 404 的文案改为由 `ApiException.userHint` 携带，`ErrorText.of()` 优先使用它。
文案指向地址与协议，不再说「会话不存在」。失败提示另按实际协议给建议：
http 下拿到 4xx 提示改用 https，https 下连不上提示服务端可能只开了 http
（`ErrorText.hint(e, usedHttps)`，`usedHttps` 由 `InstanceRepository.usesHttps` 判定）。

**与计划文档的两处偏离**（本轮动手前写过一份 https 修复计划，其中提出加探测请求、
把日志留在 application interceptor）：

1. 计划提出加一个「不跟随重定向」的探测请求来判断是否发生 301。实际不需要：
   `login()` 只在 `authStatus.enabled && hasUsers` 为真时调用，说明服务端确实
   提供了登录接口，此时 404 只可能是请求没有落到该端点，文案可以直接说明这一点。
2. 日志改用 **network interceptor**。application interceptor 看到的是跟随之后的
   最终响应，301 那一跳不在其中；network 层才能记下「被重定向到某处」。
   `LoggingInterceptor` 现在记录 `scheme://host:port + encodedPath`，3xx 追加
   「（重定向，未跟随）」。

### 26.5 托管平台域名的拦截位置

两个域名按用户给定的原文与文案拦截：

| 域名 | 提示 |
| --- | --- |
| `qwenpaw.platform.agentscope.io` | QwenPaw Node无法添加源于AgentScope Platform的实例，请使用私有化部署方案 |
| `modelscope.cn` | QwenPaw Node无法添加通过魔搭创空间创建的实例，请使用私有化部署方案 |

`hostedPlatformOf()` 同时匹配域名本身与子域名（`xxx.modelscope.cn` 同样是创空间实例），
匹配前统一小写并去掉末尾的点。

**拦截放在 `normalizeBaseUrl()`，不是各个界面。** 验证连接、真正连接、列智能体、
保存实例四条路径都要经过它，放在这里意味着「验证失败 → 下一步不可点」自然成立，
不必在每个页面各写一遍判断，也不会因为新增入口而漏掉。
`IllegalArgumentException.message` 直接就是给用户看的那句话，
经 `ErrorText.ofWithHint()` 原样显示。

选择 `IllegalArgumentException` 而不是新的异常类型：这个函数的既有契约就是
「参数不合法时抛它」，托管平台域名属于同一类问题，调用方已有处理。

也就是说：官方客户端能连 Platform，不是因为它找到了直连端点，而是因为它走
另一条鉴权通道。本项目的拦截不构成对官方能力的否定，

这一点在 README 里单独写了一句，否则读者容易理解成「Platform 根本不能连」。

## 29、多架构构建与公开仓库（2026-10-30）

用户要求「多构建一个 x86 和 arm v7a 的客户端」，并明确「不保证额外构建的可以用」。
因此本轮的重点不是代码，而是**把可验证边界写清楚**。

### 29.1 为什么用 splits.abi 而不是 abiFilters

`abiFilters` 加两项只会得到**一个**包含四份 native 的包，约 93MB。
用户原话是「多构建一个」，他要的是分开的包，不是更大的包。
`splits.abi` + `isUniversalApk = false` 才对应这个语义。

两者不能共存：同时写时 `abiFilters` 被忽略。因此把原来那行 `ndk.abiFilters` 删了，
换成 `splits.abi`。这一点写进 release.md，否则后来者看到 `include()` 会以为
还要配 `abiFilters`。

### 29.2 实测数据（`assembleRelease`，3m12s）

| 架构 | 字节 | 约 | native 构成 |
| --- | --- | --- | --- |
| `arm64-v8a` | 24,497,163 | 23.4MB | 21.4MB |
| `armeabi-v7a` | 17,267,983 | 16.5MB | 14.5MB |
| `x86_64` | 27,443,453 | 26.2MB | 24.2MB |
| `x86` | 38,448,662 | 36.7MB | 5.1MB + `libonnxruntime.so` 29.6MB |

`x86` 比 `x86_64` 还大，原因是只有 32 位 x86 在 AAR 里额外带了一份独立的
`libonnxruntime.so`。这一条与直觉相反，值得记下来：架构「更老」不等于「更小」。

R8 只跑一次，输出的是 dex，与 ABI 无关；多架构增加的只是每个 split 各打一次包、
各签一次名的时间，不是四倍构建时间。

### 29.3 验证到了哪一步

x86_64：模拟器 `qp35` 上安装 `app-x86_64-release.apk`。

- 第一次 `adb install` 失败：`INSTALL_FAILED_UPDATE_INCOMPATIBLE`，
  原因是模拟器上装的是 debug 包，签名与 release 不同。
  按 release.md 4.1 的既有约定先 `adb uninstall` 再装，通过。
- 启动 → 通知权限 → 引导页「连接到 QwenPaw」，`ConnectingScreen` 正常渲染。
- 填 `10.0.2.2:8088`（已 `adb reverse`），点「验证连接」得到
  「连接正常，服务端 2.2.2.post1」。

arm64-v8a：此前多轮真机验证过，本轮未重复。
**armeabi-v7a 与 x86 没有验证**，原因见 29.4。

### 29.4 为什么这两个架构验不了

- **armeabi-v7a**：本机是 x86 宿主，ARM 镜像只能 `-accel off` 全模拟运行，
  慢到无法完成界面操作；AGENTS.md 也写明真机测试已停用。
- **x86**：API 30 起官方不再提供 32 位 x86 系统镜像。要测只能退回 API 29 的 AVD，
  而这与本项目 minSdk 26 的验证矩阵混在一起，成本高于收益。

**所以文案只写「额外构建、未实测」，不写「支持」。** README 用加粗区分两组，
release.md 7.1 用表格逐条标状态，CHANGELOG 也重复一次——
三处口径一致，避免用户从 Release 页面看到四个包就以为都验过。

## 30、CI 首次跑通与自动发布（2026-10-31）

### 30.1 目标

推 `v*` tag 即自动产出四个架构的签名包并挂到对应的 GitHub Release。
第 29 节的做法是本地构建、手工上传，这一节把流程交给 GitHub Actions。

### 30.2 第一层障碍：runner 上的 SDK 安装步骤直接失败

前两次失败发生在 `android-actions/setup-android@v3`，该步骤 failure 之后其余步骤全部
skipped，注解里只有一句「Process completed with exit code 1」。为排除「Actions 未启用」
与「仓库私有」两种猜测，临时加了一个只执行 `echo` 的 `Smoke` workflow，它 success，
说明 runner 本身可启动，问题出在 SDK 步骤。

改为直接调用 runner 自带的 `$ANDROID_HOME/cmdline-tools/*/bin/sdkmanager`：
先 `yes | sdkmanager --licenses`，再装 `platform-tools`、`platforms;android-35`、
`build-tools;35.0.0`。`ci.yml` 与 `release.yml` 共用同一段，此后该步骤通过。

### 30.3 第二层障碍：诊断信息本身把原因挡住了

最初把失败的 `tail -n 20` 写进注解，拿到的是 `DaemonCommandExecution` 的堆栈尾部，
真实原因在更靠前的位置，等于什么也没诊断出来。

改为用 `awk` 截取 Gradle 输出里「What went wrong」到「Get more help」之间的一段，
取不到再退回 `tail -n 40`，才看到真正的原因：
`Plugin [id: 'com.google.devtools.ksp', version: '2.1.0-1.0.29'] was not found`。

单测失败时同理。新增一步解析 `app/build/test-results/testDebugUnitTest/*.xml`，
按 `类名#方法名: 消息` 逐条输出，才定位到唯一失败的用例。

### 30.4 原因一：阿里云镜像在 runner 上不可达

`settings.gradle.kts` 把 `maven.aliyun.com` 排在所有仓库之前。本机可达，
runner 上不可达，KSP 的插件标记因此在所有仓库解析失败。

改为按环境切换：`CI=true`（GitHub Actions 默认注入）时只保留 `google()`、
`mavenCentral()`、`gradlePluginPortal()`；本地仍优先镜像。验证时注意，
本机 Trae 的 shell 也带 `CI=true`，在这个 shell 里跑构建走的同样是官方仓库。

### 30.5 原因二：TimeLabelsTest 依赖本机时区

```
io.qwenpaw.node.ui.TimeLabelsTest#parses timestamp with local offset:
java.lang.AssertionError: expected:<26> but was:<25>
```

`TimeLabels.parse` 按 `ZoneId.systemDefault()` 换算，runner 是 UTC，
`2026-10-26T00:15:42+08:00` 落到 10-25，断言里的 26 日与 `2026.10.26` 前缀都失败。

测试类的文档注释本来就写着「本地时区固定为东八区来断言，避免测试机在别的时区时结论漂移」，
但实现取的是 `ZoneId.systemDefault()`，注释与代码不符。这是测试的缺陷，不是产品缺陷。
改为 `@BeforeClass` 里 `TimeZone.setDefault(Asia/Shanghai)`、`@AfterClass` 还原，
`zone` 直接取 `ZoneId.of("Asia/Shanghai")`。

本地以 `TZ=UTC` 复跑全量单测：340 个用例、0 失败。

### 30.6 结果

tag `v0.1.0-b2` 指向 `1f5764a`，Release workflow 的十一步全部 success，
Release 页面出现四个包，字节数与本地构建逐一相同：

| 包名 | 字节数 |
| --- | --- |
| `QwenPaw-Node-v0.1.0-b2-arm64-v8a.apk` | 24,497,163 |
| `QwenPaw-Node-v0.1.0-b2-armeabi-v7a.apk` | 17,267,983 |
| `QwenPaw-Node-v0.1.0-b2-x86_64.apk` | 27,443,453 |
| `QwenPaw-Node-v0.1.0-b2-x86.apk` | 38,448,662 |

签名密钥不在仓库里。workflow 从四个 secrets 解码 `release.jks` 与 `keystore.properties`
到 `$RUNNER_TEMP`，随 runner 销毁；`apksigner verify` 不通过就中止发布，
不会产出未签名的包。secrets 缺失时在解码步骤直接报错退出。

## 32、全量盘点 Console 页面并确定替代方案（2026-11-01）

### 32.1 拿到完整端点清单的方式

`/openapi.json` 默认返回 404。原因是 `constant.py:265`：

```python
DOCS_ENABLED = EnvVarLoader.get_bool("QWENPAW_OPENAPI_DOCS", False)
```

关闭时不注册 `docs_url` / `redoc_url` / `openapi_url`。**不能通过改运行中实例的环境变量
重开**，因为该值在进程启动时已固化。采用的替代做法是在临时 HOME 下起一个独立进程，
只调用 `app.openapi()` 导出 JSON 后即退出，不监听端口：

```bash
HOME=/tmp/qp2 QWENPAW_OPENAPI_DOCS=1 ~/.qwenpaw/venv/bin/python -c "
from qwenpaw.app._app import app
import json; json.dump(app.openapi(), open('/tmp/qp_openapi.json','w'))"
```

结果：**517 条路径、649 个操作**，其中挂在 `/api/agents/{agentId}/` 下的有 234 个，
即同一批端点有两套入口（全局与 agent-scoped）。此前 `待办清单.md` 记录的是
「43 个 router、已实现 37 个方法」，两个口径都不完整。

导出时 FastAPI 报了一条 `Duplicate Operation ID preview_file_api_files_preview__filepath__get`，
说明 `files.py` 里同一函数注册了两次（GET 与 HEAD），不影响使用。

### 32.2 页面清单的来源

不依赖文档推演，直接从构建产物 `console/assets/index-*.js` 提取：

```bash
grep -ohE '\{id:"[a-zA-Z0-9_.:-]+",path:"/[a-zA-Z0-9/_.:-]*"' *.js
```

得到 **28 个 `core.*` 路由**。菜单分组与顺序从同一文件的 `route:"core.*"` 片段读取，
四个分组为 `primary.agentScoped`（聊天 / 收件箱 / 扩展市场 / 导入 / 控制组 / 工作区组 / 智能体组）、
`primary.settings` 等。`docs/console.zh.md` 的 第 19 节与之一一对应，但少了
`core.acp`、`core.agent-stats`、`core.backups`、`core.debug` 等。

### 32.3 三个关键实测

**多智能体串号。** 同一个 `GET /api/chats?archived=false`，不带 `X-Agent-Id` 返回 9 条，
带 `X-Agent-Id: Kurikawa_Nana` 返回 12 条；而 `/api/agents/Kurikawa_Nana/chats` 也是 12 条。
两者统计口径不同足以说明：全局路由在多智能体环境下会按某种默认作用域过滤。
客户端切换智能体时若不同步该头，看到的就是别的智能体的会话。

**本机限制的实际边界。** 从 `127.0.0.1` 调 `POST /api/fork/agent` 返回 200；
从局域网地址 `192.168.1.10` 调同一个端点返回
`403 {"detail":"Fork endpoint is localhost-only"}`。
`/api/agents/{id}/portability/*` 同样返回
`403 {"detail":"Import endpoints are localhost-only"}`。
这是「手机能不能用」的分水岭，此前只在源码里读到限制，没有实测过远程侧的行为。

**WebView 无法只加载单个 App。** 装官方 `agent-kanban` 后访问 `/apps/agent-kanban`，
返回的是与首页**完全相同**的 `index.html`（38125 字节，引用同一个 `index-BpFaGbCq.js`）。
PawApp 的真实形态是 `GET /api/frontend_plugin/{id}/files/ui/index.js` 动态 import 的
ESM 模块，依赖宿主注入的 `window.QwenPaw.host.React` 与 `antd`。
用 headless Chrome 以 390×844 视口访问，DOM 中出现 `Kanban` 与 `Issue`，
说明移动视口可渲染，但代价是必须先加载整个 Console。

### 32.4 一处推翻自己的估算

上一轮答复里说「WebView 首屏会加载 55 MB assets」。本轮重新测量后修正：

- `console/assets` 目录总计确实约 **55 MB**，但其中包含 `.br` / `.gz` 旁文件与
  540 个按需加载的 chunk。
- 首页实际需要的只有 `ui-vendor` 6.1 MB + `index` 0.88 MB + `chat-vendor` 0.72 MB
  + CSS 0.15 MB ≈ **7.9 MB**。
- 服务端注册了 `ResponseCompressionMiddleware(minimum_size=1000)`，但
  `app/response_compression.py` 只接受 `gzip` 与 `*`，**不接受 `br`**。
  实测带 `Accept-Encoding: br, gzip` 请求 `ui-vendor`，仍返回 6370169 字节、
  无 `content-encoding` 头。静态目录里那份 1.68 MB 的 `.br` 并未被中间件利用。

所以正确说法是「首屏 7.9 MB 未压缩，压缩是否生效取决于客户端发什么
`Accept-Encoding`，需在阶段 3 开工时实测」。上一轮的 55 MB 是把目录总量当成了首屏成本，
属于没有测量就下结论。

### 32.5 两个被否定的方向

**「改环境变量重开 OpenAPI」** —— 该值在启动时固化，改运行中实例无效，

### 32.6 用户本轮确认的决策

1. **App 中心不做内嵌 WebView，改为 `Intent` 跳转浏览器。** 最初倾向 WebView，

另确认：工作区文件与技能**要支持简单编辑**。`PUT /api/workspace/file-content`

`PUT /api/skills/save` 的 `content` 是 Markdown 字符串。两者可共用一个文本编辑组件。

## 34、验收脚本切到容器与跨版本适配调研（2026-11-01）

上一轮把测试环境从宿主机的 `:8088` 换成两个 LXC 容器，本轮把脚本与文档一并切过去，
同时回答用户提出的「少端点怎么适配」这个问题。脚本切换是收尾，
调研才是本轮的主要产出，因此先写调研。

### 34.1 问题

用户在 2.3.0b2 上发现 `GET /api/workspace/download` 返回 404，
2.2.2.post1 上同一个路径返回 200 的流式 zip。问题是：
客户端该按服务端版本分支，还是放弃依赖该端点的功能。

### 34.2 先数清楚差在哪

导出两份完整 OpenAPI 后逐条比对（方法见第 32 节，本轮复用同一套流程）：

| 项目 | 2.2.2.post1 | 2.3.0b2 |
| --- | --- | --- |
| 路径数 | 517 | 545 |
| 新增 | — | 33 |
| 移除 | — | 5 |

关键是客户端自己用了哪些。按 `app/src/main/java` 里出现在代码行（不含注释）中的
`/api/` 字面量去重，得到 **33 条路径**，逐条在两份规格里查，
结论是：**路径与 HTTP 方法完全一致，没有一条落在被移除的 5 条上**。
其中 `/api/files/preview/` 是拼路径用的前缀，实际请求为 `/api/files/preview/{filepath}`，
两版都有该路由。

被移除的 5 条是：`workspace/download`、`workspace/upload` 的全局与 agent-scoped 版本，
以及 `desktop/shutdown`。客户端一条都没用——
`desktop/shutdown` 从未实现，整包下载/上传上两轮的设计里本就换成了逐文件方案。

参数层面只有两处变化，都是**新增可选参数**：
`POST /api/console/chat/stop` 多 `initiator`，`GET /api/models/{provider_id}/pool` 多 `model_type`。
旧调用不带这两个参数，行为不变。

### 34.3 一个踩到的判定坑

第一反应是「探一下端点是否存在」。实测发现这条路走不通：

- `GET /api/workspace/download`：2.2.2 回 200，2.3.0b2 回 404；
- `POST /api/workspace/upload`：2.2.2 回 422（缺 `file` 字段），2.3.0b2 回 **405**。

405 是因为同一路径下仍有 `file-upload` 一类其它方法的路由，FastAPI 对「路径在、方法不在」
回 405；而 404 才表示路径本身没有。可这两者都不能单独作为「端点被删」的证据：
路径拼错同样回 404，方法写错同样回 405。
所以**判断端点可用性只能以规格对照为准**，运行时探测没有可信的判据。

### 34.4 定下的规则：不分支

三条理由写在 [protocol.md](protocol.md) 第 17 节，这里只重复最要紧的一条：
版本号不是稳定的能力标识。`2.3.0b2` 是预发布写法，正式版是 `2.3.0`；
用字符串前缀比较迟早出错，而服务端没有 `capabilities` 一类接口。
再叠上「当前没有调用落在被删端点上」这个事实，分支没有任何作用对象，
只会增加未被测试覆盖的代码。

规则因此是**约束式**的而非分支式的：客户端不依赖可被移除的整包端点，
需要整包能力时改走 `workspace/tree` + `file-download`，或 `project-directory/upload-zip`。
这条已经写进 [AGENTS.md](../AGENTS.md) 2.2，作为后续接端点时的硬约束。

### 34.5 意外发现：干净实例才暴露的 null

本轮顺手把两个容器的几个端点各跑了一遍，比对实际报文。`GET /api/token-usage` 在
2.3.0b2 容器（全新、零调用）上返回 `"cache_hit_rate": null`，
而 2.2.2 容器有历史数据，返回的是数字。DTO 里写的是非空 `Double`，
于是整个响应解析失败——界面显示「加载用量失败」，而不是一组零值。

OpenAPI 早已把该字段声明为 `number | null`，两版一致；也就是说这不是版本差异，
而是**一直存在、只是没被空数据覆盖到**的形状。改法是把字段声明成 `Double?`，
界面在为空时显示「暂无数据」——「还没测过」与「命中率为零」对用户是两件事。

这个发现的价值不在这一行代码，而在方法论：拿有数据的实例做回归，
永远测不出「空数据时字段为 null」这类形状。

### 34.10 接着做完自动命名（4.2）

用户列的第 2 项「创建新会话发消息后自动命名对话」此前一直没有真正生效，
本轮把它做完。查服务端源码后确认根因不在拼接名称，而在请求体：

```python
# console.py，两处判断缺一不可
if first_text and not chat.last_finished_at and chat.meta.get("console_placeholder_name") == chat.name:
    chat = await patch_chat_if_name_matches(chat.id, chat.name, ChatUpdate(name=name))
if first_text and chat.name == name:
    asyncio.create_task(generate_and_update_title(..., placeholder_name=name))
```

客户端一直只传 `name`，从不写 `meta`。第一处判断落空，名字停在占位值；
第二处因此也不成立，标题生成任务根本没被派发过。
这解释了为什么「自动命名从来没生效」，而不是「偶尔不生效」。

改法是三处：

1. `QwenPawApi.createChat` 增加 `placeholder` 参数，为 true 时写入
   `meta.console_placeholder_name = name`；请求体抽成 `createChatBody` 以便断言。
2. `send()` 新建会话与 `createChat()` 手动新建都传 `placeholder = true`，
   并把占位名按 chatId 记进内存 map。
3. `finishRun` 的列表刷新改为按「名字是否仍等于占位名」判断，
   需要时补刷一次（4 秒后）。不轮询：标题生成有 30 秒超时，
   而会话名在手改后也不该被覆盖。

实测（`10.10.0.211:8088`）：建会话时名字为「帮我检查网络是否通」，跑完一轮后
`GET /api/chats` 返回「一句话说明助手能力」，自动命名确实生效。
对照早前不带 `meta` 的探针会话，名字保持不变。

新增 4 个 `AutoTitleTest`（占位名判据）与 2 个请求体断言，单测总数 345 → 351。
协议细节写进 [protocol.md](protocol.md) 第 11 节新增的「会话标题的自动生成」。

### 34.11 公式渲染（4.1）

第 1 项要求「消息需要 LaTeX 渲染支持」。选型阶段先否掉两条现成路线：

- `jlatexmath-android` 是 GPL-2.0。本项目是 MIT，一旦链接进来，
  整个 APK 的分发条款都会被传染；这不是风格问题，而是许可证不兼容。
- WebView + KaTeX 要打包几百 KB 的 JS，并且流式输出时每帧都要重建 WebView，
  与项目此前为性能做的所有努力相悖。

因此自研，但**只做明确列举的子集**：结构（`\frac`、`\sqrt`、上下标、
`\left…\right`、`\text`）、大运算符（`\sum`、`\int`、`\lim` 等）、
希腊字母、常用关系与运算、函数名、定界符。超出范围一律返回 null。

**「不做尽量解析」是一个决定，不是偷懒。** 半个公式渲染出来比源码更难判断哪里出错，
所以未知命令、花括号不配平、`\left` 缺 `\right`、嵌套超过 8 层全部整体失败，
界面退回原文并说明不支持。

实现过程中踩到两个自己写的坑：

1. `\sqrt[3]{x}` 解析不出来。根指数的 `[…]` 没有对应的结束判定，
   标量序列一路把 `]` 当普通字符吃掉，最后 `require` 抛错。加 `stopAtBracket` 解决。
2. `\left( x \right)` 抛 `NoSuchElement`。`peekCommandName` 只负责看，
   而收割时直接调了 `readCommandName`——它从当前字符开始读，当前字符是反斜杠，
   于是读到空串，随即越界。改为先 `pos++` 跳过反斜杠再读名字。

行内公式一开始想做二维排版，实测发现 `InlineTextContent` 要求预先给出固定尺寸，
而公式高度随嵌套层数变化，估出来的框不是压字就是留空。改为压成单行文本：
`\frac{a}{b}` → `a⁄b`、`\sqrt{x}` → `√(x)`、可映射的字符转 Unicode 上下标。
有一个字符映射不到就整段退回 `^`，避免半上标混排。

流式输出的处理：`$$` 先于内容到达，此时解析必然失败。因此 `MarkdownParser`
只在找到闭合定界符时才产出 `MdBlock.Math`，否则留在普通段落里按原文显示。
若不这样做，界面会在「半个公式」与「源码」两态之间来回跳。
行内 `$` 还要避开货币符号：起始 `$` 后须紧跟非空白、闭合 `$` 前须紧邻非空白，
`$5 and $10` 因此保持原样。

单测新增 18 个 `LatexParserTest` 与 5 个 Markdown 公式块用例，总数 351 → 375。
Kotlin 字符串里 `$` 是模板前缀，测试里必须写 `\$`，否则 `$x` 会被当成变量引用——
第一次写测试时正因此编译失败。

渲染与判定规则记在 [ui-guidelines.md](ui-guidelines.md) 8.7。

## 35、服务端头像与十一项体验优化收尾（2026-11-01）

本轮把计划里剩下的九项做完，并接入服务端头像。单测 375 → 404，
仪器测试 1 → 6。

### 35.1 服务端头像只能做用户侧

先确认能不能一个接口解决「用户头像 + 智能体头像」两件事，结论是不能。
`qwenpaw/user_assets/avatar_routes.py` 的 `avatar_owner()` 不读任何请求参数，
固定返回 `"console"`，服务端也没有按智能体区分的头像端点。因此这张图只用于用户侧，
智能体头像保留本地存储，两者的取值优先级分开处理。

服务端上限来自 `avatars.py`：单张 2 MB、PNG/JPEG/WEBP/GIF、最长边 16384、历史 12 张。
了解上限是为了两个决定：一是缓存文件名用 `selected` 的 id 而不是固定名（避免覆写后
Coil 按路径命中旧图），二是换 id 后要删旧文件（2 MB × N 张不可忽略）。

**图片端点必须单独开一条通道。** `QwenPawApi` 的常规请求把 `body` 读成 `String`，
二进制图会按字符集转换而损坏。新增的 `requestBytes` 与 `execute` 同构，
只把 `body.string()` 换成 `body.bytes()`，错误分支保持同一套日志与 `ApiException`。

缓存策略是「先读盘上屏，再联网核对」：冷启动与断网都能显示上一次的头像。
`refresh()` 里 `selected` 为 null 时清空缓存并返回 null，id 未变时只发一次清单请求。
网络失败不在此处静默——调用方（`AppViewModel.refreshServerAvatar`）在失败时保留旧文件，
否则一次网络抖动就会让头像消失。

取值优先级抽成纯函数 `resolveUserAvatar`，八种组合逐一单测。两条规则值得写下来：
本机图片优先于服务端（用户在这台设备上的主动选择），开关只作用于服务端
（关掉它是「不显示」，不是「清空我的头像」）。

### 35.2 滚动跟随的缺陷是「按下的那几秒」

原实现只在 `DragInteraction.Stop` 之后采样落点。问题出在按住往上滑的整个过程中：
流式内容仍在增长，贴底副作用持续生效，用户看到的是「拖不动、拖到一半被拽回去」。
补 `DragInteraction.Start → followTail = false` 即可，代价是必须同时处理 `Cancel`
（来电或布局突变打断手势时若不再采样，`pendingSample` 永不置位）。

抽成 `FollowTail` 普通对象而非 `mutableStateOf`：它的值只在副作用里读写、不参与组合，
不需要触发重组；抽出来是为了四条转移规则能在 JVM 里断言，而不必开模拟器拖列表。

**打 release 包时才发现，接入 `FollowTail` 的那段收集代码本身是空的。**
构建日志给出三条 `Check for instance is always 'false'`，指向 `ChatScreen.kt` 的三个
`is DragInteraction.*` 分支。根因是 `listState.interactionSource.interactions`
已经是 `Flow<Interaction>`，却又被套进了 `snapshotFlow { ... }`，于是 collect 拿到的是
那个 Flow 对象本身，三个分支恒不成立。改成直接收集 `interactions` 后警告消失。

这个错误有两点值得记：

1. **构建成功不等于行为正确。** 三条都是警告，`assembleRelease` 一路成功、四个包都产出、
   签名也生效，若不去读编译输出就会把一个「拖拽完全不响应」的包直接交给用户。
   本轮的单测也没拦住它——`FollowTailTest` 只验证状态机本身，而状态机从未被调用。
2. **同一个 `when` 里的 `userScrolled = true` 一起失效了。** 补页逻辑用它判断
   「用户是否真的滚动过」，于是长历史永远补不出下一页。这是第二个独立症状，
   查起来很容易误判成两个 bug。

### 35.3 按来源排序不能只信 order

原实现按 `pinned` → `order` 排序。两个容器实测 `cron` 与 `subagents` 的 `order`
取值不同，只按 order 排会让定时任务偶尔出现在默认分组之前。改为五级权重
（custom 0 / default 1 / 其他内置 2 / cron 3 / subagents 4），`order` 只在同权重内生效。

未分组的位置单独处理：它插在「其他内置」之后、`cron` 之前，而不在末尾。
依据是它属于用户自己产生的会话，不该被自动任务的表头压在下面。

顺带修了一处顺序不稳定：`order` 相同时原来依赖 `sortedWith` 的稳定性，
现在让 `withIndex()` 参与排序，同一份数据两次渲染顺序一致。

### 35.4 会话图标用哈希做文件名

`ChatIconStore` 与 `AvatarStore` 同构，键换成会话 id。文件名取 SHA-256 前 16 位：
渠道会话 id 形如 `channel:lark/chat:123`，直接拼进路径轻则建不出目录，重则写到目录外。

图片与预设互斥，保存一类时清掉另一类。`resolveChatIcon` 仍按「图片 > 预设 > 默认」判一次，
因为从备份恢复时两份可能同时存在，需要一个确定答案。删除会话（含批量）时清图标——
图标是本机数据，服务端不知道它的存在，留着会让新建的同 id 会话显示上一次的图标。

### 35.5 菜单图标的遗漏靠单测守

`MenuIcons.of` 对未登记的 `MenuAction` 返回 null，菜单项退化为纯文字。
这种遗漏肉眼扫菜单未必看得出来，因此 `MenuIconsTest` 遍历全枚举断言不为 null。

编译期踩了两个图标名的坑：`DriveFileRenameOutline` 只在 `filled` 下，没有 `automirrored` 版本；
`Icons.Default.Label` 已废弃，要换成 `Icons.AutoMirrored.Filled.Label`。

### 35.6 仪器测试的两条写法约束

`UiRegressionTest` 首次运行时 5 条里有 1 条失败（设置分组的默认收起），
两次修正的原因都在测试写法而非实现：

1. **设置页是 `verticalScroll` 的 `Column`。** 语音组位于首屏之外，直接
   `performClick()` 的命中点落在屏幕外，表现为「点了没反应」。加 `performScrollTo()`。
2. **折叠状态由调用方持有。** 测试里只给 `onSectionCollapsed = {}` 时，点击回调了但状态
   没变，界面不会展开。必须传一份可变的 `collapsedSettings` 并在回调里更新它。

第 2 条更值得记：它说明「断言回调被调用」不等于「验证了交互效果」。

另有一次构建失败与代码无关：模拟器上残留了不同签名的旧包，
报 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`。`adb uninstall` 返回
`DELETE_FAILED_INTERNAL_ERROR`、`pm list packages` 也查不到，但仍占着签名槽位；
重启模拟器后消失。遇到这个错误先重启模拟器，不要在签名配置上找原因。

## 36、实机反馈第二轮：公式、设置层级与系统分享（2026-11-01）

用户在真机上装了上一轮的 release 包，反馈六条：公式几乎都渲染不出来、
段落里的上下标原样显示、设置页平铺太乱、页面切换先瞬切再播动画、
移除实例没有二次确认、附件只能选图片、导出只能写文件。另追加两条文案要求：
界面「会话」改「对话」，三个内置分组显示简体中文。

### 36.1 公式「几乎全都渲染不了」的真实原因

问题不在缺哪一条语法，而在解析器的失败模型：**一处未知命令即整条公式失败**。
一条 `\begin{cases}`、一个 `\mathbb{R}`、一个 `\vec`，都会让整段退回原文并附一句
「暂不支持渲染」。用户在真机上看到的正是这种整条降级。

改法是分层容错，而不是继续堆语法：

- 未知命令降级为 `Sym("\\name")`，按原样画出来，其余部分照常排版；
- 补齐高频命令：`\mathbb`、`\vec/\hat/\bar/\overline/\tilde/\dot/\ddot`、
  `\dots/\ldots/\cdots`、`\boxed`、`\tag`（丢弃，不参与排版）、转义 `%{}&#_$`；
- 多行环境单独排版：`cases`、`aligned`、`matrix`、`pmatrix`、`bmatrix`、`vmatrix`、`array`；
- 环境外的 `&` 与 `\\` 降为空格，避免表格语法混进正文时出现满屏反斜杠。

依据是服务端模型的实际输出：让 agent「只输出 LaTeX」后实测，它偏好 `cases`、
`\frac`、`\sqrt`、`\mathrm{H}_2\mathrm{O}` 与 `x^2`，这些都不该失败。

段落里的裸上下标是第二条独立问题。此前 `H_2O`、`x^2` 整段按普通文本处理，
`_` 与 `^` 原样显示。现在 `MarkdownText` 把它们转成 `BaselineShift` 的 span，
同时遵守 CommonMark 的「词内下划线不构成强调」，避免 `snake_case` 被拆成斜体。

### 36.2 多行环境在无上界约束下崩溃（本轮的实测事故）

第一版 `EnvView` 用 `SubcomposeLayout` 先量内容再画两侧定界符，测量调用写的是
`Constraints(maxWidth = (constraints.maxWidth - reserved).coerceAtLeast(0))`。
块级公式放在 `horizontalScroll` 容器里，父约束宽度是 `Constraints.Infinity`，
减去定界符占位后得到 `2147483615`，Compose 直接抛

```
IllegalArgumentException: Can't represent a width of 2147483615 and height of 0 in Constraints
```

模拟器上连续三次 FATAL，每次打开带 `cases` 的对话都退出。用 JVM 直接构造
`Constraints` 复验：`Infinity` 本身通过，`Infinity - 1` 到 `Infinity - 1000` 全部失败。
这说明 Compose 只把 `Int.MAX_VALUE` 当作无上界哨兵，对区间内的其它大值一律拒绝，
减法必须避开这条路径。

修法是宽度无上界时原样返回，并把这段判断抽成 `envContentMaxWidth`，
由 `LatexLayoutTest` 的四条断言守住，其中一条直接断言「`Infinity - 32` 会被 Compose 拒绝」，
把这条规则的存在理由写进测试。

### 36.3 分式横线与根号尾巴画不出来

原实现是 `Column { 分子; Box(fillMaxWidth().height(1.dp)); 分母 }`。
`fillMaxWidth` 在无上界约束下拿到的上限是 `Infinity`，实际宽度等于没有，横线不可见；
根号上那条代替尾巴的横线同理。

改成 `SubcomposeLayout`：先分别量出分子与分母，再按较宽一侧用
`Constraints.fixed(width, 1.dp)` 铺线。没有采用 `Modifier.width(IntrinsicSize.Max)`
的写法，因为该写法要求子项支持固有测量，而子项一旦是多行环境（`SubcomposeLayout`）
就会直接抛异常，`\frac` 里放 `cases` 即触发。

### 36.4 设置页「先瞬切再播动画」

根因是 `AnimatedContent` 只把页面枚举当作 targetState，而内容分支读的是外部的
`addMode` / `editing`。点击瞬间这两个值已经改变，正在退出的旧槽位因此被画成新页面，
表现为先瞬切、再两个相同画面互推。

改法是把「页 + 该页依赖的数据」整体放进 `SettingsNav` 作为 targetState，
退出槽位拿到的是它自己那一份数据。设置页同时从七组平铺折叠改成一级列表 + 二级子页：
一级页每行是图标 + 标题 + 当前取值 + 箭头，点行进子页，返回键逐层后退。
副标题直接给出当前状态（「跟随系统 · 字号 100%」「折叠结果 · 用量关」），
不必点进去才知道取值。

### 36.5 动画方向按入口边缘推导

规则收敛成一条：**入口按钮在哪条边缘，就从哪边进入；返回是进入的反向**。

| 转场 | 方向 |
| --- | --- |
| 聊天页 → 对话列表（入口在左上角） | 抽屉：列表从左滑入、退出时向左滑走，被盖住的聊天页只淡入淡出 |
| 列表 → 设置 / 归档 / 用量、设置 → 运行日志 | 从右滑入，返回向右退出 |

设置页的返回层级一并修正：此前从列表进设置、返回却回聊天页，「设置盖住列表」
这层关系被跳过，方向无从推导。现在 `parentOf` 显式给出父页，`BackHandler` 按层级后退。

### 36.6 三项交互收口

- 移除实例接入 `DestructiveActionDialog`，列出会丢失的配置，且不承诺撤销：
  服务端与本机都没有回收站。
- 附件入口由图库改为 `OpenMultipleDocuments("*/*")`，图片与文档走同一个入口，
  上传通道不变。
- 导出改为 `ACTION_SEND` + `createChooser` 的系统分享，删除原先的 SAF 写文件流程。
  纯文本不需要 `FileProvider`。

### 36.7 文案与内置分组

界面「会话」统一改「对话」，包含顶栏、列表、搜索框、批量管理、选择模式与通知。
三个内置分组的服务端名称是英文（`Uncategorized` / `Scheduled tasks` / `Subagents`），
读取时按 `kind` 换成「未分组」「定时任务对话」「子智能体对话」；
自建分组保留用户起的名字，名称为空才退回 id。菜单里的「移动到分组」与顶栏的
当前分组标签也走同一处映射，避免列表显示中文、菜单显示英文。

### 36.8 验证方法上的两个坑

**模拟器的动画缩放默认是 0。** `settings get global animator_duration_scale` 返回 0 时，
Compose 动画直接跳到终态。录屏逐帧比对了两次都只有首尾两帧，一度误判「动画没生效」。
把 `animator_duration_scale` 临时设为 1 到 10 才录到中间帧，验证完已还原为 0。

**`adb shell input text` 在模拟器上会跳进 Gboard 的搜索页。** 中文与含括号的英文串
都发不进去，输入框始终是空的。改走服务端 `POST /api/console/chat`，发一条
「只输出 LaTeX，不要解释」的消息，再回应用里刷新对话，直接看到真实渲染结果。
验证公式排版用这条路径比在模拟器上打字可靠。

### 36.9 结论落点

- 公式容错、多行环境与上下标 → [ui-guidelines.md](ui-guidelines.md) 8.7
- 设置页两级结构 → [ui-guidelines.md](ui-guidelines.md) 9.7
- 过渡方向与内置分组中文名 → [ui-guidelines.md](ui-guidelines.md) 9.10、9.11
- 分享、附件、移除确认与分组中文名 → [guide.md](guide.md) 第 2、3 节

## 37、实机反馈第三轮：图标集、空态与原文页（2026-11-01）

用户在真机上又验了一轮，反馈四条，另外追加四条小项。四条主项是：附件只能进小米文件管理器、
设置里所有点击又出现「先瞬切再播动画」、希望图标与官方网页对齐、以及要一整套空态首页。

### 37.1 设置子页瞬切的根因在 else 分支

上一轮把「页 + 依赖数据」整体放进 `SettingsNav` 当 targetState，解决了添加与编辑那几条分支，
但一级列表与子页之间的切换走的是 `else ->`，而它的内部仍然读外层 `section`。
点击瞬间 `section` 已是新值，正在退出的旧槽位因此被画成新页面——症状与上一轮完全相同。

修法是在分支开头取 `val page = current.page`，顶栏副标题、滚动重置与内层 `when` 全部读它；
写操作（`onClick` 里的 `section = …`）保持不动。**这条值得记住：
`AnimatedContent` 的内容槽里不许读与 targetState 同步变化的任何外部状态，
包括看起来「只是个枚举」的那种。**

### 37.2 附件来源由 Intent 动作决定

对照两种契约在小米上的实际表现：

| 契约 | 动作 | 表现 |
| --- | --- | --- |
| `OpenMultipleDocuments` | `ACTION_OPEN_DOCUMENT` | 系统文档提供器接管，固定进自带文件管理器 |
| `GetMultipleContent`（新增） | `ACTION_GET_CONTENT` | 先让用户挑应用，可列出第三方文件管理器、WPS、相册 |

官方网页是普通 `<input type="file">`，Chrome 内部同样走 `ACTION_GET_CONTENT`，
因此这也是与网页版对齐的做法。代价是每次多一步选来源。
`parseResult` 同时读 `clipData` 与 `data` 并去重：多选的结果在前者，单选的后者。
不申请持久 URI 权限，文件只用当次上传。

### 37.3 图标换成 lucide

官方 Console 的 `ui-vendor` 打包产物里 `lucide-react` 出现 232 次，据此把图标集定为 lucide。
一次性脚本从 `lucide-static@0.400.0` 取 SVG，把
`path / circle / rect / line / polyline / polygon` 转成等价 path 数据，
统一按 24×24 视口、2px 线宽、圆头圆角构建 `QwenIcons`。脚本不入仓库。

转换阶段踩了四处，都会静默出错而不是报错：

1. `star` / `clock` / `code` 的 `points` 用 `re.split` 会切出空串，配对时 IndexError。
2. `more-vertical`、`alert-triangle` 在 0.400.0 已改名 `ellipsis-vertical`、`triangle-alert`，
   按旧名取会 404。
3. 圆角矩形的路径顺序一开始写错，画出来的 `server`、`folder` 是塌的。正确的顺序是
   上边 → 右上角弧 → 右边 → 右下角弧 → 下边 → 左下角弧 → 左边 → 左上角弧 → 闭合。
4. `package` 是 Kotlin 关键字，属性名只能用 `packageIcon`。

替换按映射表批量做：52 个名字，正则替换
`Icons.Default / Outlined / Filled / AutoMirrored.*`，同时删掉 Material 图标的 import，
21 个文件受影响。`material-icons-extended` 依赖暂未移除，等确认无遗漏用法后再处理。

**第一版在真机上被发现形状是坏的。** 用户截图圈出 `server`（两条塌陷横杠）、
`user`（只有一段弧）、`info`（半圆加竖线）、`bot`、`archive`、`share`——都是能编译、
能显示、但形状不对的图标。根因是两条转换公式同时写错：

- **`circle` 的起点用了 `cx`，应为 `cx - r`。** 于是 `info`（r=10）画出来是
  `M12 2a10 10 0 1 0 20 0`，从圆心起步、向右画出直径长度的弧，实际落点跑到画布外。
- **圆角矩形的四段弧顺序错位。** 模板里 `%s` 的个数与传入参数的个数对不上，
  生成出 `M4 2h16a2 2 0 0 1 2 2v4h16…` 这种缺角的路径。

教训不是「再仔细点」，而是**这类转换必须有渲染层面的验证**。只编译、只跑单测都发现不了：
`ImageVector` 只要 path 非空就是「合法」的，形状错了任何断言都不会失败。

补的验证方法是把原始 SVG 与转换后的 path 并排渲染成位图再逐像素比：
生成一张 HTML（绝对定位，两列各 64×64），用 `chrome --headless=new --screenshot` 截图，
再用一个手写 PNG 解码脚本把两块区域二值化后算墨迹 IoU。修正后的 59 个图标
IoU 全部 ≥ 0.986，修前是 0。这个脚本同样是一次性的，不入仓库，
但方法写进了 [ui-guidelines.md](ui-guidelines.md) 9.12，下次换图标集要照做。

Android 侧另外抽了三个有代表性的图标在模拟器上做 ASCII 采样复核
（`server` 双矩形、`user` 圆环加肩膀、`bot` 头加双眼），确认 Compose 的 `PathParser`
对同一份绝对坐标弧命令的解释与浏览器一致。

### 37.4 选择文本前询问原文

触摸选中的只是屏幕上渲染出来的文字：公式是二维排版、表格被重画、图片只剩占位，
拖动选到的字符与原文并非一一对应。因此点「选择文本」先问一次：
「显示」打开原文页、「不显示」进原有选择态、「取消」什么都不做。

对话框是新写的 `ChoiceDialog`，不是 `DestructiveActionDialog`：后者要逐条列影响范围，
这里只是几个并列的无破坏性分叉。三个按钮同排，因为「不显示」与「取消」若分列两端，
读起来会像两种不同程度的确认。

原文页 `MessageSourceScreen` 只做一件事：等宽铺开源字符串、可拖动选中、可整条复制。
不做 Markdown 渲染是刻意的——这里要给的就是标记本身。

### 37.5 空态首页与默认头像

空态按官方网页的形状做：56dp 智能体头像、标题「你好，我今天能帮你做什么？」、
副标题「我是一个智能助手，可以帮助你解答问题。」、两张预设卡片。
预设点击后先弹「发送这条消息？」：触屏误触成本高，而且这两条会真的建立一个对话。

智能体头像的回落分支改为内置的 `agent_default.png`；用户侧仍用首字 + 底色，
因为自己的头像缺省时，一个通用标志不如首字好辨认「哪个是我」。

### 37.6 引导式第 1 步与顶栏副标题

顶栏原先写 `if (addMode == null) "添加实例" else "添加实例 · 引导式"`，
填表式也被标成引导式，改成 `when` 三档。引导式第 1 步原先把地址、名称、别名
平铺成三个独立输入框，改成与填表式同构：名称在上、地址与别名收在同一个灰框里。
首次启动复用同一个 `InstanceWizard`，两处同时生效。

- 图标集 → [ui-guidelines.md](ui-guidelines.md) 9.12

## 38、v0.1.1 发版前的入库审计（2026-11-02）

### 38.1 不该进仓库的三类东西

**口令。** `AGENTS.md` 第 2.1 节写着 LXC 容器两个账户的口令与用户名同值。

**真实局域网地址回流。** 第 27 节已把全仓的 `192.168.10.204` 统一换成
`192.168.1.10`，本轮新写的 devlog 第 34 节又写回了一次原地址。

**没人调用的代码。** `data/remote/DownloadClient.kt`（229 行）与

## 39、正文裸上下标的判据收口（2026-11-03）

用户实机反馈：聊天页面里 `P_A、P_B` 的下划线被吞掉、字母掉到基线以下，读起来像排版坏了；
同一屏还挂着一条「MiMark: LaTeX 渲染失败：`got 'R' (in "\mathbb{R}")`」的横幅。

### 39.1 先确认这条报错出自哪套渲染

MiMark 在本仓库不存在，逐项核查如下。结论：那条横幅不是这份代码产生的。

| 检查 | 结果 |
| --- | --- |
| `app/build.gradle.kts` 依赖表 | 无 MiMark，本地 aar 只有 `sherpa-onnx-1.13.3.aar` |
| `git log --all -S "MiMark"`、`-S "MergedChatRepository"` | 各 0 命中 |
| 分支与远端 | 只有 master；`origin/master` 与本地 `a9482ed` 同一提交；`git worktree list` 只有主目录 |
| 本机 11-02 的 `app-arm64-v8a-release.apk` | dex 里 `MiMark` 出现 0 次 |
| 手机（Redmi 24117RK2CC，网络 adb） | 第三方包只有 `io.qwenpaw.node`，`versionName=0.1.0`；拉下 `base.apk` 后 13 个 dex 全部 0 次 |
| `~/.gradle`、`~/.m2` | 无 mimark 产物 |
| LXC 容器 `qp-test-prerelease`（2.3.0b2）的 `console/assets` | `MiMark` 与 `MergedChatRepository` 各 0 命中 |
| `~/.trae-cn/worktrees/QwenPaw Node` | 空目录 |

用户提出的怀疑是「项目目录从 `QwenPaw Node` 改成了 `QwenPaw-Node`，所以看错了仓库」，
这条已排除：旧名对应的 worktree 是空的，全历史也没有 MiMark。
`\mathbb{R}` 在本仓库由 `Latex.kt` 的黑板字母表支持，不会报「渲染失败」。
本轮因此只修本仓库自己那条等价规则——图 1 的症状在这里可复现，且原因就在源码里。

### 39.2 原判据为什么会误伤

`isWordInternalUnderscore` 用 `prev.isLetterOrDigit()` 判「词内」，把两类东西放了进来。
一是 `P_A`、`msg_id` 这类载荷为字母的下划线：`readBareScript` 只吃紧跟的一个字符，
于是 `user_name` 变成「user + 下标 n + ame」，标识符被从中间拆断；表格单元格走同一个
`inline()`，`msg_id` 表头同样中招。二是汉字——`isLetterOrDigit()` 对中文为真，
「第_1_章」也进这条分支。`^` 更宽，压根没有判据，`[^1]` 这类脚注标记直接排成上标。

### 39.3 只收判据会把问题变严重，两条必须同轮改

第一版只改判据（标记前须为 ASCII 字母数字、标记后须为数字或 `{`），单测里
`第_1_章` 那条失败：下标判据挡住了，落空的 `_` 掉进行内强调分支，而该分支的闭合位置
是「行内下一个 `_`」，于是字母「1」被排成斜体。顺着这条线索手推 `P_A、P_B`，
结果是在这个判据收紧之后，第一个 `_` 会与远处那个配上，把「A、P」整段斜体——
比原症状更难读。因此 `*` 与 `_` 的 emphasis 分支拆成两条，`_` 改走
`closingUnderscoreEmphasis` 的四条边界。

边界里的「词字符」按 Unicode 判定而不是 ASCII，这一点同样是单测逼出来的：
沿用 ASCII 时「这是_重点_内容」会成对斜体、「第_1_章」仍被吞掉一对下划线，
与 CommonMark 和 GitHub 的处理都不一致。改为 Unicode 后汉字算词字符，
夹在中文里的 `_…_` 一律保持原文，`_斜体_`、`见 _重点_ 内容` 照常成对。

`MarkdownPlainText`（「复制」按钮走的路径）里那条 `_` 正则也按 ASCII 写，
`(?<![\w])` 不含汉字，因此「附录_ 与 表_」会吃掉中间一段。改成 `[\p{L}\p{N}_]`
与显示侧对齐——两处规则必须同写，否则界面上没有斜体、复制出的文本却少一对下划线。

### 39.4 判据落在被标注的一侧，`C^2` 因此仍然排上标

想连 `C^2` 一起放过，就得判主体是不是「像变量的单字母」，而主体判据一视同仁会让
`x^2`、`2^10` 同时失效——这两个恰是模型最常写的裸指数。取舍结果是只判被标注的一侧：
`P_A` 因载荷是字母回到原文，`C^2` 因载荷是数字仍排上标。
`MarkdownScriptTest` 专门留一条 `C^2` 断言把这个后果钉住，免得下一轮当 bug 改掉。

### 39.5 数字成串整段收进下标

`readBareScript` 原先只取一个字符，`x_12` 排成「₁2」。判据收窄后载荷只剩数字，
于是顺手让连续数字整段消费——多一条断言，不多一条分支。花括号分支不变，
`P_{A}` 视为作者的显式意图，仍排下标，与 `P_A` 表现不一致是有意保留的。

### 39.6 已知限制与本轮验证

- 上下标只做基线偏移、不缩字号，`H_2O` 看起来仍是「大写字掉下去」。
  `SpanStyle` 没有相对字号，要按块级公式的 `0.58` 比例缩小，得把基准 sp 透传进
  `inline()` 与段落/标题/列表/引用/表格五处调用，属于独立一轮，本轮不塞。
  口径记在 [ui-guidelines.md](ui-guidelines.md) 8.7；条目按用户要求登记进
  [待办清单](../待办清单.md) 0.1.3「正文上下标缩字号」，与阶段 1 同轮做。该文件原本只收
  「服务端已提供、客户端未接」的条目，本项属渲染层欠项，因此在条目末尾写明来源与例外。
- 439 个单测通过（第 38 节记的是 432）。本轮新增 7 条断言型用例，
  另有 1 条原断言翻转（`a_i` 从「排下标」改为「保持原文」）。
- 未跑模拟器验收：`scripts/e2e_acceptance.sh` 的 A1–A6 不覆盖 Markdown 路径，

## 40、待办清单改为版本制（2026-11-03）

本轮只改文档，不动代码。上一轮定下「下一轮做完整阶段 1」，用户随即要求先把这个清单
本身改成「一个版本要做什么」的形式，并对小版本细化到 0.2.1、0.3.1 这一级。

### 40.1 阶段制为什么失效

旧文件同时维护两套编号。前半段是「阶段 0–5」加 `0.1`–`2.9` 的子编号，
后半段又按「高优先级 / 中优先级」重排成 `1`–`10`，同一件事写了两遍：
定时任务是 `1.2` 也是编号 `1`，收件箱是 `1.1` 也是编号 `3`，备份是 `2.9` 也是编号 `8`，
检查点、用量统计、技能与 MCP 同理。两处正文并不完全一致——编号 3 的收件箱多了事件结构
与验收，编号 1 的定时任务多了端点表与三种 cron 表达式写法，`1.2` 只有一个审阅锁提醒。
读的人要在两处对照，改的人只改一处就会漂。实测后果已经出现过：
第 39 节登记 `1.6` 时，指向的是一个只在阶段段里存在的编号。

阶段制另有第二层问题：阶段标题只描述难度（「零服务端改动」「中等难度」），
不说明做完能发出什么。用户要的是排期，而排期的最小单位是版本号，不是难度档。

### 40.2 新结构

主结构改为「版本总览表 + 每个版本一节」。总览表四列：版本、主题、包含、前置。
每节固定写「这一版要做什么 / 端点与实测 / 前置 / 验收」，条目只在它要发的那一版里出现。
排期到 0.7.0，插件不占客户端版本号，单列「独立仓库」。

合并处的取舍写进了文件：工具调用控制并入 0.2.0，与定时任务同属「后台长任务」，
且两者都要读 SSE，拆成两版会让同一批端点写两套状态机。大文件通道拆成下载侧
（0.3.0）与上传侧（0.3.1），因为中间隔着整个编辑功能，合在一节里会让前置条件读不清。

### 40.3 搬运与漏项

正文用脚本按锚点整段搬运，不重写端点表与实测数据。这一步出过三类漏项，
都是「看起来完整、实际少了」的那种，记录下来避免下次重犯：

1. **按标题切片会连表头一起切掉。** cron 与工作区两处端点表丢掉了
   `| 方法 | 路径 | 作用 |` 与分隔行，剩下的数据行在 Markdown 里渲染成一段文字。
2. **锚点选在段落中间会漏掉紧随其后的段。** 收件箱丢了 `**实测**…unread_count`
   与 `**事件结构**` 两段，cron 丢了 `**注意**` 整段与 `**涉及层次**`。
3. **用 f-string 拼 Kotlin 代码块会抛 `NameError`。** 代码块里的 `{backup_id}`、
   `{"upload_max_size_mb": null}` 被当成插值，改用占位符替换才通过。

核对口径是逐串比对而不是通读。对端点表取「方法 + 路径」去重后求差集，旧文件 65 行、
新文件 61 行，差集为空——少掉的 4 行是两处重复，不是漏项。对实测串（`Kurikawa_Nana`、
`If-Match`、`Accept-Ranges`、`MiddlewareBase`、`etag=W/`、`upload_max_size_mb`、
`conversation_history_fts`、`Imported cron job`、`22.4 MB` 等）逐个 `grep -cF` 比对两版计数。
这一轮补回的有 `total_prompt_tokens=64085508`、`目标与范围` 的四类分级表
（「明确不做」里「属 C 类改动」的说法依赖它）、以及「不是缺口」这一节的标题。

### 40.4 同步改的引用与数字

`AGENTS.md` 5.4 与 `docs/ui-guidelines.md` 8.7 原先按「第 1.6 项」指这份清单，
改为按版本指（0.1.3「正文上下标缩字号」）。第 39 节正文里的同一处引用一并改，
其余历史节号按 5.2 不追溯。

文件从 713 行变成 815 行，二级标题从 7 个变成 22 个。行数增加主要来自每节固定的
四段结构与总览表；正文事实没有扩写。

### 40.5 剩余风险

排期是估算。文件首段已写明 0.1.3 起「是计划，不是承诺」，发版时若临时调整范围，
同一轮把该节改回，否则 tag 与清单会长期不符——旧文件正是在这种情况下开始漂的。

## 41、插件排期与插件探测（2026-11-03）

用户问两件事：插件工程放在哪、从哪个版本开始做；以及客户端要能检测配套插件，
装没装决定功能是禁用还是换实现。第一节已定在客户端仓库之外，
目录现名为 `QwenPaw-Node-Plugin`，与客户端 `QwenPaw-Node` 平级。

### 41.1 为什么是 0.2.1，而不是 0.1.x 或最后

0.1.3 与 0.1.4 是同一套 Kotlin 工具链的连续两轮，中间插一个 Python 仓库会打断节奏，
且这两版不装插件也做得完。到 0.2.0 发完，客户端已有稳定的 2.5 秒轮询
（`ChatViewModel.POLL_INTERVAL_MS`），插件的事件流才有可替代的对象；
0.1.3 的分页骨架也已落地，检索结果列表可以直接复用。

更关键的是风险暴露的时机：`plugin.json` → `qwenpaw plugin validate` → 容器热加载 →
客户端识别，这条链是两端唯一的接合点，没有编译期检查能拦住不一致。
等到 0.7 才发现契约对不上，返工面比在前面验证一轮大得多。因此 0.2.1 先只做脚手架
与探测契约，不追求功能数量。

`fork` 的转发不随 0.6.0 一起做：它面向 `spawn_subagent(fork=True)`，客户端没有对应界面。

### 41.2 探测规则与三条否决的写法

两个容器都启动后实测（2.2.2.post1 / 2.3.0b2）：

| 端点 | 2.2.2.post1 | 2.3.0b2 |
| --- | --- | --- |
| `GET /api/plugins` | 200 | 200，多 `status` 与 `diagnostics` |
| `GET /api/plugins/{id}/status` | 200 `{id, loaded, enabled, version}` | 200，同上多 `status` |
| `GET /api/plugins/{id}` | 404，路由不存在 | 200 |
| `POST /api/plugins/{id}/enabled` | 不存在 | 存在 |

**否决的写法一：只看 `enabled`。** loader 未初始化时 `list_plugins` 退化为磁盘扫描
（`_list_plugins_from_disk`），返回 `enabled: true, loaded: false`。判据取 `loaded`，
2.3 上再加 `status == "active"`。

**否决的写法二：用 `GET /api/plugins/{id}`。** 2.2 上这条路由并不存在，
拿它做判定会让稳定版上所有插件都显示未安装，而 2.2 正是当前基线。

**否决的写法三：比 `qwenpaw_version`。** 列表响应里没有这个字段——manifest 的版本约束
只在安装校验时由 loader 读取并交给 `PluginApi`，不回传到列表。客户端拿不到兼容区间，
于是把能力自述交给插件自己：新增 `GET /api/plugins/qwenpaw-node-bridge/info`，
返回 `capabilities` 数组，客户端按名字开关功能。这条形状是两端约定的草案，
尚未实现，文档里已写明「草案、未实测」，避免下一轮把它当成既成事实。

### 41.3 禁用态实测，以及为什么不能给「去启用」

禁用插件的方式是把目录改名加 `.disabled`，发现阶段直接跳过
（`plugins/loader.py` 的 `_is_disabled_plugin_dir`）。这一条是从源码读出来的，
没有直接采信，在 `qp-test` 上做了完整验证：

1. `mv clawhub-hub clawhub-hub.disabled` 之后**不重启**，`GET /api/plugins` 仍返回 4 个插件，
   `/status` 仍是 `loaded: true`。已加载的实例在内存里，目录改动不影响本次运行。
2. 重启服务端后列表只剩 3 个，`GET /api/plugins/clawhub-hub/status` 返回
   404 `Plugin 'clawhub-hub' not found.`——与从未安装的表现完全相同。
3. 恢复目录名并重启，确认回到 4 个插件，现场还原。

因此客户端只设「已检测到」与「未检测到」两态。对未检测到的情况给安装指引，
不给「去启用」：2.2 没有 `/{id}/enabled` 这个开关，被禁用的插件在界面上也没有
可恢复的入口，承诺一个做不到的动作比不给承诺更糟。

### 41.4 两类功能的处理

必须插件的能力（检索、`fork` 与 `portability` 转发、离线推送）在未检测到插件时
入口置灰或隐藏，就地写明原因；插件增强的能力（SSE 替代轮询）自动回落，不提示不报错。
回落路径必须先在无插件环境下验证通过，判定逻辑集中在 `PluginProbe` 一处，
页面不自行查插件列表，否则每加一个功能就要再写一遍判定。

### 41.5 收尾

两个容器在测完后都关停，避免长期占用内存（第 1 节的硬约束）。
容器内 `/api/plugins` 的四个 hub 插件与离开时一致。

结论落点：端点形状、判定规则与禁用态表现 → [protocol.md](protocol.md) 第 19 节；
排期与客户端条目的分层 → [待办清单.md](../待办清单.md) 的 0.2.1「配套插件探测」
与「独立仓库」一节的开发排期表。

## 42、插件版本号与探测改由插件自述（2026-11-03）

用户提出两件事：待办清单只按客户端版本排期，看不出「某个功能需要插件做到什么程度」；
以及既然插件能回传版本号，探测是否应当改由插件自己实现。两问都成立，
第二轮据此改了排期表结构与 0.2.1 的探测方案。

### 42.1 插件版本独立编号，不跟客户端同号

第 41 节只写了「从 0.2.1 起并行」，没有给插件版本号，于是排期表里的
「起点 0.2.1」既指客户端版本又指时间点，无法回答「0.2.2 要的插件是哪一版」。

三种编号方式比较过：与客户端同号、只写 capability 不写版本、插件独立语义化版本。
选了第三种。同号的问题在插件侧：客户端不发版时插件就不能发，或者只能越号，
而插件修一个 `snippet()` 的边界缺陷不需要客户端跟着发一版。只写 capability
则回到原状，排期表里看不出进度。独立编号的代价是多一张对照表，
收益是两端可以各自发版，且版本号能出现在设置页与日志里，用户报问题时可直接说版本。

版本号只用于展示与排查，**仍不参与能力判断**——这一点沿用第 41 节否决的写法三，
没有因为现在有版本号就改回「比版本」。

### 42.2 探测改打插件自己的 `/info`

新方案只请求 `GET /api/plugins/qwenpaw-node-bridge/info`：200 视为已检测到，
404 一律视为未检测到，不再查核心的 `/api/plugins` 列表。

这样能省掉第 41 节的两条判定：`enabled` 与 `loaded` 的启动竞态、
以及 2.3 上才有的 `status == "active"`。`/info` 能返回 200 本身证明插件路由挂上了，
证明力比查列表更强——列表里 `loaded: true` 只说明 loader 记住了记录，
不说明该插件的 router 已经注册成功。

**核实过的两件事**（本机 8088，2.2.2.post1，只读）：

1. `GET /api/plugins/qwenpaw-node-bridge/info` → 404 `{"detail":"Not Found"}`，
   不是 SPA 返回的 `index.html`。`_app.py` 的 catch-all 里有
   `if full_path.startswith("api/"): raise HTTPException(404)`，因此客户端可以用
   404 明确判定「未安装」，不必额外判断响应体是不是 HTML。
   `GET /api/plugins/qwenpaw-node-bridge/status` 则是 404 `Plugin 'qwenpaw-node-bridge' not found.`，
   两者都是 404，但 detail 不同，日志里可区分。
2. `auth.py` 的 `_PUBLIC_PATHS` 与 `_PUBLIC_PREFIXES` 都不含 `/api/plugins`。
   开启登录后插件路由需要 token，因此探测只能排在验证与登录之后。
   验证阶段尚无 token，此时若收到 401 应记为「待重探」而不是未安装——
   否则开着鉴权的服务端会永远显示「未装插件」。

### 42.3 插件路由不得与核心路由同名

`plugins/registry.py` 的 `register_http_router` 把插件 prefix 拼成 `/api` + prefix
再挂到 app 上。核心 `plugins.py` 在模块级先注册，插件路由随后插入，
路径相同时命中核心那条。

这一条最初只是读源码的推断，收尾时补了实测。在未装插件的实例上请求同一前缀下的
四个子路径，结果分成两类：

```
/status    → 404 Plugin 'qwenpaw-node-bridge' not found.   参数化 detail，进了核心 router
/files/x   → 404 Plugin 'qwenpaw-node-bridge' not found    同上
/info      → 404 {"detail":"Not Found"}                    通用 404
/search    → 404 {"detail":"Not Found"}                    通用 404
```

前两条连 detail 都带插件 id，说明请求确实被核心 `/{plugin_id}/status` 吃掉了；
后两条没匹配上任何路由。因此 `/status` 与 `/files/**` 不能给插件用。
这条同时说明：**404 仍然能当「未安装」的判据**，但要靠 detail 的形状区分是
「进了核心 router 但插件没装」还是「根本没有这条路由」，两者都不影响探测结论。

### 42.3.1 id 与 prefix 统一为完整名

第一版把插件 id 写作 `qwenpaw-node-bridge`、HTTP 前缀写作 `/plugins/node-bridge`，
两种写法混着用。前缀一旦真的按 id 注册，端点会变成
`/api/plugins/qwenpaw-node-bridge/info`，与上面的实测路径才对得上。
两段字符串现已统一：id 与 prefix 都用 `qwenpaw-node-bridge`，
文档里不再出现 `/plugins/node-bridge` 这一缩写形式。

### 42.4 新增 0.2.2，SSE 从 0.4.x 提前

第 41 节把 SSE 排在 0.4.x，理由是「0.2.0 发完才有稳定的轮询可替代」。
但按那个理由，0.2.0 一发完条件就满足了，继续等三个版本只是让插件装上去却用不上。
新增 0.2.2「插件能力接入」，包含会话检索与 SSE 两件，都需要插件先就位。

**版本号没有重编**：0.3.0 及之后的号保持原样，只是发布顺序顺延到 0.2.2 之后。

## 43、阶段 1 起步与主体合并发版（2026-11-03）

### 43.1 两版合一的理由

`待办清单.md` 把 0.1.3（分页骨架、频道筛选、斜杠补全、正文上下标字号）与
0.1.4（收件箱、工具开关、环境变量、后台策略）排成两版，理由是后者的收件箱依赖前者的分页骨架。
分开做的问题是分页骨架这一版没有任何真实调用方：11-01 写过的 `ui/common/Paging.kt` 就是因为
无调用方无单测，在第 38 节审计时被删掉。只发一版「零证明力」的骨架，等于把同一个风险再走一遍。

合并后分页骨架的第一批调用方与它同轮落地，`PagingTest` 的四种情形（首页拼接、翻页续接、
空页结束、重复游标）由收件箱的真实字段形状驱动。代价是改动面横跨数据层、列表页、输入框、
三个新页面与 Markdown 渲染，构建轮次变多；这一轮按「纯 JVM → 数据层 → 列表页 → 输入框 →
新页面 → 发版」的顺序串行推进，每个子步都能单独跑通单测。

合并的另一个后果是版本号：0.1.3 未单独发布，因此 `versionCode` 从 3 直接到 4，
`versionName` 为 `0.1.4`。`CHANGELOG.md` 只有一个 `## v0.1.4` 小节——Release 正文取第一个
`##` 小节并与 tag 比对，出现 `## v0.1.3` 会让 CI 中止。

### 43.2 待办清单的前提被字节码推翻

0.1.3 的上下标条目写明「基准从 `MaterialTheme.typography` 取，不要读 `LocalTextStyle`，
因为全仓没有 `ProvideTextStyle`，运行时它必然是 `Unspecified`」。这条前提不成立。

`material3-android:1.3.1` 的 `MaterialThemeKt$MaterialTheme$1` 字节码里依次是：

```
41: invokevirtual  androidx/compose/material3/Typography.getBodyLarge()
50: invokestatic   androidx/compose/material3/TextKt.ProvideTextStyle(...)
```

`MaterialTheme` 自己就提供了 `LocalTextStyle = typography.bodyLarge`。而 `ChatFontScale`
内部又套了一层 `MaterialTheme(typography = scaled)`，所以该作用域内的 `LocalTextStyle`
是**已乘过 chatScale 的 bodyLarge**，与段落实际渲染字号严格一致。

原来的判断来自一次源码搜索：全仓确实没有 `ProvideTextStyle`，但提供方在依赖库里，
搜索覆盖不到。结论：段落基准直接取 `MaterialTheme.typography.bodyLarge.fontSize`，
不需要给 `MarkdownText` 加参数，也不需要改 `MessageBubble` 的两处调用点。
为了把隐式依赖变显式，段落、列表、引用三处 `Text` 补上了 `style = bodyLarge`。

### 43.3 分页骨架的两处实现取舍

**并发护栏用 `tryLock` 而不是 `withLock`。** 第一版写成 `gate.withLock`，第二次并发调用会
排队等前一次结束再执行，等于同一列表连发两次请求。测试用例 `concurrent loadNext is ignored`
要求第二次当场返回 `Busy`，才发现这个写法与语义不符。

**空响应归为结束，不当作错误。** `QwenPawApi.decode` 对空 body 抛 `ApiException(204)`，
真正的 HTTP 204 与「200 空 body」在这一层已经无法区分。分页把 204 归为「空页 = 结束」，
因为干净实例上的「0 条事件」不该弹一条「服务端返回了空响应」。其余异常照原样上抛，
失败时 `items`/`hasMore`/`next` 都不改动，调用方可以直接重试。

**重复游标时保留本页已取到的条目。** 游标不推进是服务端缺陷，但已经到货的数据没有理由丢弃；
代价是服务端若重复返回同一批数据，客户端会出现重复条目。这一取舍在 0.1.4 的收件箱上没有触发
（offset 形态靠 `total` 判断），等有真实重复行为时再收紧。

### 43.4 频道筛选最容易踩的坑

候选值必须从**未过滤**的完整列表算。若从切片结果算，选中某个频道后候选立刻退化成它自己，
控件随之消失，用户被锁死在该频道里。`ChannelFilterTest` 里
`candidates do not collapse when a channel is selected` 专门守这一条。

状态放界面本地 `remember`，不持久化：换服务器或换智能体后，记住的频道在新数据里可能根本不存在，
用户进入列表会看到空页却找不到原因。为此补了「选中值不在候选内即回落到全部」的钳制。

管线次序是「先按频道切片，再在切片里搜索」。反过来搜索会跨频道命中，而列表头显示的是频道切片。

### 43.5 斜杠候选放在输入条内部

候选列表内嵌在 `ChatInputBar` 的 `Column` 里，不用 `Popup`。那个 `Column` 已经挂了
`navigationBars ∪ ime` 的内边距，候选自然被键盘顶上去，不需要自己算浮层位置；
`Popup` 开新窗口后要么抢焦点导致键盘收起，要么点到窗口外无法穿透。

`ChatScreen` 的 `bottomBar` 本来就同时容纳 `ApprovalBanner`、`ErrorBar`、`VoiceSheet`，
高度随状态变化是这个界面的常态，内嵌不会引入新的布局问题。

触发判据与服务端 `SlashCommandRegistry.resolve` 对齐：只有整条草稿以 `/` 开头、
且其后不含空白时才是一次命令输入。点击候选写回 `"/name "`（带尾随空格），
下一次判据立刻返回 `null`，候选自动收起。

请求失败静默：`refreshCommands` 的失败分支不写 `state.error`，这是 `ChatViewModel` 里唯一的例外。
补全缺失不影响手打命令，弹一条错误只会打断正在输入的人。

### 43.6 实测才发现的两个 `null` 形状

服务端 2.2.2.post1 的 `GET /api/tools` 有两处会让整份响应解析失败：

1. 无配置项的工具返回 `"config_fields": null` 与 `"config_values": null`，不是空数组/空对象。
2. 非 select 类型的配置字段返回 `"options": null`。

DTO 里把它们声明成非空集合后，页面上表现为「没有可用的工具」——一个字段就能让整份列表反序列化失败，
而从响应里看不出任何异常。改为可空并补了两条单测钉住形状。

同时修了空态的语义：`tools.isEmpty()` 且 `error != null` 时显示「加载失败：…」而不是「没有可用的工具」，
后者会让用户以为服务端确实一个工具都没装。

### 43.7 `AppViewModel` 构造期访问未初始化字段

`AppViewModel` 的 `init` 里调 `bind`，而 `bind` 需要清空收件箱与三张表单的状态。
把这两个对象写成普通 `val` 后，debug 包首次启动直接崩溃：

```
NullPointerException: Attempt to invoke virtual method 'void ...InboxViewModel.clear()'
on a null object reference
```

kotlin 的属性按声明顺序初始化，`init` 先于它们执行。改成 `by lazy` 同样不行：
lazy 的委托字段自己也是属性，在这个时点仍是 null。最终用显式可空字段加 getter 惰性创建，
并在 `bind` 里只清「真的换过实例/智能体」的那一次——首次绑定没有旧数据可清，
也不必为此提前创建两个 ViewModel。

### 43.8 收件箱与列表页角标

收件箱的 `created_at` 是浮点秒（服务端 `time.time()`），不是 ISO 字符串，
因此 `TimeLabels` 加了一个走 `Instant.ofEpochMilli` 的入口，时区作为参数显式传入，
单测钉住东八区输出。金额、时间的断言依赖默认时区是本地通过、CI 失败的典型原因。

未读数由服务端在每页查询时一并返回，客户端不在本地推算。列表页的入口角标原本只在
进过收件箱后才有值，改为落到 `Screen.LIST` 时拉一次。代价是一页事件（30 条）。

### 43.9 验证范围

单测 497 个全通过，新增覆盖：分页 11 例、频道筛选 6 例、斜杠 8 例 + API 3 例、
上下标字号 5 例、收件箱时间格式 2 例、三张表单端点与遮罩 12 例。

收件箱的事件列表、全部已读、删除与列表页角标；工具开关往返、后台策略往返、

## 44、v0.1.4 收尾：中文文案与工具行形态（2026-11-03）

### 44.1 中文文案只能从 Console 打包产物里取

服务端没有 i18n 接口。`GET /api/workspace/commands/available` 的响应里
`description` 就是英文原句，实测 35 条命令中只有 11 条带描述；
`GET /api/tools` 的 33 个工具同样只有英文 `description`。

中文译文只存在于 Console 前端打包产物：
`qwenpaw/console/assets/zh-*.js`。其中 `commands:{...}` 给出 11 条命令描述，
`catalog:{...}` 给出 33 条工具名与描述（形如 `read_file:{name:"读取文件",description:"…"}`），
另有 `groups:{files, web, media, agents, runtime, migration, other}` 的工具分组译名。

浏览器端的资源客户端取不到，因此译文**静态内置在 `ui/LocalCopy.kt`**。
这是查表而非运行时合并：服务端新增命令或工具时查不到就回退到服务端原文，界面不会开天窗。
工具侧有两条差异：`view_audio` 在接口里有、语言包里没有，按 `view_video` 的句式补了一条；
`enhance_and_generate_image` 在语言包里有、当前版本接口未下发，保留无害。

命令侧另有一处译名冲突：Console 把 `conversation` 分类译作「会话内容」，
`ui-guidelines.md` §9.11 要求界面一律用「对话」，客户端取后者。

### 44.2 候选列表用黑名单而不是白名单

只给「面向用户的命令」写白名单看似更省事，但服务端还会注册插件与技能提供的命令——
白名单会把它们一并挡掉，表现为装了插件却看不到它的斜杠命令。
因此反过来只列内部命令（17 条：对话侧的程序化命令、daemon 子命令、`cron-*`），
命中即从候选里剔除；未收录的命令一律保留。

过滤必须排在前缀匹配之前。反过来写的话，打 `/` 时的全量与打 `/d` 后的结果来自两个不同的集合，
用户会看到「先出现、后消失」的条目。已敲完的完整命令名仍能执行，只是不再提示。

### 44.3 工具行：从两行开关到单行圆片

原实现是「启用」开关一行、启用后再挂一行「异步执行」开关。
两个 `Switch` 外观完全相同且上下相邻，看起来像同一个设置被重复了一次。

改版后每个工具占一行：左侧名称与中文描述，右侧是「同步 / 异步」两段圆片与启用开关。
第一版在描述下面又加了一行英文工具名（便于和服务端字段对账），模拟器实测每行从 3 行文字
堆到 4 行，比原来的两行开关还高，与「更清爽」的目标相反，因此删掉。

两处实现细节值得记下：

1. **整行不能挂 `clickable`。** 行内已有圆片与开关两个可点区域，
   再给整行加点击后，点圆片时事件会同时落到两处，异步设置会被启用开关顺手改掉。
   关闭态的点击区域靠开关本身。
2. **圆片用 `selectable` 而非 `clickable`。** `clickable` 生成的语义节点不带选中态，
   `uiautomator dump` 里 `checked` 与 `selected` 都是 `false`，读屏也念不出当前选的是哪一个。
   改成 `selectable(selected, role = Role.RadioButton)` 后节点才带状态。

圆片只在工具启用时出现，与「关掉的工具不会被执行」一致。实测关闭工具后该行圆片消失
（radio 节点 20 → 18），行随之上移。

### 44.4 新增环境变量复用 PATCH 的合并语义

服务端没有 `POST /api/envs`。新增走 `PATCH /api/envs`：`store.py` 的 `update_env_vars`
是 `{**old, **updates}`，提交一个此前不存在的 key 即等于创建，未提交的已有项不受影响，
响应返回合并后的全量列表。客户端已有的 `saveEnvs(Map)` 直接可用，不必加接口方法。

2.2.2.post1 上实测的四条响应：

| 请求体 | 结果 |
| --- | --- |
| `{"QA_PROBE_VAR":"probe-1"}` | 200，返回全量列表 |
| `{"qa_probe_var":"x"}` | 400 `Environment variable names conflict: QA_PROBE_VAR, qa_probe_var` |
| `{"1BAD":"x"}` | 400 `Invalid environment variable name: 1BAD` |
| `{"qwenpaw_x":"y"}` | 400 `QwenPaw environment variable must be uppercase: qwenpaw_x` |
| `{"QWENPAW_LLM_MAX_RETRIES":"5"}` | 400 `Environment variable is read-only: …` |

本地校验与之逐条对应，但**只读判定排在重名判定之前**。
`catalog` 列出全部 17 个内置项（含未配置的），先查重会让只读项得到「已存在」这句无用提示，
用户看不出它其实是被服务端锁住的。与已有项比对按 `uppercase()`，
服务端就是大小写不敏感查重的。

**未配置的内置可写项允许新增。** 这类项在 `catalog` 里有、在 `vars` 里没有，
「新增」是覆盖其默认值的唯一入口；把它们当成重名挡掉，那两个 `hot_runtime`
变量就永远只能停在默认值。已配置的内置项仍按重名拦下，应当去编辑原值。

界面入口放在已配置卡片内部、列表最后一项之后，与「添加实例」同一写法。
**空列表时也要有入口**——一个变量都没有的实例，这是唯一的添加路径。

### 44.5 模拟器启动失败：蓝牙模拟器阻塞

本轮模拟器连续六次卡在 QEMU 初始化，日志报
`detected a hanging thread 'QEMU2 CPU0 thread'. No response for ~19s`，
进程随后在 `-gpu off`、`-no-snapshot`、`-wipe-data` 下均以段错误退出。

排查过程与结论：

- `emulator -accel-check` 报 KVM 可用，`/dev/kvm` 可读写。
- 卡住期间 `lsmod` 里 `kvm` 的引用计数为 0，说明虚拟机根本没有开始执行；
  抓 `/proc/<pid>/task/*/wchan`，CPU 线程停在 `futex_wait_queue`，不是缺页或 IO。
- `-accel off`（纯 TCG 软件模拟）同样卡住，**排除 KVM**。
- 日志末尾的 `Unable to connect to packet streamer, no bluetooth emulation available`
  是唯一指向具体子系统的线索；`netsim_stderr.log` 显示
  `DeviceActor: Startup timeout reached (no devices connected), initiating shutdown`。
- 加 `-feature -BluetoothEmulation` 后一次启动成功，59 秒内 boot 完成。

**这台机器此后启动模拟器必须带 `-feature -BluetoothEmulation`**，
否则会误判成 AVD 损坏而反复擦除数据。AGENTS.md 第 3.1 节的启动命令已按此更新。

期间还有一次干扰：19:03 的 `app.slice` 被 OOM killer 杀掉，当时 Gradle daemon
与模拟器同时在跑。按第 1 节的约束，构建与模拟器应当串行。

### 44.6 验证范围与未覆盖项

单测 518 个全通过（54 个测试文件），本轮新增 21 例：
中文命令表 5 例、工具表 4 例、新增变量校验 9 例、候选过滤 3 例。

模拟器（qp35 + 容器 `10.10.0.211:8088`）上验证了 debug 包：

## 附录：几条反复起作用的原则

1. **先测量，再优化。** 本项目代价最大的教训是：四个「看起来很像」的假设全部被实测推翻，
   真正原因是构建类型。
2. **先核实服务端，再写计划。** 端点形状、是否存在 summary 字段、
   字段名是 `image_url` 还是 `source.url`，都依靠阅读源码与实测确认，不依赖文档推演。
3. **坐标从 `uiautomator dump` 动态获取。** 凭截图目测点击会落空；
   语音按钮那次排查了很久的「假 bug」，实际原因是点击坐标错误。
4. **跨版本的数字要重新取。** 体积、单测数、APK 大小都曾出错。
5. **守住资源约束。** `free -h`、构建、收尾关进程，几乎每轮都执行。
6. **区分过程与结论。** 对话记录是过程，项目文档是结论。
   不要把前者当作后者修改，也不要把后者的严谨程度套用到前者。
