## 一、立项与可行性（2026-10-25）

起点是一个可行性问题：QwenPaw 是否已有 Android 客户端，若没有，做到「该有的都有」的难度如何。

此前的调研已经确认两件事：官方与社区都没有 Android 客户端；QwenPaw 使用纯 REST + SSE，
不像 OpenClaw 那样需要 WS 网关与节点能力协商，因此工程量低一个量级。

本轮进一步确认 L2 的可行性，结论如下：

- L2 所需能力服务端基本都已具备，**不需要改动 QwenPaw 源码**，这是项目能够成立的前提。
- 有两项需要重新定义而不是直接实现：**离线自动补发**（QwenPaw 没有 outbox 概念）与
  **实时推送**（没有推送通道，Console 自身也是轮询）。
- 有一个前置问题必须先定：**直连还是代理**。QwenPaw 的鉴权是可选的，
  直连局域网地址是最省事的路径。

**项目范围在本轮即已固定**，此后未再变更：

| 项 | 决定 |
| --- | --- |
| 目标 | 只做 L1 + L2，不做 L3 管理面 |
| 连接 | 直连，不做代理层 |
| 自动补发 | 不做，仅保留草稿箱与手动重试 |
| 实时推送 | 不做，审批走 2.5s 轮询 |
| Mermaid | 不做，降级为可复制源码 |
| 构建方案 | 采用当时最新（Kotlin 2.1 / AGP 8.7.3 / compileSdk 35） |
| 测试深度 | C 级（功能可用且关键路径通过验收） |

在项目开始阶段就把「不做什么」固定下来，后续节省了大量反复讨论。
[protocol.md](protocol.md) 第十三节的「已知取舍」正是这一轮的产物。

**环境**：用户要求安装 javac 与 Android 开发环境，并指定使用 **redroid（Android 12）**。

## 二、环境搭建与 L1+L2 首版（2026-10-25）

用户离开前留言：环境弄好后先做一份开发计划，然后直接开始。

### 2.1 redroid 未能启动

依次尝试了 `docker.1ms.run`、`daocloud`、`1panel`、`rat.dev` 等镜像源，
`redroid/redroid:12.0.0_64only-latest` 全部拉取失败，表现为无进度或鉴权返回 401。

最终改用本机 KVM 与 Android 15 模拟器（AVD `qp35`）完成 C 级测试。
binder 模块已通过 `modprobe` 加载，用户后续自行拉取 redroid 时环境是通的。

### 2.2 首版交付

约 4600 行 Kotlin，分层为 `data/`（API、SSE、Room）、`ui/chat/`、`ui/settings/`。
核心文件：

- `QwenPawApi.kt`：auth、version、agents、chats、console、approval 全套端点
- `ChatStreamClient.kt`：SSE 长连接，支持 `reconnect: true`
- `ChatEventParser.kt` / `StreamAccumulator.kt`：把增量帧折叠为消息
- `ChatViewModel.kt`：发送、停止、重连、审批轮询、草稿
- `MarkdownText.kt`：轻量 Markdown 渲染器，覆盖表格、代码块、行内样式
- `InstanceStore.kt`：多实例管理，token 使用 `EncryptedSharedPreferences`
- `AppDatabase.kt`：草稿与历史缓存

### 2.3 一处测试基础设施的妥协

Compose 语义树在无头模拟器上不稳定：由 `createAndroidComposeRule` 托管的 UI 测试
反复出现「Compose 层级未附着」，而应用本身运行完全正常。

因此设备端测试收敛为验证「Activity 能启动、内容视图真实渲染」，
界面细节验收改由 adb 截图脚本承担。这是测试基础设施的限制，不是功能缺陷。

这一妥协直接影响了后续策略：**能覆盖的逻辑一律写成 JVM 单测**，设备端只做冒烟。

**结果**：50 个 JVM 单测全部通过，仪器化冒烟测试 1 个通过。

## 三、资源事故（2026-10-25）

### 3.1 现象

用户报障：整个 GNOME 桌面失去响应，内存与 swap 接近耗尽。

### 3.2 原因

当时连续执行了 `./gradlew` 全量构建与 `connectedDebugAndroidTest`，
并与设备测试、模拟器、Gradle daemon、Kotlin daemon 叠加：

| 进程 | 内存占用 |
| --- | --- |
| `qemu-system-x86_64`（模拟器 qp35，已运行 3 小时） | 3.6 GB |
| Gradle daemon（`-Xmx3072m`） | 2.8 GB |
| Kotlin 编译 daemon（`-Xmx3072m`） | 1.1 GB |

三者合计超过 7.5G，加上桌面环境自身（gnome-shell 372M、壁纸渲染 213M），
8G 的 swap 被完全占满。**gnome-shell 卡住的原因是 swap thrash，而非 shell 自身的问题。**

更无谓的是，那次设备端测试本身也失败了（`INSTRUMENTATION_FAILED`，测试 APK 未安装成功），
内存被消耗却没有产生任何结果。

### 3.3 教训固化

用户要求把这些约束写入 agent 约定文件，重点关注编译与构建环节的资源占用。
由此形成 [AGENTS.md](../AGENTS.md) 第一节的硬约束，核心几条：

- 构建与设备测试**不连跑**，逐个执行
- 动手前先 `free -h`，可用内存低于 3 GB 时先关闭进程
- 用完即关：`gradlew --stop` / `pkill -f KotlinCompileDaemon` / `adb emu kill`
- 模拟器内存固定 2048 MB，不加
- 优先增量构建（`installDebug` / `testDebugUnitTest`），不使用 `gradlew build`
- 单测优先于设备测试

此后每一轮重活之前都会执行 `free -h`，也确实多次拦住了「模拟器与构建同时运行」的做法。

## 四、真机验收（2026-10-25）

模拟器操作繁琐，用户提供了真机 `192.168.1.20:5555`（LM-G820N，Android 12，arm64），
可通过 `ssh lg` 免密登录 Termux，adb 走 TCP 5555，锁屏密码已关闭。

### 4.1 真机的坑（均已写入 AGENTS.md）

- **Termux 保活 Magisk 模块**会定期把 Termux 拉到前台。看到界面切到 Termux 不是应用崩溃，
  重新执行 `am start` 即可。用户提前说明了这一点，避免误判。
- **中文输入法把 `.` 与 `:` 打成全角**（`。`、`：`），`adb shell input text` 输入地址会变形。
  应用侧后来在 `normalizeBaseUrl` 中做了全角到半角的折叠。
- 输入框获得焦点后键盘会挡住按钮，点击前需先 `input keyevent 4` 收起键盘。
- 屏幕会自动息屏，且偶发**唤醒无效**（`mWakefulness=Asleep` 持续，`input keyevent 26/82` 均无效）。
  此时应通过 `pidof` 与 `logcat -b crash` 确认进程存活且无崩溃，而不是当作应用问题排查。

### 4.2 A6 断网场景

用户询问 A6 断网场景应当如何操作，并贴出了 `uname` 输出。

由此发现**手机具备 root（Magisk）**：直接 `adb shell` 得到的是 uid=2000，
但 `su -c` 可以取得 uid=0。此前判断「真机没有 root」是错的。

脚本随后改为自动探测三种提权方式（已 adb root、`adb root` 成功、su 免密），
并依据 `HOST` 中的端口封闭网络，不再写死 8088。

需要留意的边界：封闭的是服务端端口 8088，不是 adb 使用的 5555。
误封 5555 会直接断开 adb 连接。

### 4.3 验收结果

A1–A6 全部通过：审批卡片弹出与回传、图片上传、断线重连接回运行中的输出、
停止后服务端回到 idle、多实例隔离、断网中文提示与草稿保留及重试成功。

## 五、v0.1.0 打版（2026-10-26）

用户询问应当如何选定版本号。

最终选 **v0.1.0**。理由有三：代码中的 `versionName` 已经是 `"0.1.0"`，标签与代码一致，
无需改动；`0.x` 恰好表达「可用但功能未堆满、行为可能变化」的语义；
`versionCode` 保持为 `1`，因为它只是一个必须单调递增的整数，正式对外分发前不必改动。

采用**附注 tag**，使 `git show v0.1.0` 能够看到版本说明，指向 `18f3df1`：

```
18f3df1  (tag: v0.1.0)  chore: 移除零引用依赖与未接线的死代码
4e7bce9                 feat: QwenPaw Node Android 客户端首个可用版本
```

当时 release APK 仅 **1.5MB**，因为尚未接入 sherpa-onnx。
接入语音引擎后体积增长到 23MB，这个数字后来在文档中出过一次错（见第十五节）。

## 六、UI 重做（2026-10-26）

用户的意见是前端观感不佳，建议参考 openclaw 的安卓客户端。

### 6.1 诊断

问题定位在 `Theme.kt`：使用的是 **Material3 默认紫色动态配色**
（`#6D3FA8` 紫、`#EADDFF` 淡紫），并且部分颜色手填、部分保留默认值，
结果是「能运行但缺乏设计」。

同时澄清了一处信息：OpenClaw 的官方安卓包名为 `ai.openclaw.app`，
并不存在名为「OpenClaw Node」的官方客户端。

### 6.2 正解：采用 QwenPaw 自身的视觉 token

颜色从 QwenPaw Console 实测提取，而非照抄 OpenClaw：

| 用途 | 浅色 | 深色 |
| --- | --- | --- |
| 主色（橙） | `#FF7F16` | 同 |
| 主色文字 | `#BD5100` | `#FF9A47` |
| 页面底 | `#F9F8F4`（暖白） | `#141414` |
| 卡片表面 | `#FFFFFF` | `#1F1F1F` |
| 描边 | `#EAE8E7` / 强 `#D8D4CF` | `rgba(255,255,255,.12)` |

判断依据是目标：要让界面「像 QwenPaw」，就应当采用 QwenPaw 自身的配色体系，
参考另一个产品的配色无法达成这个目标。

### 6.3 流程：先原型，再落地

用户要求先用 HTML 与 CSS 做静态原型确认效果，全部确认后再写入项目。

产物为 `prototype/ui-prototype.html`，包含 6 个切换入口
（全部、聊天页、列表页、首次连接、设置页、新旧对照）以及深浅色切换。

原型中包含若干当时代码尚未具备的能力（实例编辑、常亮、列表密度等）。
用户确认：原型中出现的未实现功能都要实现。

### 6.4 文案与素材

- 文案要求：使用书面语言但不过度正式，减少括号与冒号，不出现破折号与箭头。
  该轮使用了一次 Humanizer skill 做润色。
- Logo：从 QwenPaw 官方 SVG 中单独取出图形部分（横版包含图形与文字，
  颜色为黑色与橙 `#FF9D4D`）。启动页需要**完整 logo**，因为它是字母「a」的艺术化处理。
- 字体：MiSans，来源为 `https://hyperos.mi.com/font/download`。

## 七、功能补齐与语音（2026-10-26）

### 7.1 MiSans 字体：从子集到完整

第一版打包的是**子集**（约 200KB，仅含项目自身文案用到的字）。
结果是智能体回复中出现生僻字时回退到系统字体，**视觉效果不一致**。

用户决定改为完整打包，并明确知晓这会增大包体。
于是替换为完整字重（增加 5 至 8MB）。

该决定后来被推翻过一次：在体积压力下改为**运行时可下载**（见第十节）。
两次判断都成立——前期以一致性优先，后期以包体优先，取舍随项目阶段变化。

### 7.2 语音输入：从系统识别到 sherpa-onnx

第一版计划使用系统 `SpeechRecognizer`，几乎不增加包体。
用户要求支持实时字幕，因此改用 **sherpa-onnx**（k2-fsa，Apache-2.0），全部在本地运行。

决策过程经过两次调整：

1. 用户最初确定「默认使用系统识别，本地模型作为可下载的附加能力」；
2. 随后改为「语音功能必须额外下载模型，同时在设置中提供是否显示该按钮的开关」。

最终形态：模型为 126MB 压缩包（解压后约 168MB），在设置页手动下载，
并提供「显示语音按钮」开关。

### 7.3 语音实现的三个问题

**问题一：识别不出文字。** sherpa 日志显示 `in_sample_rate: 1600`。
原因是 `OnlineStream.acceptWaveform` 的第二个参数是**采样率**，而非采样数，
而实现中一直把 buffer 长度当作采样率传入（那个 4000 实际是 `minBufferSize`）。
修正后识别正常。

**问题二：按钮点击无响应。** 初期怀疑是 `AnimatedVisibility` 拦截了点击事件，
或面板每帧移动导致点击落空。**实际原因是点击坐标错误**——面板位置会随消息数量变化。
改用 `uiautomator dump` 动态获取坐标后恢复正常。

由此确立约定：操作界面时坐标一律从 dump 动态获取，不凭截图目测，
因为截图是缩放的，按截图坐标点击会落空。

**问题三：按住说话时中途松手。** 最初手指滑出按钮范围即停止录音。
用户要求手指在不离开屏幕的前提下持续录音。
实现改为只跟踪按下那一根手指的抬起（`awaitFirstDown` 配合跟踪相同 id 的 `pressed` 状态）。

### 7.4 其它补齐项

- **智能体选择**：用户指出手动输入 id 的体验很差，因为不会有人特意记住这个 id。
  改为填完网关后拉取 `/api/agents` 列表点选，手填 id 淡化为备用方案。
- **页面切换动画**：使用 `AnimatedContent` 做淡入与轻微水平位移，返回时反向。
- **时间不对齐**：标题使用 `weight(1f, fill = false)` 并跟随一个弹性 `Spacer` 抢占空间，
  导致时间缩进随每行标题长度浮动。改为标题 `weight(1f)` 占满剩余宽度（超长自动省略）、
  时间固定贴右。
- **左侧圆角方块**：原本显示会话名首字（出现「U」「新」这类看不出含义的单字），
  改为对话气泡图标，当前会话以橙色点亮。

## 八、性能第一次攻坚（2026-10-26）

用户反馈每个页面上下滑动都有卡顿。

### 8.1 走过的弯路

**弯路一：怀疑 MiSans 字体。** 假设是 `Compose` 的 `Text` 每次遇到不同字重都会触发完整字体解析。
实测关闭 MiSans 后反而更卡（jank 32% 升至 54%），说明字体不是主因。
但当时样本量太少，该测法本身也不严谨。

**弯路二：在设置页做测量。** 设置页内容少，无法体现真实差异。

**弯路三：只依赖 jank% 判断。** 真机 LM-G820N 上测出列表页 65%、聊天页 80% 的 jank，
但 `dumpsys gfxinfo` 的 jank% 在设备性能偏低时噪声很大，且会被 GPU 项主导。
这一指标需要谨慎使用，当时尚未意识到（详见第十三节）。

### 8.2 实际找到的问题

| 问题 | 修法 |
| --- | --- |
| 2.5s 轮询每次 `copy` 出新 state，导致整页重组 | 改为有变化才更新（approvals 未变化时 `return@onSuccess`） |
| `QwenPawTheme` 每帧重建 `Typography` 与字体族查表 | 按 `(scale, family)` 做 `remember` 缓存 |
| `SideEffect` 每帧重设状态栏外观 | 改在 `LaunchedEffect(dark)` 中只执行一次 |
| `timeLabel()` 每次重组都新建 `SimpleDateFormat` 与 `Calendar` | 改用 `java.time.LocalDate`，并按时间戳 `remember` |

**效果**：列表页 jank 从 65% 降到 8.78%，聊天页从 80% 降到 5.16%，设置页基线约 3%。

这一轮是有效的，但并不彻底。第 37 轮用户再次反馈滑动卡顿。
当时的修法都集中在「减少重组次数」，而真正的量级问题在别处，直到第十三节才查清。

### 9.1 先核实服务端能力，再写计划

- `GET /api/chats?archived=true|false`：按归档状态过滤
- 服务端**没有** summary 字段，因此会话摘要只能由客户端生成

由此确立：在用户的真实数据上执行写操作需要格外谨慎。

### 9.2 图片消息的字段问题（影响最大的一次）

服务端在 `runtime/message_convert.py` 的 `_request_input_to_msgs` 中读取的是**扁平字段**
`image_url` / `video_url` / `file_url`，**不是**早期协议中的嵌套结构
`{"type":"image","source":{"url":...}}`。

早期版本按嵌套结构发送，服务端会**静默丢弃**该内容块：不返回任何错误，
图片无法进入模型上下文，历史中也只留下文字。排查完全依赖阅读服务端源码。

正确形状：

```json
{"type":"image","image_url":"/home/u/.qwenpaw/workspaces/default/media/xxx.png"}
```

历史侧返回的则是 `data:image/png;base64,...`，由服务端将本地文件内联为 data URI。

**渲染方案**：不引入 Coil，`ChatImageLoader` 直接使用 OkHttp 与 `BitmapFactory`，
支持 `data:`、`http(s)://` 与服务端本地路径三种形态。
大图先读取尺寸再用 `inSampleSize` 采样，避免 OOM。

## 十、包体瘦身与 GitHub 仓库（2026-10-26）

用户反馈包体过大，同时提供 GitHub token，要求创建仓库并将 MiSans 改为从 GitHub 拉取。

### 10.1 诊断：主要成因不是字体

133MB 的 debug APK 构成如下：

| 组成 | 体积 |
| --- | --- |
| sherpa-onnx `.so` × 4 ABI | **约 98 MB** |
| dex（debug 未优化） | 44 MB |
| MiSans 字体 × 2 | 15.8 MB |
| 其它 | 约 10 MB |

MiSans 仅占 12%，**4 个 ABI 的 native 库才是主因**。

### 10.2 两项措施

1. **只保留 `arm64-v8a`**（`ndk.abiFilters`）：`.so` 从 98MB 降到 21.4MB
2. **MiSans 改为运行时下载**：默认使用系统字体，设置中的开关默认关闭

结果：debug APK 从 133MB 降至 **40.6MB**（降幅约 70%）。

### 10.3 MiSans 的许可约束

`adivenxnataly/MiSans` 中的 `MiSans.ttf` 为 Medium（500）、`MiSans-Static.ttf` 为 Regular（400），
与本地两个字重一一对应。Compose 提供 `Font(File, …)` 可在运行时构造 FontFamily。

但 MiSans 许可**明确禁止再分发字体本体**，因此仓库不提交字体文件
（`.gitignore` 排除 `res/font/*.ttf`），应用也不随包分发，
仅在用户主动点击时从其 GitHub 原址下载，并在设置页与关于页标注出处。

下载策略：两个字重先下载到 `.tmp`，**全部成功后再原子改名**，
避免半成品被判定为「已安装」；任一失败则清空全部并回到未安装状态。

### 10.4 顺带清理的死代码

发现一批「已定义但未接线」的代码：`OutboxEntity` 与 4 个 outbox DAO 方法、
`ChatWatchService` 前台服务壳（从未被调用）、`archiveChat`、`channel_watch_*` 字符串。

清理后 release APK 从 1.6M 降到 1.5M，56 个单测通过。

这次清理在文档中留下了一处隐患：旧文档仍写着「`ChatWatchService` 只是前台服务壳」，
而该类在本轮已被删除。第十五节重构文档时才发现并修正。

## 十二、折叠与分页（2026-10-26）

用户提出 4 项改动（含卡顿问题），随后追加 1 项。

### 12.1 对齐官方 Console 的折叠语义

阅读官方前端 bundle 后找到关键枚举：
**Expanded / Collapse process / Collapse results**，默认为 **Collapse results**。
此外 `autoCollapseThinking` 会在流式输出结束后折叠思考内容。

据此实现三档（`AssistantCollapse`）：

| 档位 | 行为 |
| --- | --- |
| `EXPANDED` | 全部展开 |
| `PROCESS_COLLAPSED` | 每条正文单独显示，思考与工具调用合并为一组（对应官方 text-only） |
| `RESULT_COLLAPSED` | 一个回合只保留最后一条正文，其余全部并入一组（对应官方 result-only） |

实现细节：`countSteps()` **只统计思考与工具调用**，中间正文虽也折入同组但不计数，
与官方口径一致；`Steps` 的 key 取**首条 id**，追加步骤时 key 不变、列表项不重建；
折叠结果模式下**出错的消息必须留在组外**，否则用户看不到失败原因与重试入口。

### 12.2 分页：一个后来被否定的判断

用户猜测可以一次只加载 8 条，向上滚动时按需加载。

服务端**没有分页参数**，历史一次返回全部，因此只能做**客户端窗口化**。
实现为按分组后的条目开窗，而非按原始消息数——一组处理过程可能包含几十条原始消息。

当时判断这就是卡顿的解决方案，下一轮即被证伪。

## 十三、卡顿根因：debug 与 release 的差异（2026-10-27）

用户反馈卡顿问题依然存在。

这一轮的价值在于**此前所有假设都被推翻**。

### 13.1 测量方法本身的三个陷阱

**陷阱一：模拟器的掉帧百分比不可信。** 在 `-gpu host` 模式（宿主 GPU 为 GTX 950）下，
RenderThread 单帧 `Drawing` 可达 45ms、`dequeueBuffer` 出现阻塞，
jank% 完全被 GPU 主导，无法反映客户端差异。
软件渲染（swiftshader）下更为极端，GPU 项出现 4950ms 量级。

**陷阱二：atrace 必须指定包名。** 使用 `atrace --async_start -c gfx,input,view`
不包含应用进程，采不到 `AndroidOwner:measureAndLayout`、`Compose:recompose`
这类应用级 section。必须使用 `-a io.qwenpaw.node`。

**陷阱三：atrace 文本解析中的 pid 语义。**
`tracing_mark_write: B|<pid>|` 中的 `<pid>` 是**进程 id**，不是线程 id。
嵌套栈配对必须使用行首 `comm-tid (pid)` 中的 **tid** 作为 key。
最初以 pid 作 key，算出 `total=0.0ms` 或出现大量错配，白费了一轮工作。

**正解**：采用与 GPU 无关的主线程帧指标，即
`dumpsys gfxinfo <pkg> framestats` 中 `HandleInputStart → PerformTraversalsStart` 的间隔。
Compose 的 doFrame 回调在 `performTraversals` 之前完成，
因此这一段代表「一帧内主线程实际消耗的时间」，与 GPU 无关。

### 13.2 决定性数据

同一份源码、同一会话（171 条消息）、同一手势：

| build | p50 | p99 | max |
| --- | --- | --- | --- |
| debug（3 轮） | 1.41 / 1.75 / 1.72 ms | 26.8 / 4.7 / 3.7 ms | **43.3 ms** |
| release（3 轮） | 0.77 / 0.65 / 0.68 ms | 2.7 / 2.0 / 11.4 ms | **11.9 ms** |

release 的主线程帧耗时约为 debug 的 **43%**（快约 2.3 倍），长帧从 43ms 降至 12ms。

debug 变体 `isMinifyEnabled = false`：没有 R8 内联与优化、没有 AOT、
没有 baseline profile，Compose 内部还会走 debug 断言路径。

debug 构建下的 atrace 分片也印证了这一点：`AndroidOwner:measureAndLayout` 累计 440–500ms
（单次最大 145.6ms）、`Compose:recompose` 208–244ms、`TextLayout:initLayout` 出现上百次。

### 13.3 四个被排除的假设

| 假设 | 实测结论 |
| --- | --- |
| 历史一次铺开太多条 | LazyColumn 只组合可见项；窗口化 8 条与铺开 500 条在滚动时的可见项数量一致，无差异 |
| `SelectionContainer` 嵌套 | 仅约 8%，属噪声级 |
| Markdown 解析与正则新建 | 微基准 0.113ms/条、正则 1μs/次，量级不足 |
| `atBottom` 在父作用域被 `by` 读取 | 确实会导致滑动起止重组整屏，但 A/B 只带来重组时间从 221ms 降到 208ms（约 10%），`measureAndLayout` 无变化 |

这四个方向此后不再投入。记录于 [ui-guidelines.md](ui-guidelines.md) 5.2 节。

### 13.4 保留下来的实际收益

虽然不是根因，但值得保留：

- `MarkdownText`：行内样式按块缓存、表格单元格按内容缓存；
  解析期 `Regex` **提升为文件级常量**（原先写在循环内，每行、每个单元格都重新编译 `Pattern`）
- `ChatScreen`：`atBottom` 改为 `remember { derivedStateOf { … } }` 且**不使用 `by`**，
  读取点仅存在于协程内部与 `JumpToLatestButton` 组件内部

### 13.5 一个被忽略的交付环节

`scripts/e2e_acceptance.sh` 安装的是 **debug** 包（`APK=.../apk/debug/app-debug.apk`）。

因此「脚本通过」与「用户手上流畅」是两件事。这正是用户反复反馈卡顿的直接原因：
验收一直通过，但验收使用的构建本身就是慢的那一种。

用户安装 release 包后确认卡顿消失。

## 十四、边到边适配（2026-10-27）

当时真机 LM-G820N 已关机，因此改用模拟器。
用户反馈：除设置页外的页面都出现顶部挤占通知栏、底部挤占小白条的问题，
设备为红米 K80。

### 14.1 根因：一条容易被忽略的 Scaffold 约定

`targetSdk = 35`，Android 15 起系统**强制**边到边（系统栏透明浮在内容之上）。

但直接原因是 M3 `Scaffold` 的语义：
`ScaffoldDefaults.contentWindowInsets` 取值为 **systemBars**，
而 Scaffold **只在顶栏或底栏槽位为空时**，才把对应方向的系统栏留白算进内容区。

因此：

- 设置页使用**不带** `topBar` / `bottomBar` 的 `Scaffold`，自动避让，显示正常
- 其他页面把自定义栏传入 `topBar` / `bottomBar`，Scaffold 认为由页面自行处理，于是被压住

用户提供的「设置页除外」这一条线索直接指向了答案。

### 14.2 修复原则

**底色仍铺满系统栏区域（保持真边到边），只把内容让开。**

- 顺序：先 `.background(...)`，再 `.statusBarsPadding()`
- 顶栏补 `statusBarsPadding()`：`ChatTopBar`、`ListHeader`、`ArchivedScreen`、`TokenUsageScreen`
- 底栏补 `navigationBarsPadding()`：新建按钮、批量操作条
- 输入条：留白加在 **`Surface` 内部**（否则外部会露出一条页面底色），
  且使用 `navigationBars ∪ ime` **取并集**而非相加——键盘高度本身已包含手势条
- `ConnectScreen` 是裸页面，自行补齐。**不能加进 `InstanceForm` 内部**，
  因为设置页也复用该表单，那边已由 Scaffold 注入留白，加在内部会造成双重留白
- 对话框走 Compose `Dialog`（默认 `decorFitsSystemWindows = true`），无需处理

### 14.3 验收

环境为模拟器 1080×2400、420dpi，状态栏 128px、手势条 63px。
通过 `uiautomator dump` 获取节点坐标，并解码 PNG 做像素采样
（环境中没有 PIL，PNG 解码为手写实现）：

| 位置 | 修复后 |
| --- | --- |
| 聊天页标题 | y ≈ 154（状态栏 128 之下） |
| 输入条按钮 | 底边 2293（手势条上沿 2337 之上） |
| 列表页顶栏 | y ≈ 158 |
| 设置页（原本正常） | y ≈ 154，**无双重留白** |
| 键盘弹出 | 输入条上移至 1424–1469，无多余空隙 |

状态栏区域的像素采样结果为应用自身底色 `#F9F8F4`，确认保持了真边到边。

## 十八、九项体验修复（2026-10-28）

用户提出九个问题，其中三项是功能缺失，五项是体验与配色偏差，一项是文案错误。
本轮同时确定了测试设备的变更：**停用真机，只用模拟器**。

### 18.1 语音按钮的 bug 有两个成因

表面现象是「开关关了麦克风还在」，实际是两处独立的错误叠加：

1. `ChatInputBar` 无条件渲染麦克风，只靠 `enabled` 置灰。开关关闭时按钮仍在，只是变灰。
2. `MainActivity` 传的值是 `voiceEnabled && modelState is Ready`。模型未下载时
   条件恒为 false，按钮**也不显示**——用户因此无从发现这个功能缺什么。

第二个成因是第一个的`解药`被误当成`补丁`：为了让「模型没下载时不显示」成立，
可见性被绑到了模型的就绪状态上。正确做法是把「可见」与「可用」拆成两个参数：
`voiceVisible` 只由开关决定，`voiceReady` 只影响视觉与点击后的提示。

修复后实测确认：关闭开关，`uiautomator dump` 里找不到任何麦克风描述，
附件按钮与发送按钮紧邻排列，没有留白。

### 18.2 灰色小字过淡的根因是用了描边色

`colorScheme.outline` 在 Material3 里的用途是**描边**，浅色 `#D8D4CF`、
深色 `0x2EFFFFFF`（18% 白）。把它当正文小字用，深色下对比度只有 **1.78:1**，
远低于 4.5:1 的可读下限。

新增语义色 `LocalCaptionColor`：浅色 54% 黑、深色 60% 白，
再把 21 处「文字用途」的 `outline` 换掉。替换时按行号逐条人工甄别，
`border`、`HorizontalDivider`、状态圆点等描边与图形用途全部保留原色。

实测深色设置页「字体版权归小米…」一行，文字亮度 165、背景 31，
对比度 **6.69:1**。

### 18.3 深色黑字是 LocalContentColor 的默认值

`Text` 不给 `color` 时读 `LocalContentColor.current`，其默认值是 `Color.Black`。
正常情况下 `Surface` 会提供正确的内容色，但连接页是裸 `Column`、
`AlertDialog` 内的部分层级也没有 `Surface`，于是深色模式下退到黑色。

修法是给这三处显式指定 `onSurface`。实测深色模式下「智能体 default」
采样为纯 `(255,255,255)`。

### 18.4 多地址回退：只对连接失败换地址

数据结构从 `baseUrl: String` 改为 `baseUrls: List<String>`。
旧字段以 `@EncodeDefault(NEVER)` + `@SerialName("baseUrl")` 保留，
读出后由 `migrated()` 迁进列表，写盘时不再输出。

第一版迁移测试失败，原因是存储用了 `encodeDefaults = true`，
不加 `@EncodeDefault(NEVER)` 会把 `"baseUrl": null` 一起写进 JSON。
这条约束写在 [InstanceStore.kt](../app/src/main/java/io/qwenpaw/node/data/local/InstanceStore.kt) 的注释里。

回退逻辑抽成纯函数 `AddressFallback`，因为 `InstanceRepository` 依赖 Android 的
`InstanceStore`，不便在 JVM 单测里构造。两条规则：

- **只对连接类失败换地址。** HTTP 4xx/5xx 说明地址是通的，换下一个既解决不了问题，
  还会把真实原因（例如 401 需要登录）掩盖掉。
- **命中后不改写顺序。** 用户把局域网地址排在第一是有意的，隧道地址通常更慢。

OkHttp 对连接被丢弃的地址抛的是普通 `IOException`，类型上看不出来，
只能靠文案里的 `Failed to connect` 识别。漏掉这条，真实环境里回退根本不生效。

实测：主地址填 `10.99.99.99:8088`（不可达）、备用填 `10.0.2.2:8088`，
验证结果为「连接正常，服务端 2.2.2.post1，已回退到 http://10.0.2.2:8088」。

回退提示最初误报了一次：`effectiveHosts` 是用户原文（`10.0.2.2:8088`），
`result.baseUrl` 已补齐协议（`http://10.0.2.2:8088`），直接比字符串会把
「未回退」判成「已回退」。改为比较前先 `normalizeBaseUrl`。

### 18.5 模型切换：服务端不接受 null

计划里写的是「传 null 恢复智能体默认」，来自 `docs/protocol.md` 此前的记述。
实测否定：四种写法全部失败。

| 请求体 | 结果 |
| --- | --- |
| `{"provider_id": null}` | 400，`Input should be a valid string` |
| `{"provider_id": ""}` | 400，`Model provider is unavailable` |
| `{"provider_id": "", "model": ""}` | 同上 |
| `{}` | 同上 |

`DELETE /api/chats/{id}/model` 返回 `Method Not Allowed`，不存在清除端点。

正确做法是先读 `GET /api/models/active` 拿到全局默认，再显式 `PUT` 回去。
这个端点是从 Web 前端产物里找到的：`grep` 打包后的 JS 才看到 `/models/active`，
服务端不提供 `openapi.json`（返回 404）。

另一个被否定的假设是模型列表的来源。计划原先打算用
`GET /api/models/{provider_id}/pool`，实测本机部署下返回空数组；
实际可选模型在 `GET /api/models` 每个供应商的 `models` / `extra_models` /
`discovered_models` 三个数组里，共 36 个供应商、合并后上百个模型。

模型菜单因此要限高（320dp）并允许滚动，否则会顶出屏幕。

### 18.6 导出的「无论如何都失败」

用户报的是导出必定失败。排查发现两个独立问题：

1. `pendingExportText` 用的是普通 `remember`。选文件时系统会把 Activity 推后台，
   低内存下可能被杀掉重建，文本变成 null，回调里静默早退——
   表现出来的就是「点了导出什么都没发生」。
2. 失败路径没有任何原因输出，`writeTextToUri` 只返回 `Boolean`。

修法：文本与文件名改放 `rememberSaveable`；`writeTextToUri` 改为返回
可读原因（`String?`），toast 里带上具体信息。`uri == null`（用户取消）
与 `text == null`（内容丢失）也分别给出不同提示，不再静默返回。

实测导出成功，`/sdcard/Download/新会话.md` 3934 字节，内容为完整 Markdown。

### 18.7 其余三项

- **归档提示**：单条与批量两处都加「今日不再提示」，按 `yyyy-MM-dd` 存日期而非布尔值，
  跨天自动恢复，不需要额外的零点重置任务。规则抽成 `ArchiveTip` 纯函数以便单测。
- **地址验证**：步骤 1 的勾从「地址非空」改为「验证成功」。地址非空不算完成，
  否则用户会以为这一步已经过了。新增「验证连接」按钮，只查版本与鉴权状态，
  比拉智能体列表轻。
- **文案**：把「离线识别模型」「下载后不联网也能语音输入」改为
  「语音识别模型（使用前必须下载）」与「语音输入依赖此模型，未下载时无法使用」。
  原表述容易读成「下载后还能离线用」，实际是不下载就完全不能用。

## 十九、测试用例清单（2026-10-29）

### 19.1 分类依据：按「能否在 JVM 上判定」切分，而不是按功能模块

一开始想把用例按功能模块排（会话、聊天、附件、语音、设置）。排下来发现同一个模块里的
用例在可执行性上差别很大：例如「会话」里既有纯排序函数，也有长按菜单的交互。
按模块排会让执行者反复在同一节里切换验证手段。

最终改成按验证层切分，每条带一个层标记：U（JVM 单测）、P（MockWebServer 桩）、
E（设备脚本）、M（手工）、N（非功能）。这样读的人可以直接筛出「本轮只能跑 U 的部分」。

「现状」列是有意加的：`已有` 与 `待补` 的区分让人一眼看出 119 个单测到底覆盖了什么，
而不是笼统地说「有测试」。

### 19.2 现场取的数字

- 用例总数 **213** 条：U（JVM 单测）126、M（手工）52、P（协议桩）17、N（非功能）12、
  E（设备脚本）6。其中 **68** 条由现有测试承接，12 条部分覆盖，**133** 条为待补缺口。
- `@Test` 共 **119** 个，分布在 13 个测试文件；`app/src/main` 44 个 Kotlin 文件、
  **12420** 行。
- `scripts/e2e_acceptance.sh` 六个场景（A1–A6），每个需 `--only` 单独跑。
- `free -h`：可用 9 GiB、swap 已用 2.3 GiB；`/dev/kvm` 存在，模拟器可直接起。

这些数字当场取，没有沿用上一节的记录——[AGENTS.md](../AGENTS.md) 五节已经写明
体积、单测数、APK 大小都曾凭记忆抄错。

用例数远大于单测数（213 对 119）是刻意的：单测只能覆盖纯逻辑，而发送、停止、重连、
语音、附件这些路径必须落到设备与手工。把它们一并列出来，是为了让「没有自动化覆盖」
这件事可见，而不是因为没写测试就当作不需要验证。

### 19.3 覆盖缺口的实际分布

盘点下来最大的一块不在解析层，而在 `ChatViewModel`：**零覆盖**。
它承担发送拦截、停止收尾、重连合并、审批轮询、草稿防抖、
后台通知判定这六件事，每一件的失败都会直接被用户看到。

解析层反而覆盖得不错：`ChatEventParser` 16 条、`StreamAccumulator` 11 条、
`HistoryMapper` 9 条、`SseReader` 9 条，真实抓包做输入，邪门形态基本都有用例。

协议层只有 `AgentAndWorkspaceApiTest` 9 条与 `QwenPawApiTest` 5 条，
chats、approval、token-usage、upload 全无桩测试。这是第二块缺口。

### 19.4 七条待验证疑点：读代码读出来的，不是猜的

写用例过程中顺带核对了状态更新与副作用的位置，发现七处逻辑不一致。
**没有一条在设备上复现过**，因此全部标成「待验证」而不是「缺陷」，
每条都附了验证方法。列出四条最有代表性的：

1. `finishRun` 收到新列表后直接赋值，绕过了 `orderChats`。GET `/api/chats`
   的排序无保证（[protocol.md](protocol.md) 二节已写明），所以「回复结束后置顶项掉位」
   是可预期的结果。但只有实际观察才能确认，因为服务端可能恰好按时间返回。
2. `archiveChat` 在 `chats` 过滤之后才去取会话名，取不到，提示文案固定回退成「会话」。
   这是纯逻辑错误，单测可直接判定，不需要设备。
3. `MainActivity` 里图片加载与导出用的 `Connection` 取 `primaryBaseUrl`，
   而仓库与 ViewModel 都用 `resolvedBaseUrl`。多地址回退生效时，这两条路径指向不同地址。
   影响范围比前两条大：图片可能加载不出来，导出也可能写到错误实例。

4. 离线缓存表的主键只有 `id`，查询却按 `chatId` 过滤；而 `StreamAccumulator` 的
   `local-user-N` 每次从 1 起算，`HistoryMapper.uniqueIds` 的 `#N` 后缀同样按会话重新计数。
   跨会话撞号时 `REPLACE` 覆盖，断网可能读到别的会话的消息。

第 4 条在写进文档前做了一次实测纠偏。原本怀疑的是「缓存命中率差 100 倍」，
先打了一次真实接口，返回 `cache_hit_rate=94.1325…`，证实服务端给的是百分数，
`%.1f%%` 的格式化是对的。**这条假设当场否掉**，换成上面这条缓存主键问题。
这是本轮唯一一次靠实测救回来的判断：若不先验证，就会把一个不存在的缺陷写进清单。

### 19.5 与既有约定的关系

**D-2：所有提示都发不出去。**

**D-3 / D-4** 分别是 V-7 与 V-6 的实机确认，见表格，不重复。

## 二十一、修复七个缺陷并复验（2026-10-29）

### 21.1 修复策略：能抽成纯函数的一律抽出来

七条缺陷里有四条的核心判据可以脱离 Android 框架，这一轮把它们抽成独立文件，
单测直接覆盖，而不靠模拟器验证：

| 抽取出的文件 | 对应缺陷 | 为什么值得抽 |
| --- | --- | --- |
| `data/remote/ErrorText.kt` | D-7 | 异常到中文的映射原本在 ConnectScreen 与 ChatViewModel 各写一份，行为不一致；抽出来才能用 `IllegalStateException` / `IOException` 直接测 |
| `ui/chat/AttachmentPlaceholder.kt` | D-3 | 占位文案的判据是纯字符串逻辑，抽出来后不必启动 Compose 就能验证「空文本 + 纯图片附件」应返回空列表 |
| `data/remote/UploadNames.kt` | D-5 | 文件名归一化的入参是三个可空字符串，最容易写错也最容易测 |
| `MainActivity.uploadAttachment` 内的 `uploadFileName` | D-5 | 只剩取 `DISPLAY_NAME` 这一小段与 `ContentResolver` 打交道，其余全在纯函数里 |

反过来，D-1 / D-2 / D-4 依赖协程与 Compose 生命周期，抽不出来，只能实机验。
这是本轮取舍的判据：**能脱框架就脱框架，脱不掉的才留给模拟器**。

### 21.2 D-5 的根因比原先写的更靠前

上一轮把 D-5 记在 `MainActivity` 的取名逻辑上。这一轮改了取名方式之后发现，
问题不止「取不到扩展名」：`uri.lastPathSegment` 拿到的是 `..._1000000058` 这种数字串，
连原始文件名都没有。`OpenableColumns.DISPLAY_NAME` 才能拿到 `qa_blue.png`。

即便如此仍然不够：服务端上传接口返回的文件名也可能不带扩展名。
因此 `UploadNames.resolve()` 在拿到名字后还要再判一次扩展名，缺了就按 MIME 补。
复验时 chip 显示 `..._1000000067.png`，服务端该消息 `content[0].type` 为 `image`，
`image_url` 是 `data:image/png;base64,...`，才算真正修好。

顺带记一条实测结论：换成 `image` 块之后，`deepseek-v4.1-flash-1017` 直接回
「The request model is not multimodal」。上一轮之所以能读出 RGB 值，
是因为它用 `execute_shell_command` 去读像素，走的是工具链而非视觉通道。
**「模型能说出颜色」不能作为图片通道正常的证据。**

### 21.3 脚本修好之后反而暴露了更多问题

D-6 表面上只是「节点名对不上」，实际改下来是四个独立问题串在一起：

1. `pick_first_agent()` 取「y>400 的第一个整行宽可点区」，而地址输入框本身就是整行宽可点区。
   点进去之后地址被改坏，流程退回第 1 步，表现成「脚本卡住」。
2. 地址框首次启动带真实默认值（不是 placeholder），`input text` 会追加。
3. Android 13+ 的通知权限对话框是系统窗口，覆盖在应用之上，之后所有点击都落空。
4. `adb shell input text` 遇到引号会截断，`bash -c 'nc -e /bin/sh ...'` 只输入到 `bash` 就停。

第 4 条最有欺骗性：脚本看起来正常跑完，审批卡片却不出现，
很容易误判成「服务端不再拦截这类命令」。实际是命令根本没发全。

结论写进 [test-plan.md](test-plan.md) 22.3，同时说明一件事：
**验收脚本失败时，先怀疑脚本的输入路径，再怀疑产品。**

## 二十二、九项功能与体验优化（2026-10-29）

本轮范围是九条来自实际使用的反馈，涉及日志、连接状态、地址管理、消息呈现与列表分组。
分七期推进，逐期编译验证，全部编码完成后先写单测再上模拟器。

### 22.1 「已就绪」与连通性无关

用户的第一条反馈是「顶部已就绪永远存在，连不上 QwenPaw 也显示」。
查证 `ChatTopBar.kt` 的写法是 `if (running) "正在生成" else "已就绪"`，
而 `running` 的六处赋值全部来自流式事件或历史 `status`——**它描述的是服务端有没有在生成，
不是这台手机能不能连上服务端**。断网时既没有事件也没有 `status`，于是永远停在「已就绪」。

改法是引入由轮询结果推导的 `LinkState`（UNKNOWN / ONLINE / OFFLINE），顶栏三态：
正在生成（琥珀）、连接中断·点击重连（error 色，整行可点）、已连接。
`UNKNOWN` 显示为「已连接」，避免冷启动瞬间闪红。

### 22.2 断网恢复必须自动，不能只加刷新按钮

用户的原话是「1 分钟前没有网络，1 分钟后恢复，现在必须重启应用才能恢复」。
查证发现 `ACCESS_NETWORK_STATE` 在清单里声明过，但全仓零使用：
没有 `ConnectivityManager`、没有 `onResume` 刷新、列表也没有下拉刷新。

因此加了 `NetworkMonitor`，并在 `AppViewModel` 里订阅它的 `online`。
两个细节是踩过的坑：

1. **必须同时覆写 `onLost`。** VPN 断开时系统只回调 `onLost`，不再给一次能力变化；
   只听 `onCapabilitiesChanged` 的话，VPN 拔掉后客户端仍以为在 VPN 上。
2. **订阅要 `drop(1)`。** `StateFlow` 订阅瞬间会先发一次当前值，不丢会立刻重复拉一轮会话列表。

另外只对 `false → true` 的跳变动作，关闭网络时不重载——否则地铁里穿隧道会反复打请求。

### 22.3 「验证连接」慢，以及备用地址为什么形同不存在

两个问题同源，都是超时配置与缓存策略的问题。

**慢的根因**：`defaultClient` 的读超时是 10 分钟且没有 `callTimeout`，
「连上但对端不回包」（隧道或 VPN 半开连接）要等满 10 分钟。
新增 `probeClient()`：connect 4s / read 5s / `callTimeout 8s` / 不重试，
且验证只发一个 `GET /api/version`（原来每个地址发两个请求且串行）。
另外把「正在尝试 1/2 · url」显示出来，用户能分清卡住还是在回退。

**备用地址失效的根因**：`runtimeHit` 是一个**单桶永久缓存**。在家连上局域网后缓存记下
`192.168.x.x`，出门 VPN 上线时缓存仍指向那个地址，于是每条请求都先等一遍连接超时才回退。
改为按 `id@网络类型` 分桶，网络一变桶就换；同时加 `resolveOrder()` 四级优先：
网络命中 `preferOn` > 用户手动指定 `preferredBaseUrl` > 运行期命中 > 原始顺序。
前三者都只「提到最前」不排他——排他会让一次手动选择在地址故障时彻底不可用。

**实测又发现一个更隐蔽的**：冷启动（或重装）时运行期缓存为空，
`resolvedBaseUrl` 返回的只是「排序后第一个」，**并不保证可达**。
重装后第一次启动，第一个地址是失效的 `10.0.2.9`，聊天页直接报连接失败，
备用地址完全没有机会。补了 `probeReachable()`：启动后台探一次，
命中地址与当前绑定不同就重绑并重载。复验后冷启动自动切到备用地址，无需用户操作。

### 22.4 服务端 usage 的真实形状与两个假设的推翻

计划阶段用 `curl` 看过一条消息，得出「整轮用量挂在该轮最后一条 assistant 消息上」。
实机上比对整段历史后发现**假设错了**：服务端把同一个 `qwenpaw_turn_usage` 挂在
**该轮每一条** assistant 消息上（reasoning、plugin_call、plugin_call_output 全都有）。
原样渲染会让一个 37 步的回合里每段正文下面都重复一遍相同的 token 数字。

改法是 `HistoryMapper.markTurnEnd()`：按「连续的非用户消息」切成回合，
只让该轮最后一条**带统计的正文**保留 `stats` 并标 `turnEnd`，其余清空。

第二个被推翻的假设是 `cache_hit_rate` 的量纲。原以为是小数值，实测返回
`74.99633806943021`——**百分数**。解析时统一除以 100，
避免界面与日志两处各折一次、结果不一致。

顺带确认了一件事：服务端**没有**首字耗时字段（源码里搜不到 `first_token`/`ttft`/`latency`），
用户也确认不做，因此界面上只显示输入、输出、模型。

### 22.5 头像：不引入 Coil 的取舍

用户要求头像支持裁剪与 GIF。项目此前**零图片库**（自建 `ChatImageLoader`，
`OkHttp` + `BitmapFactory`，内存 LRU 24 张，无磁盘缓存），也**零裁剪/缩放/EXIF 代码**。

两个决定：

1. **GIF 存原样、只显示首帧，不引入 Coil。** 只在 32dp 的圆形头像里播动图，观感收益很低，
   却要引入第二套图片加载体系并给 R8 加 keep 规则。存原文件而不是转成 PNG 的理由是：
   将来换成支持动图的版本时不必让用户重新选图。设置页明写「GIF 动图原样保存并在头像中显示首帧」。
2. **新增 `androidx.exifinterface`。** 不处理 EXIF 的话竖拍照片存出来的头像会躺倒。

裁剪的几何换算抽成纯函数 `CropGeometry`（基础缩放 / 生效缩放 / 位移夹取 / 裁剪区域），
因为手势拖动与缩放最容易出「拖到底还能拖」「裁剪区偏出图片」这类问题，
而在 Composable 里没法断言。绘制用 `Canvas` 自己算 dst 偏移，
而不是给 `Image` 加 `graphicsLayer`：缩放与位移必须和几何计算用同一套公式，否则裁剪结果会偏。

### 22.6 分组三态与时间口径

QwenPaw 网页版的分组三态（按时间 / 按来源 / 不分组，单击循环）来自打包产物
`assets/zh-*.js` 里的 `groupByTime`/`groupBySource`/`groupByNone`，不是推测。

顺带修掉一个既有偏差：`ChatListScreen.timeLabel()` 原来直接截 UTC 字符串前 10 位当日期，
等于按**UTC 日界**划分「今天/昨天」。东八区早上 7 点发的消息会被算成前一天。
新增 `ui/TimeLabels` 统一解析到本地时区，会话列表与消息气泡共用。

分组实现上有两条规则：置顶项无论哪种模式都单独成区排最前（否则置顶等于没有），
空桶不输出（只有表头的分区是噪声）。搜索时强制不分组——分组会把命中的会话拆到多个表头下。

## 二十三、十一项体验问题修复（2026-10-29）

用户在一次实际使用后列了十一条问题，从「按钮显示条件写反」到「缺一整条引导流程」都有。
十一条全部落地：三处是状态判定写错，两处是手势冲突，其余是交互重构与新增流程。

### 23.1 三个根因，都在状态判定上

三条问题（跳到最新、发消息另建会话、顶栏谎报已连接）表面无关，根因都在「某个布尔/字符串
被当成了它并不表示的东西」。

1. **「跳到最新」显示条件写反。** `ChatScreen` 里 `visible = { atBottom.value }`。
   停在底部时常驻、上翻历史时消失，与语义完全相反。改为 `!atBottom.value`。
   顺带把 24 裸像素换成 `8.dp.toPx()`：xxhdpi 上 24 像素只有 8dp，
   手指一碰就误判离开底部，按钮会闪。
2. **发消息会另建会话。** `ChatViewModel.bind()` 无条件清空 `currentChatId`，
   而 `AppViewModel.refreshAll()` 也调 `bind()`，被「顶栏重连 / 网络恢复 / 改地址」三处共用。
   同实例重连一次就把会话置空，`send()` 随即走新建分支。
   改为仅当实例 id 真的变了才清空（抽成纯函数 `shouldClearOnBind`）。
3. **断网仍显示「已连接」。** `ChatTopBar` 的三分支漏了 `LinkState.UNKNOWN`，
   它落进 `else -> "已连接"`；同时 `AppViewModel` 的网络订阅在 `online == false` 时
   `return@collect` 空转，断网信号根本传不到聊天页。
   补第四分支，并让 `setNetworkState(false)` 直接置 OFFLINE、恢复时置 UNKNOWN
   交给随后的请求证明。`startRun` 失败与 `attachRunningStream` 异常两处各补一次
   `updateLink(OFFLINE)`（后者排除 `CancellationException`，否则点「停止」也会显示断线）。

**教训**：同一个状态字段被多处读取时，任何一处把它当成别的含义都会表现出来，
且症状与真正的位置相距很远。`bind()` 那次尤其典型——它的调用点是「重连」，
但后果出现在「发消息」。

### 23.2 实例名与地址别名是两件事

原表单没有实例名输入框，`connect()` 用 `addresses.first().alias ?: url` 当 `name`。
结果实例卡片的标题与副标题显示同一个字符串，读起来像「给实例起别名」，
而那个字段描述的其实是某一条连接地址。

新增 `InstanceDraft`（`addresses` / `instanceName` / `username` / `password` / `agentId`），
`resolvedName()` 在名称空白时回落到第一个地址——名称是自由文本，用户很可能只敲空格，
否则卡片第一行会是一片空白。表单在地址列表上方加「服务器名称」，与别名分开标注。

### 23.3 地址切换的两层语义

用户的原话是「仅在本次打开生效」，但编辑实例里已有持久偏好，两者不能互相顶掉。
分成两层：

- `InstanceConfig.preferredBaseUrl`：写配置，长期有效，编辑实例里改。
- `InstanceRepository.sessionPick`：内存 map，进程结束即失效，设置页点「本次使用」写入。

`resolveOrder()` 的五级优先级（sessionPick > 网络偏好 > preferredBaseUrl > 运行期命中 >
原始顺序）抽成纯函数 `resolveOrderPure()` 以便单测。前四级都只是**提到最前**，
不去重也不排他：指定地址坏了仍然能回退，否则一次手动选择会让实例在地址故障时彻底不可用。

踩坑：`sessionAddressOf` 初版直接读 `repository` 里的普通 `mutableMap`，
Compose 观察不到，用户点了「本次使用」界面纹丝不动。改为 `AppState.sessionPicks`
与仓库同步写，界面读 state。

### 23.4 分组的折叠与新建

服务端早已支持 `POST/PUT/DELETE /api/chats/groups`，客户端此前只做展示。

折叠只清 `chats`、保留表头，折叠状态存 `qwenpaw_ui` 的 `collapsed_groups`——
它是用户偏好，既不属于某台服务器，也不该跟着实例走。

空的自建分组必须显示。用户刚建完必然还没有会话，藏起来像建失败。
初版 `bySource` 写 `buckets[group.id] ?: return@forEach`，恰好把所有空组过滤掉；
改为 `.orEmpty()`，再只过滤掉空的内置分组。

### 23.5 长按从「直接复制」改为菜单

原实现 `combinedClickable(onLongClick = 复制)` 压在 `SelectionContainer` 外层，
两套长按手势互抢，结果既选不中文本又会被整段复制。

改为长按弹 `DropdownMenu`（复制 / 复制为 Markdown / 选择文本），并且
`SelectionContainer` **只在选择态下包裹正文**、选择态下不挂 `combinedClickable`。
底部操作行在选择态换成「完成选择」，那是退出该态的唯一入口。

「复制」走新增的 `MarkdownPlainText.strip()`，「复制为 Markdown」走原文——
此前两个按钮行为完全相同，等于同一个功能给了两个名字。
`strip()` 保留围栏内内容原样，因为代码里的 `*` 与 `_` 是语法本身。

踩坑：`strip()` 初版把分隔线与表格分隔行整行删掉后，上下原本的空行留下来变成三连空行。
改成删标记行时顺手收掉相邻空行（`skipBlank` + 回退删除尾部空行）。

### 23.6 选区配色不能用主色

`LocalTextSelectionColors` 此前取 `colorScheme.primary`，而用户气泡底色就是品牌橙
（实测 `rgb(255,127,22)`），同色系高亮叠上去完全不可见。
改为浅色 `#1F6FEB`、深色 `#7AA7FF`，底色取把手色 32% 透明度。

**这条约束已写进 [ui-guidelines.md](ui-guidelines.md) 8.4**：选区色不得与它能覆盖的
任何气泡底色同系。

### 23.7 气泡头部改两行

原头部是单行 `Row`（昵称 + `HH:mm`），昵称一长就只剩时间，时间也缺秒。
改为两行 `Column`：昵称在上、`yyyy.MM.dd HH:mm:ss` 在下，用户侧右对齐、
智能体侧左对齐，与头像位置一致。

`TimeLabels.fullStamp()` 新增。这里踩了一个只有真机才暴露的坑：
服务端 `metadata.timestamp` 形如 `2026-10-26T00:15:42.910613+08:00`，
**带偏移量**，而 `Instant.parse` 在 Android 的 `java.time` 上不接受偏移，
返回 null → `showHeader = stamp != null` 为假 → 整块头部不渲染。
修复是在 `parse()` 里加 `OffsetDateTime.parse(...).atZoneSameInstant(zone)` 回退分支，
并补 3 条回归单测。这个 bug 在单测里发现不了，因为测试用的都是 `Z` 结尾的样本。

用户昵称存 `qwenpaw_ui` 的 `user_name`，默认「我」。

昵称输入**逐键提交**而不是等失焦：实测在设置页按返回键只是收起键盘，
焦点仍留在输入框上，`onFocusChanged` 不触发；设置页在页面栈里也不销毁，
`DisposableEffect(onDispose)` 同样等不到。只挂失焦回调会让用户敲完直接返回时静默丢内容。

### 23.8 首次启动三步引导

新增 `InstanceWizard`：第 1 步地址 + 实例名 + 地址别名（验证通过才能下一步）→
第 2 步按 `authRequired` 决定是否需要账号（不需要则轻提示后自动跳第 3 步）→
第 3 步读智能体列表单选，手填 id 作备用。

引导页**不放多地址相关条目**：把「备用地址」「回退」这类概念摆在首次启动的路径上，
只会让人怀疑自己漏填了什么。需要多地址的人在设置里用填表方式补。

`scrollable` 参数是必须的：首次启动页外层已有滚动容器（还要接「已保存的实例」），
设置页的子页面只有这一层，两层 `verticalScroll` 会互相抢手势。

`InstanceRepository.loginRequired()` 把 `enabled && has_users` 统一到一处，
四处判定共用同一个式子。只开 `enabled` 却没有用户时，登录接口无从登录，
按「不需要登录」处理。

设置页的「添加实例」改为先选方式（填表 / 引导式），两种形态共用 `addConnecting` / `addError`。

### 23.9 二级菜单改居中对话框

顶栏三个 `DropdownMenu`（模型 / 审批 / 分组）改为 `OptionDialog`：
`Dialog` + 圆角卡片 + `LazyColumn` 限高 420dp，选中项右侧对勾，`leading` 放固定首项。

「移动到分组」补了首项「未分组」——此前下拉里没有这一项，会话进组后移不回去。
输入框上方的模型胶囊加 `.clickable(role = Role.Button)`，点它直接开同一个对话框。

思考模式那处**保留下拉**：最多五六项，下拉比对话框更快。

## 二十四、六项界面与文案修正（2026-10-30）

六项来自一轮连续使用：三处是文案与归属信息，两处是真实缺陷，一项是界面口吻清理。

### 24.1 顶栏末尾的归属名

用户要求「已通过「地址/别名」连接至 QwenPaw」里的 QwenPaw 跟随服务器名称变化，
未设置时仍写 QwenPaw。三选一确认后取了「只替换末尾的 QwenPaw」这一形态。

`connectedLabel()` 由两参改三参，`ChatState` 新增 `boundServerName`，
`ChatViewModel.bind()` 新增 `instanceName`，`AppViewModel.bind()` 传入实例名。

**第一版把「名称是不是地址」的判断放在 `connectedLabel` 里，是错的。**
它只能拿到当前绑定的那一条地址，而实例名是表单留空时由
`InstanceDraft.resolvedName()` 回落出来的**首条**地址。当实际绑定的是备用地址时，
两者不相等，判断失效，顶栏显示成「已通过「EasyTier」连接至「10.0.2.9:8088」」——
同一个网关地址在句子里出现两次，且指向的还是那条没在用的。

改在数据层：`InstanceConfig.serverDisplayName` 拿实例的全部地址比对，
忽略协议前缀与结尾斜杠（回落值存的是用户原文，`addresses` 里是规范化结果）。
命中任一条就返回空串，表示「没起名字」。

**教训**：判断需要「完整上下文」时，不能放在只拿到局部参数的纯函数里。
这一条与 23 节把判定抽成纯函数的做法并不矛盾——抽纯函数的前提是参数够用。

顺带修了排版：`已连接至` 后面接中文引号不留空格，接 `QwenPaw` 留一个空格。
单测先暴露了这点（`已连接至[]「家里的机器」` vs `已连接至[ ]「...」`）。

### 24.2 服务器名称改非必填

`InstanceWizard` 第 1 步此前要求名称非空（`nameOk`），而填表方式早就标了「可选」。
两处口径不一致，用户在引导页会被拦住。改成 `canNext = verified && !verifying`，
名称标签由「必填」改「可选」，说明补上回落规则。

落库仍走 `InstanceDraft.resolvedName()`，空白时回落地址，无需改动。

### 24.3 引导页第 2 步的死锁

根因在 `LaunchedEffect(step)` 的守卫写成了 `if (needsLogin != null) return`。
它把「是否已判定」与「是否要跳走」混成了一件。于是：

未开登录 → 首次进第 2 步判定 `needsLogin = false` 并跳到第 3 步 →
用户点「上一步」→ 回到第 2 步 → `LaunchedEffect` 因缓存命中提前返回，不再跳；
而该步的 `canNext` 要求 `needsLogin == true && 用户名 && 密码`，
输入框又因 `needsLogin == false` 根本不渲染。第 2 步成了不能前进也不能填的死页面。

两处一起改：

1. `LaunchedEffect` 缓存命中时也要执行跳转，只在**首次**判定时弹提示。
2. `wizardBackStep(step, needsLogin)` 在「无需登录 + 从第 3 步返回」时直接回第 1 步，
   避免「回到第 2 步被立刻弹走」的闪动。抽成纯函数以便单测。

这类缺陷的共同点是**两个条件的组合才是完整前提**，只检查其中一个会漏。
写 `if (x != null) return` 之前应当先问：这个守卫拦住的是不是全部该拦的情况。

### 24.4 消息底部的「选择文本」

消息操作行此前只有「复制」「复制为 Markdown」，进入选择态只能长按。
新增第三个按钮，复用同一个 `onToggleSelection`。

进入选择态时弹一条轻提示：「已进入选择态；「完成选择」在这条消息下方」。
理由是选择态的退出入口在与按下的地方同一条消息下方，但用户按的是「选择文本」这个字样，
不一定知道该往哪看。长按菜单里的同一项也补了同一条提示。

图片气泡 `copyable = false`，不会出现该按钮——图片没有可选的文字。

### 24.5 头像裁剪器的绘制溢出

`drawImage` 的 `dstSize` 是「图片尺寸 × 有效缩放」。用户放大或图片长宽比极端时，
它会大于取景框；`CropGeometry.clampOffset` 只保证**铺满**，不保证**不溢出**。
Compose 的绘制默认不按布局边界裁剪，溢出的部分直接画到上方标题行之上，
把「取消 / 调整头像 / 保存」压住。

修法是给取景框 `Box` 加 `clipToBounds()`。实测 16:9 横图放大后，
取景框位于 y 732–1812，顶部工具行（y 140–255）采样全部是 `#101010` 纯背景，
没有任何图片像素越过边界。

**这条已写进 [ui-guidelines.md](ui-guidelines.md) 8.4**：凡是用 `drawImage`
自行计算 `dstOffset` / `dstSize` 的场景，必须给容器加 `clipToBounds()`。

全量扫描 `app/src/main/java/io/qwenpaw/node/` 下含中文的字符串字面量（643 条），
筛出会显示到界面的部分，按「明显口语 / 轻度口语或句式松散 / 标点与一致性」三类列出，

## 二十五、发送反馈与 GIF 头像（2026-10-30）

四项来自同一轮使用：两处是同一个真实缺陷的两个观感面，一处是 GIF 只显首帧，
一处是继续清理重复的灰色说明行。

### 25.1 「发送后页面空荡荡」与「回复完毕才看到历史」是同一个 bug

用户先描述为两个问题：

1. 给智能体发消息后，聊天页没有任何反馈，要等上游开始输出 token 才出现工具调用或 think；
2. 回复完毕前看不到之前的消息，看着像新建了一个会话来发。

追问后确认第 1 点不是「完全没有用户气泡」，而是「气泡以后整屏仍然空着」。
按这个口径查代码，两问落在同一条语句上。

`ChatUiState.messages`（界面消息）与 `StreamAccumulator`（流式折叠器）是两份独立列表：

- `openChat()` 把服务端历史**直接写进** `_state.messages`，同时 `accumulator = StreamAccumulator()`
  被清空——历史**不进** accumulator；
- `startRun()` 随后写 `messages = accumulator.snapshot()`，用只含刚追加的用户气泡的快照
  **整体覆盖** state；
- `pushSnapshot()` 每收到一帧同样整体覆盖。

于是每发一条消息，此前所有消息都被整屏冲掉。首个 token / 工具调用 / think 帧到达前，
界面上只剩一条用户气泡；到帧之后才一点点长回来，观感就是「点了发送没反应」。
回复结束时 `reconcileWithServer()` 用服务端历史重新覆盖，于是「输出完毕才正常」。
两问因此是同一个根因。

**修法**：引入「历史前缀」。`private var historyPrefix: List<ChatMessage>` 只在三处更新
（`openChat` 成功、离线读缓存、`reconcileWithServer`），其余写入一律走
`mergedMessages() = mergeHistory(historyPrefix, accumulator.snapshot())`。
换实例、删会话、归档当前会话、批量删除/归档时同步清空前缀，避免旧服务器的残留被拼回来。

同一文件里 `attachRunningStream()`（重连路径）本来就是按 id 合并，写法是对的，
这次反过来把它当成范本。**教训**：同一份状态有两个写入路径时，只要其中一条是「整体覆盖」，
另一条迟早会把对方的数据吃掉。这类覆盖必须收敛到一个拼接函数里。

### 25.2 建会话往返期间界面完全不动

`send()` 在 `chatId` 为空时先 `createChat` 再 `startRun`，而用户气泡原先是在 `startRun`
内部追加的。没有当前会话时，这次网络往返期间 state 一次都没更新，界面静止。
把回显提到 `send()` 开头（`echoUser`），点下发送的同一帧就能看到自己的消息，
并立即置 `running = true`，让「停止」按钮与等待行同时出现。

建会话失败时用新增的 `StreamAccumulator.rollback(ids)` 撤回这几条回显，改由错误气泡承载
原文并挂「重试」。不撤的话用户点重试会把同一段文字再画一遍。
`rollback` 只删末尾的用户消息，不动 `indexByMsgId` / `toolIndexByCallId`——
后两者只登记智能体消息，删尾部不影响它们的下标。这一点写进了注释，否则下一个人
很容易「顺手」补一段重排逻辑。

### 25.3 等待态：判据不能是「有没有在流式」

首帧到达前的占位行由纯函数 `needsAwaitingPlaceholder(messages, running)` 决定。

第一版判据是「`running` 且没有任何 `streaming` 的智能体消息」。实机跑起来发现收尾时会闪：
`ResponseStatus=completed` 先把流式标记清掉，而 `running` 要到流处理结束才复位，
中间那段空档让等待行重新冒出来、紧跟着又消失。

改成「`running` 且最后一条还是用户自己发的」。任何一个智能体消息——正文、思考、工具、错误——
落下来它就永久退场，不存在回闪。这条抽成纯函数（`AwaitingPlaceholderTest`，6 个用例），
因为它在设备上只能靠肉眼观察，而时序最容易被后续改动碰坏。

文案取「正在生成」，不用「已发送」：此刻请求未必已经到达服务端，写成状态确认是错的。

### 25.4 列表贴底：三个连环坑

这一节是本轮耗时最多的部分，三次修改都只治了表象。

**坑一：按 `atBottom` 判断是否跟随。** 流式内容变长会重新分组，`ChatItem` 的 key
跟着变，LazyColumn 找不到原来的锚点，位置跳一下。跳完 `atBottom` 变 false，
若据此刻判断就永久停止跟随。改为只在**用户拖动结束时**采样 `followTail`。

**坑二：用 `isScrollInProgress` 识别「用户在滑」。** 它对 `scrollToItem` /
`animateScrollToItem` 同样为 true，而本文件几乎每帧都在程序化贴底，
于是跟随标记被反复误判成 false。改用 `listState.interactionSource.interactions`
里的 `DragInteraction`，并等到惯性也停下来（`isScrollInProgress` 转 false）
再读取最终位置。

**坑三（真正的根因）：`scrollToItem(i)` 默认把第 i 条的顶部对齐到视口顶部。**
最后一条往往是几屏长的回复，那样只停在它的**开头**，`atBottom` 仍为 false，
「跳到最新」按钮随即冒出来——看起来就像「跑到了别处」，其实是停在了这条消息的开头。
所有贴底调用改用 `requestScrollToItem(index, Int.MAX_VALUE)`：偏移超出内容范围会被
钳到真实底部，这才是「滚到最后」。

顺带补了两处：

- 贴底的触发键从 `messages.size` 改成三路（最后一条的 id、文本长度、分组后的条目数）。
  回复结束时 `reconcileWithServer` 用服务端历史整体替换列表，本地 id
  （`local-user-N` / 流式 msg_id）全部换成服务端 id，条数却可能不变；而此时流式标记被清掉，
  一串「正文 + 思考 + 工具」又会被折成一个 `Steps`，条目数反而减少。三个键各盯一种变化。
- 补页逻辑加 `if (followTail || state.running) return`。列表被整体替换的瞬间，
  旧锚点消失，`firstVisibleItemIndex` 可能短暂塌到 0，被误判成「翻到顶了」，
  接着把几个月前的历史铺回来。

**这一节的教训**：`scrollToItem` 的偏移参数不是「额外微调」，它决定对齐方式。
不传就是顶部对齐。项目里此前所有贴底调用都没传，只是恰好那些位置最后一条很短，
没暴露出来。看 Compose 滚动 API 时要连默认值一起看。

### 25.5 GIF 头像

用户要求 GIF 头像动起来，不是只显首帧。两条路取舍后选了引入 Coil：
`io.coil-kt:coil-compose:2.7.0` + `coil-gif:2.7.0`（约 700KB）。

`AvatarStore` 新增 `imageLoader`：API 28 及以上注册 `ImageDecoderDecoder`（系统
`ImageDecoder` 驱动动画），API 26–27 用 `GifDecoder`（Coil 自带 `Movie` 逐帧播放）。
minSdk 是 26，两条分支都必须留。`ChatAvatar` 改用 `AsyncImage`，
删掉 `AvatarStore.load()` 与它对 `BitmapFactory` 的依赖。静态 PNG 走同一条路径，没有第二条分支。

首字回落保留，但只在图片就绪前显示。图片就绪后不再叠在底下：带头像的 GIF 常有透明区域，
首字会从透明处透出来。加载失败（文件损坏、格式不支持）退回首字，不留空洞。

「关于」页补了 Coil 的第三方资源条目。

**被推翻的旧决定**：22 节曾明确写过「不引入 Coil，GIF 只显示首帧」，
理由是「32dp 圆形头像播动图的观感收益不足以抵依赖成本」。这次用户直接要求动起来，
前提变了——那是用户明确的需求，不再是自制与依赖之间的自主权衡。
`architecture.md` 五节的两条 `ChatImageLoader` 相关行也一并改写：
会话图片仍不用 Coil（三种地址形态仍要自定义逻辑、缓存会重复），
头像用 Coil（只服务本地文件、与前者无重叠、逐帧解码已有封装）。
**这两件事不冲突，边界是「图片来自哪里」**，原来那一行没把边界写清楚，
只写了「不引入 Coil」，容易在下一次读到时被当成不可推翻的结论。

### 25.6 灰色说明行清理

`StepIndicator` 右侧「第 x 步，共 N 步」与圆点表达的进度完全重复，删掉；
`InstanceWizard` 的步骤标题只留「服务器」「登录」「智能体」。
第 1 步两处字段说明按用户给定文案统一为「将在实例列表显示，可随时修改，留空则显示地址」。

另做了一轮全量扫描（35 个文件、约 181 条中文字面量，其中界面可见约 95 条），
按「同一屏说了两遍」与「不提供新信息」两条判据清理了 20 余处，例如：

- 「生成中保持屏幕常亮」的副标题原本是同义重复，改为「仅在生成回复期间生效」；
- 「语音识别模型（使用前必须下载）」标题里已说必须下载，正文再说一遍，且
  「约 150MB」在同卡出现三次，收敛为一处；
- 填表页「服务端开启登录时填写」与两个 placeholder、一段定义性说明说了同一件事，只留定义那条；
- 用户名/密码说明与空态提示里复述「填写地址后点击「读取列表」」这类界面上明摆的步骤，删除。

**没有删的**：错误信息、空态、加载中、危险操作确认、实时进度（如「正在尝试 1/2 · 地址」）、
以及提供用户原本不知道的信息的行（图片处理规则、Mermaid 说明、日志条数与来源区分）。
判据是「删掉之后用户会不会少知道一件事」，不是「字数多不多」。

## 二十六、交付文件、气泡铺满与协议补全（2026-10-30）

本轮的问题都来自实际使用：智能体交付的文件在客户端完全不显示；用户气泡右侧与
智能体气泡左侧各有一条空白；只填域名时被补成 `http://`，登录接口返回 404。
另外按要求加入了两个托管平台域名的拦截。

### 26.1 `send_file_to_user` 没有文件接口

官方 Web 把交付结果渲染成带缩略图的文件卡片，客户端这边整轮回复只剩
「处理完成 · 16 步」。查历史消息后确认，服务端**没有「已交付文件」这类接口**，
文件字节直接内联在工具输出里。

实测了一次真实的 `send_file_to_user` 回合，
配对的 `plugin_call` 与 `plugin_call_output` 形如：

```json
{"call_id":"call_38d30734739842a996f508da","name":"send_file_to_user",
 "arguments":"{\"file_path\": \"/home/.../chatgpt_2022-12-05_esperanto.png\"}"}

{"call_id":"call_38d30734739842a996f508da","name":"send_file_to_user",
 "output":"[{\"type\":\"data\",\"id\":\"744e...\",\"source\":{\"type\":\"base64\",\"data\":\"iVBORw0KGgo...\"}}]"}
```

两条结论直接决定了实现：

1. **`output` 里没有文件名。** 文件名只能取 `arguments.file_path` 的 basename，
   因此解析器必须先按 `call_id` 把调用与输出配对。历史路径由
   `HistoryMapper.map()` 维护 `argsByCallId`；流式路径由 `StreamAccumulator.onToolOutput`
   传当前工具卡的 `arguments`，两条路径共用 `DeliveredFiles.parse()`。
2. **`output` 是字符串里再套一段 JSON**，不是对象。第一次解析拿到的是
   `"[{\"type\":\"data\"...}]"`，需要再解一层。

`DeliveredFile`（89 行）只对图片解 base64 并拼成 data URI；其它类型只保留
文件名与路径。`DeliveredFilesCard`（167 行）每行 44dp 缩略图、文件名、完整路径与
「已发送」，图片行可点开全屏。缩略图复用 `ChatImageLoader` 的 data URI 分支，
失败时回退 `Icons.Default.Description`，不新增图片库。

**解析后立即把 `ToolCard.output` 置 null。** base64 往往是几 MB 到几十 MB，
留在界面状态里会让每个携带工具卡的重组都复制一遍字符串，也让日志与导出
无意中带上整份文件内容。代价是工具卡片展开后不再显示这段原始输出——
它本来也不适合阅读，展示职责交给文件卡片。

### 26.2 一个转义坑：`JsonPrimitive.content`

第一版 `DeliveredFilesTest` 里「历史能配对出文件」一例失败，期望 1 实得 0。
原因是 `HistoryMapper` 取字符串用的是 `element.toString().trim('"')`，
对 `arguments` 这种本身就是 JSON 字符串的字段会保留内部转义（`{\"file_path\": ...}`），
二次解析拿不到 `file_path`。

改用 `(element as? JsonPrimitive)?.content`，它返回**已反转义**的内容。
三处取字符串的地方（`HistoryMapper`、`DeliveredFiles.pathOf`、`parse`）统一成这一种写法。
`toString()` 得到的是 JSON 表示，不是值本身，这两者不能混用。

### 26.3 气泡两侧的空白是结构造成的

`MessageBubble.MessageFrame` 原来的结构是
`Row[ChatAvatar | Column[头部, 内容, 操作行]]`。内容列因此永远让出
`8dp + 32dp` 的头像宽度：用户侧头像在右、智能体侧在左，于是两侧各留一条空白，
气泡永远贴不到屏幕边缘。

改为 `Column[头部行(头像 + 昵称/时刻) | 内容与操作]`，内容列 `fillMaxWidth()`。
头像与昵称同处第一行，视觉上仍是「头像在左/右」，但不再挤占内容的横向空间。

`ui-guidelines.md` 8.1 的示意图本来就是头像在头部行，是代码与文档不一致，
本轮以文档为准修代码。

### 26.4 默认协议按主机判断

原先把所有未写协议的地址一律补成 `http://`。公网域名多数只开 https，
`http://chat.example.com` 会被反代以 301 跳到 https；OkHttp 跟随 301 时
把 POST 改写成 GET 并丢弃请求体，`POST /api/auth/login` 于是变成
`GET /api/auth/login` 并返回 404。用户看到的却是「会话不存在或已被删除」。

现在的规则写在 `InstanceRepository.defaultSchemeFor()`：

| 主机形态 | 默认协议 |
| --- | --- |
| 显式写了 `http://` 或 `https://` | 不改写，用户的意思优先 |
| `localhost`、`127.*`、`::1` | http |
| `10/8`、`172.16/12`、`192.168/16`、`169.254/16`、`100.64/10` | http |
| `.local`、`.lan`、`.internal`、`.home` 结尾 | http |
| 其余（公网域名、公网 IP） | https |

端口回填与协议绑定：`https` 未写端口回填 443，`http` 回填 80。
此前统一回填 80，https 地址会得到 `https://example.com:80`，直接连不上。

登录 404 的文案改为由 `ApiException.userHint` 携带，`ErrorText.of()` 优先使用它。
文案指向地址与协议，不再说「会话不存在」。失败提示另按实际协议给建议：
http 下拿到 4xx 提示改用 https，https 下连不上提示服务端可能只开了 http
（`ErrorText.hint(e, usedHttps)`，`usedHttps` 由 `InstanceRepository.usesHttps` 判定）。

**与计划文档的两处偏离**（本轮动手前写过一份 https 修复计划，其中提出加探测请求、
把日志留在 application interceptor）：

1. 计划提出加一个「不跟随重定向」的探测请求来判断是否发生 301。实际不需要：
   `login()` 只在 `authStatus.enabled && hasUsers` 为真时调用，说明服务端确实
   提供了登录接口，此时 404 只可能是请求没有落到该端点，文案可以直接说明这一点。
2. 日志改用 **network interceptor**。application interceptor 看到的是跟随之后的
   最终响应，301 那一跳不在其中；network 层才能记下「被重定向到某处」。
   `LoggingInterceptor` 现在记录 `scheme://host:port + encodedPath`，3xx 追加
   「（重定向，未跟随）」。

### 26.5 托管平台域名的拦截位置

两个域名按用户给定的原文与文案拦截：

| 域名 | 提示 |
| --- | --- |
| `qwenpaw.platform.agentscope.io` | QwenPaw Node无法添加源于AgentScope Platform的实例，请使用私有化部署方案 |
| `modelscope.cn` | QwenPaw Node无法添加通过魔搭创空间创建的实例，请使用私有化部署方案 |

`hostedPlatformOf()` 同时匹配域名本身与子域名（`xxx.modelscope.cn` 同样是创空间实例），
匹配前统一小写并去掉末尾的点。

**拦截放在 `normalizeBaseUrl()`，不是各个界面。** 验证连接、真正连接、列智能体、
保存实例四条路径都要经过它，放在这里意味着「验证失败 → 下一步不可点」自然成立，
不必在每个页面各写一遍判断，也不会因为新增入口而漏掉。
`IllegalArgumentException.message` 直接就是给用户看的那句话，
经 `ErrorText.ofWithHint()` 原样显示。

选择 `IllegalArgumentException` 而不是新的异常类型：这个函数的既有契约就是
「参数不合法时抛它」，托管平台域名属于同一类问题，调用方已有处理。

**结论：官方客户端确实在做，但没赶上这个 beta，公开可安装的时间点未知。**
写进 README 时因此只用「已说明将随 v2.3.0 发布」这种带出处的转述，
不写具体日期。

### 28.3 Platform 实例为什么保持拦截

用户看过后确认：Platform 没有对外提供可连接的端点。要让 QwenPaw Node 连上去，
必须借助 nps 一类内网穿透把服务转发出来，而这违反平台对托管实例的使用规则。
因此不改实现，只把理由写进 README 的功能边界。

**必须与官方客户端区分开。** PR #7378 明确写了支持 Platform deployments，
走的是 Platform 自己的 OAuth 授权流，并新增二维码配对与可撤销设备 token。
也就是说：官方客户端能连 Platform，不是因为它找到了直连端点，而是因为它走
另一条鉴权通道。本项目的拦截不构成对官方能力的否定，
只是「按自建实例直连这条路不存在」。

这一点在 README 里单独写了一句，否则读者容易理解成「Platform 根本不能连」。

### 28.4 EOL 声明

README 首段之后新增「项目状态」一节：官方 Android 客户端发布并可安装后，
本项目停止维护（EOL），不再接受功能新增，仅保留仓库供查阅；
在此之前照常维护，服务端接口变动会跟进适配。

措辞限定为「官方 Android 客户端发布并可安装后」，不是「v2.3.0 发布后」。
原因是 28.2 的三条证据：v2.3.0 里移动端未必落地，把 EOL 绑在版本号上
可能出现「版本发了但客户端没发」的空档。

## 二十九、多架构构建与公开仓库（2026-10-30）

用户要求「多构建一个 x86 和 arm v7a 的客户端」，并明确「不保证额外构建的可以用」。
因此本轮的重点不是代码，而是**把可验证边界写清楚**。

### 29.1 为什么用 splits.abi 而不是 abiFilters

`abiFilters` 加两项只会得到**一个**包含四份 native 的包，约 93MB。
用户原话是「多构建一个」，他要的是分开的包，不是更大的包。
`splits.abi` + `isUniversalApk = false` 才对应这个语义。

两者不能共存：同时写时 `abiFilters` 被忽略。因此把原来那行 `ndk.abiFilters` 删了，
换成 `splits.abi`。这一点写进 release.md，否则后来者看到 `include()` 会以为
还要配 `abiFilters`。

### 29.2 实测数据（`assembleRelease`，3m12s）

| 架构 | 字节 | 约 | native 构成 |
| --- | --- | --- | --- |
| `arm64-v8a` | 24,497,163 | 23.4MB | 21.4MB |
| `armeabi-v7a` | 17,267,983 | 16.5MB | 14.5MB |
| `x86_64` | 27,443,453 | 26.2MB | 24.2MB |
| `x86` | 38,448,662 | 36.7MB | 5.1MB + `libonnxruntime.so` 29.6MB |

`x86` 比 `x86_64` 还大，原因是只有 32 位 x86 在 AAR 里额外带了一份独立的
`libonnxruntime.so`。这一条与直觉相反，值得记下来：架构「更老」不等于「更小」。

R8 只跑一次，输出的是 dex，与 ABI 无关；多架构增加的只是每个 split 各打一次包、
各签一次名的时间，不是四倍构建时间。

### 29.3 验证到了哪一步

x86_64：模拟器 `qp35` 上安装 `app-x86_64-release.apk`。

- 第一次 `adb install` 失败：`INSTALL_FAILED_UPDATE_INCOMPATIBLE`，
  原因是模拟器上装的是 debug 包，签名与 release 不同。
  按 release.md 4.1 的既有约定先 `adb uninstall` 再装，通过。
- 启动 → 通知权限 → 引导页「连接到 QwenPaw」，`ConnectingScreen` 正常渲染。
- 填 `10.0.2.2:8088`（已 `adb reverse`），点「验证连接」得到
  「连接正常，服务端 2.2.2.post1」。

arm64-v8a：此前多轮真机验证过，本轮未重复。
**armeabi-v7a 与 x86 没有验证**，原因见 29.4。

### 29.4 为什么这两个架构验不了

- **armeabi-v7a**：本机是 x86 宿主，ARM 镜像只能 `-accel off` 全模拟运行，
  慢到无法完成界面操作；AGENTS.md 也写明真机测试已停用。
- **x86**：API 30 起官方不再提供 32 位 x86 系统镜像。要测只能退回 API 29 的 AVD，
  而这与本项目 minSdk 26 的验证矩阵混在一起，成本高于收益。

**所以文案只写「额外构建、未实测」，不写「支持」。** README 用加粗区分两组，
release.md 7.1 用表格逐条标状态，CHANGELOG 也重复一次——
三处口径一致，避免用户从 Release 页面看到四个包就以为都验过。

| 文件 | 改动 |

`devlog` 里此前各节提到的「临时放开 `abiFilters` 加 `x86_64`」是历史记录，

## 附录：几条反复起作用的原则

1. **先测量，再优化。** 本项目代价最大的教训是：四个「看起来很像」的假设全部被实测推翻，
   真正原因是构建类型。
2. **先核实服务端，再写计划。** 端点形状、是否存在 summary 字段、
   字段名是 `image_url` 还是 `source.url`，都依靠阅读源码与实测确认，不依赖文档推演。
3. **坐标从 `uiautomator dump` 动态获取。** 凭截图目测点击会落空；
   语音按钮那次排查了很久的「假 bug」，实际原因是点击坐标错误。
4. **跨版本的数字要重新取。** 体积、单测数、APK 大小都曾出错。
5. **守住资源约束。** `free -h`、构建、收尾关进程，几乎每轮都执行。
6. **区分过程与结论。** 对话记录是过程，项目文档是结论。
   不要把前者当作后者修改，也不要把后者的严谨程度套用到前者。
